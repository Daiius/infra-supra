## 0. 出発点（2026-11-09）

- 外部のプレイの指摘と、シード 1〜50・何もしない方針での調査（記事コミュニティ・Next.js）:

| 構成（何もしない） | 今の合否（所持金 $1,730・満足度 0.75・止まった月 2 回以内） |
|---|---|
| Cloudflare Paid | 50 / 50 |
| さくらの VPS 2GB | 29 / 50 |
| Vercel Pro（既定の Supabase） | 0 / 50（最大 $1,473） |
| Vercel Pro・DynamoDB + 画像を Cloudflare + 提案・描き方（最大の組み合わせ） | 40 / 50 |

- ユーザーの考え:
  - 特定の閾値の合否ではなく、**おおらかに達成感を出したい**。
  - このゲームは開発体験を数えていない。所持金だけで比べると、**実務では開発が大変な構成が勝ち筋に見える**のは違う。
- そこで、合否をやめて 4 つの軸の分布の中での位置で振り返る形にし（§1〜§3）、その分布を作るために終わったプレイを匿名で集める（§4〜§6）。

## 2. 4 つの軸（D-132）

この順に並べる。

| # | 軸 | 値 | 向き |
|---|---|---|---|
| ① | 所持金 | 12 か月目の所持金 | 大きいほど上位 |
| ② | 満足度の平均 | 12 か月の満足度 S の平均（今の評価と同じ値） | 大きいほど上位 |
| ③ | 機能開発の累計 | 今の「機能開発の累計」の値そのまま（[07](./07-game-design.md) §9.4） | 大きいほど上位 |
| ④ | 費用の合計（D-166） | プレイした月の費用（月の報告の費用。インフラの請求）の合計（ドル） | **向きなし**（上位 %・自己ベスト・順位・花火の段に数えない） |

- ③ は開発体験の代わり。運用・移し替え・出来事への対応に手間を取られる構成ほど低くなるので、「実務では開発が大変な構成」が所持金だけで勝ち筋に見えるのを、別の軸で見せる。
- 軸の方針:
  - **単体で意味が分かる単純な値だけ**にする。複数の値を重みで合わせた指標は使わない（1 つの点数にまとめない。[07](./07-game-design.md) §7 の「唯一の正解を作らない」と同じ）。
  - リソースの余裕（使用率の低さ）は軸にしない（余裕を持っていても仕方ない）。
  - ④ は最初「ギリギリを攻める」（止まらずに上限の 90〜100% まで使った月の数）だったが、実測でほぼ全構成 0 か、窓を広げると常に 100% になり、構成の料金体系だけで決まったので、**費用の合計**に替えた（D-166）。高いから良い・低いから良いという軸ではないので、分布の中の位置と中央値・前回との差だけを出す。
  - **止まった月の数は軸にしない。** 完走した人は 0〜2 回で差が出ず、満足度の可用性の要素と重なる。振り返りに回数として出す。
- 計算は game の純粋関数に置き（段 1）、クライアントとサーバーが同じ関数を使う（§5）。

### 2.1 所持金の目標の目安（D-167）

- シナリオの `goal.cash`（D-142 の参照値。記事 $1,730・受託 $1,700）を「目標の目安」として出す。**下回っても未達・✗ にはしない**（D-131 の合否をやめた決定のまま。合否の言葉・色を使わない）。
- 出す所: 推移（所持金のグラフの控えめな点線と、所持金の見込みの文の下の 1 文）・完走のダイアログと結果の画面の ① 所持金の欄（「目安を $Z 上回りました」「目安まで $Z でした」）。
- 後で、集計の分布（完走した人の 12 か月目の所持金の上位 90% の線など）から目安を出す余地を残す（今はシナリオの値のまま）。

## 3. 振り返りの画面と花火（D-131・D-133）

### 3.1 完走のダイアログ

- 4 軸それぞれで「分布のどこにいるか（上位何 %）」を出す。分布は 2 種類（§6）: **同じシード**のプレイと**全シード**のプレイ。
- **上位に入った軸が多いほど花火を派手にする**（花火の数・色・続く長さ。今の花火の動き（D-25）と、動きを減らす設定の扱いはそのまま）。数えるのは向きのある 3 軸（D-166）。分布が無いときは自己ベストの数に依らずいつも 1 段（D-168。D-145 を撤回）。
- 集計が無い・通信できないときは、自分の値と、手元（localStorage）に溜めた過去の結果との比較を出す（§3.3）。どちらの比較かを画面に明記する。
- 止まった月の回数は、4 軸の下に振り返りとして出す（軸ではない）。

### 3.2 始める画面の「目標」の箱

- 今の「目標（12 か月後に、すべて満たす）」の箱（web の `scenario-briefing.tsx`）を、**「12 か月走り切る・4 つの軸で振り返る」紹介**に作り直す。目標の値は出さない。
- 見た目は完走のダイアログに寄せる。success 系の色は border で使い、**全面を塗りつぶさない**（ユーザーの以前の要望をここで扱う）。

### 3.3 手元の結果の履歴

- 終わったプレイ（完走・途中終了）ごとに、シナリオ・シード・終わった日・構成の要約・4 軸の値・終わり方を localStorage に足していく（集計の送信とは独立。オフラインでも溜まる）。
- 集計に届かないときの比較の元になる。読めない・版が違う履歴は、今のセーブ（[02](./02-architecture.md) §5）と同じく黙って捨てる。

## 4. 匿名の集計: 送るもの（D-134）

- **終わったプレイ（完走・途中終了の両方）を自動で匿名のまま送る。止める設定は置かない。**
- **プライバシーポリシーの画面を置き**、利用の分析のためのデータとゲームの結果を送ることを明記する（段 2）。

送る中身:

| 項目 | 中身 |
|---|---|
| シナリオ | シナリオの id |
| シード・始めた日 | クライアントが決めた値（§6）。始めた日は改定の出来事（D-21）に効く |
| 構成 | stack・framework・components・描き方の設定（今のセーブの始めたときの選択と同じ） |
| 行動の列 | 月ごとの行動（今のセーブ `SaveData` の `turns` と同じ中身。D-26） |
| 4 軸の値 | クライアントが計算した値（§2） |
| プレイの id | プレイごとのランダムな nonce（UUID）と手元の結果の履歴の id をつないだもの（`<nonce>.<16 進 8 文字>`）。同じプレイの送り直しを 1 件に数えるため。端末や人を識別しない（D-169） |
| 終わり方 | 完走 / 途中終了の理由（§1） |

- 送るのは 1 プレイ 1 回（手元の履歴に新しく足したとき）。web はビルドの環境変数 `VITE_STATS_ENABLED` が立っているときだけ送り、失敗しても画面に出さず送り直さない（D-152）。「この月に戻る」を使ったプレイは `rewound` の印つきで送る（D-148）。
- **持たないもの**: 名前・IP アドレス・端末の情報（User-Agent など）。サーバーとリバースプロキシのアクセスログにも **IP を残さない設定**にする。Vercel 経由の中継（§5.3）では送り手の IP が転送のヘッダー（`X-Forwarded-For` など）で届くので、そのヘッダーもログに残さない。
- 表示名・ログインは無い（[12](./12-external-scenarios-and-ranking.md) ES-16 の「匿名の表示名」も置かない）。
- プライバシーポリシーの画面（web の `privacy-policy.tsx`）は、設定のダイアログと画面の一番下のリンクから開く。文面は D-153。

## 5. 匿名の集計: サーバー（D-135）

### 5.1 形

| 項目 | 決定 |
|---|---|
| 実行 | **さくらの VPS 上の Hono のサーバー**（node の常駐プロセス） |
| API | **Hono RPC**。サーバーが `AppType` を export し、web は `hc<AppType>` でサーバーの型をそのまま使う（REST の型を手で二重に書かない） |
| DB | **すでにある Postgres**（同じ VPS で動いているもの） |
| 検証 | 送られた行動を**同じエンジン（game）で再生**して 4 軸を計算し、クライアントが送った値と**食い違えばエラーを返す**（保存しない）。書き換えと、画面とサーバーの版ずれの両方をここで止める |
| 版 | **版のハッシュは付けない。** Vercel（画面）と VPS（サーバー）の版は手動でそろえる（両方を同じコミットからデプロイする） |
| 見せ方 | ブラウザからは別のドメインに見せず、**Vercel 経由で画面と同じオリジンの `/api/*` に中継する**（§5.3。D-139） |
| パッケージ | `packages/` に Hono のサーバーのパッケージを足す（名前は §8 で決める。仮に `packages/stats`）。依存の向きは `stats → game → catalog → estimator`、web はサーバーの**型だけ**を devDependencies で読む（[02](./02-architecture.md) §1 に 1 行足す） |

- 画面のデプロイ先は Vercel（この決定で [02](./02-architecture.md) §6 の「デプロイ先は未決」のうち画面の側が決まった）。
- [12](./12-external-scenarios-and-ranking.md) §5.1 の「クライアントが送る点数は信用しない」は、「送らせて、サーバーが再生した値と照合する」形で満たす。照合で食い違ったものは受け付けない（ES-07 の「不正な行動を含めば拒否」に相当）。
- 決定論の前提（[02](./02-architecture.md) §3）が崩れると、正しいプレイまでエラーになる。ES-15（超越関数・`Date`・`Math.random` を状態の計算に使わないことをテストで止める）は段 2 で入れる。
  → 段 2 で入れた（D-151。stats の `determinism.test.ts`）。estimator の結果に効く計算にはすでに超越関数（`Math.exp` など）があるので、今ある箇所を数で固定して増やさないようにし、エンジンの間の最後の桁の差は照合の幅（相対 1e-9。D-149）で吸収する。

### 5.3 Vercel 経由の中継と接続先の秘匿（D-139）

- ブラウザからは別のドメインに見えないよう、**Vercel 経由で画面と同じオリジンの `/api/*` に見せ**、VPS の Hono へ中継する。
- 🔒 **public リポジトリに本番の接続先（VPS のホスト名・URL など）を書かない。** `vercel.json` に宛先を直書きしない（AGENTS.md の「実ドメインは公開文書に書かない」と同じ扱い）。宛先は Vercel のダッシュボードの環境変数（例 `API_ORIGIN`）に置く。

| 案 | 形 | 気にすること |
|---|---|---|
| **第一案** | `vercel.ts`（`@vercel/config`）で rewrites の宛先をビルド時の環境変数（`API_ORIGIN`）から組み立てる | ビルド時に環境変数が読めるか・rewrites で使えるかは公式に明記が見当たらない（出典: https://vercel.com/docs/project-configuration/vercel-ts 、https://community.vercel.com/t/is-there-any-way-to-use-env-in-vercel-json/1146 。2026-11-09 に確かめた範囲）。**段 2 の最初に小さなスパイクで確かめる** |
| 予備案 | 実行時に環境変数を読んで転送する小さな Vercel Function（`/api/[...path]`） | 確実に動くが、呼び出しと待ち時間（VPS の応答を待つ間）ぶんのメモリを Fluid の枠で消費する |

- 再生の重さ: 手元の実測で 12 か月 1 回 4〜24 ms（Node・温まった状態）。常駐の node で足りるので、Rust での実装（エンジンの移植になる）は採らない。
- **採らなかった案**: Vercel Functions で API 自体を動かす（画面と同じデプロイになり版が自動でそろう）。既存の Postgres を使いたいので採らなかった。
- **実装（D-150）**: 第一案で `packages/web/vercel.ts` を置いた。`API_ORIGIN` が無い・空なら設定は空（今の本番のまま）、https のオリジンでなければビルドを止める、あれば `/api/:path*` → `<API_ORIGIN>/api/:path*` の rewrite を 1 本。公式の文書には「vercel.ts executes at build time」「use environment variables to conditionally set routes」とあるが、ダッシュボードの環境変数がビルドのときに入るとは明記されていないので、§7.1 の手順 5 のプレビューで確かめる。動かなければ予備案（転送の Function）を作る（今は作っていない）。

### 5.4 実装（段 2・D-149・D-154・D-155）

`packages/stats`（Hono RPC・drizzle・node）。web は `stats` を devDependencies で持ち、`hc<AppType>('')` で型だけを使う（`stats-client.ts`）。

| 口 | 中身 |
|---|---|
| `POST /api/results` | 本文 `{ playId, save, axes, end }`（§4。`playId` の形が違えば 400。D-169）。シードは 32 ビットの整数だけ。zod でおおまかな形 → game の `parseSave` → `replaySave` で再生 → 4 軸（相対 1e-9 まで同じとみなす）と終わり方を照合。201 保存・200 同じプレイ（同じ `playId`。`duplicate`）。どちらも `inHistogram`（保存されている行が分布に入るか。段 3 の画面が自分を数えるかに使う。D-162）を返す・400 形が違う・413 大きすぎる（64 KB）・422 `invalid-save` / `replay-failed` / `unfinished` / `mismatch`（食い違った欄つき） |
| `GET /api/results/histogram?scenario=&axis=[&seed=][&value=]` | 完走・戻っていないプレイだけの分布。`{ count, min, max, bins: [{ from, to, count }], position? }`。どの軸も最小〜最大を 20 本（④ が費用の合計になったので幅 1 のビンはやめた。D-166）・中央値 `median`。`value` を付けると `position: { above, equal }`（段 3 の上位 %） |
| `GET /api/results/distribution?scenario=&seed=[&<軸>=]` | 段 3 の画面が使う。4 軸 ×（同じシード `seed` / 全シード `all`）の 8 本を 1 回で返す（`{ scenarioId, seed, axes }`。切り方は上と同じ。値を付けた軸だけ `position`）。`position` の「同じ」は照合と同じ相対 1e-9 の幅（D-161） |
| `GET /api/version` | `{ commit, builtAt }`（ビルド引数から。版を手動でそろえるときの確かめ） |

## 6. シードと分布（D-136・D-137）

- **シードはクライアントが決めて**結果と一緒に送る。サーバーはシードを発行しない（オフラインで遊べる。[12](./12-external-scenarios-and-ranking.md) §5.2 のお題（ticket）は作らない）。
- 分布は 4 軸 ×（**同じシード** / **全シード**）の 8 本。楽なシードを選び直しても、同じシードの分布の中では有利にならない。
- **ヒストグラムに入れるのは完走したプレイだけ。** 途中終了は終わり方つきで保存し、バランスの見直しの材料にする（画面には出さない）。
- 構成ごとの絞り込み（同じ構成の人の中での位置）は後で足す（§8）。

段 3 の実装（D-161〜D-164）:

- **取り方**: 完走したとき（と、完走した保存を開き直したとき）に、`GET /api/results/distribution` で 4 軸 × 2 を 1 回で取る（D-161）。送信の応答を待ってから取るので、保存された行が分布に入る（応答の `inHistogram`）なら**自分を含む**分布になる。入らない・保存されなかったプレイは自分を 1 件足して数える。開き直したときは、送ったときの結末を手元に覚えた値で決める（D-162）。
- **上位 %**: 自分以上の件数（同じ値を含む）÷ 件数（自分を含む）。上位 25% 以内を「上位」とし、同じシードの分布が見せられればそちらで、見せられなければ全シードで見る。花火の段は上位に入った軸の数（D-163）。

### 7.1 段 2 のデプロイの手順（ユーザーが行う作業）

実ドメイン・接続先・パスワードはリポジトリに書かない（`<…>` は手元の値に置き換える）。画面とサーバーは**同じコミット**からデプロイする（D-135）。

1. **DB を作る**（すでにある Postgres に、別の DATABASE とロールを作る。D-154）: `PSQL='<管理者で繋ぐ psql のコマンド>' sh packages/stats/scripts/create-db.sh --check` で今の状態を見てから、`--check` を外して流す（パスワードは尋ねられる。切り戻しはスクリプトの先頭）。
2. **イメージを作る**（GHCR。D-172）: GitHub の Actions で「Stats image」（`.github/workflows/stats-image.yml`）を、デプロイしたい ref を選んで手で走らせる。`ghcr.io/daiius/infra-supra-stats:<コミットの SHA>` ができる（main からなら `latest` も）。初回は GitHub の Packages でパッケージの公開範囲を決める（公開のリポジトリのコードだけで秘密は入らないので public にしてよい。private のままなら VPS で `docker login ghcr.io`）。
3. **VPS に置くファイル**（`packages/stats/deploy/` の例を写して埋める。リポジトリには入れない）: `compose.yml`（`compose.example.yml`。既存の Postgres の網を external で指定）・`server.env`（常駐のサーバーのロールだけ）・`migrate.env`（管理ロールだけ。常駐のコンテナには管理ロールのパスワードを渡さない）・`deploy.sh`。env は `chmod 600`。
4. **migration を流し、サーバーを入れ替える**: `sh deploy.sh <SHA> --check` で今の版とイメージの有無を見てから、`sh deploy.sh <SHA>`（pull → migration → `up -d` → `/api/version` の commit が SHA と一致するかまで確かめる）。サーバーは `127.0.0.1:4000` にだけ開け、前段の nginx から届かせる。
   - 🔒 **前段の nginx のアクセスログに IP を残さない**（§4）: `deploy/nginx.example.conf` のとおり、`$remote_addr`・`$http_x_forwarded_for` を含まない `log_format` にし、`X-Forwarded-For`・`X-Real-IP` もサーバーへ渡さない。error_log はどのレベルでも IP を付けるので、このサーバーの分は `/dev/null` に捨てる（server を決める前の TLS の失敗などは nginx 全体の error_log に出るので、その保存先と期間も見直す）。
   - API の宛先は https にする（`vercel.ts` が https のオリジンしか受けない）。
   - migration は**足す方向だけ**にする（流した migration は書き換えない）。前の SHA に戻すときも、前の版のサーバーが新しい表で動く範囲に保つ。
5. **中継を確かめる（D-150 のスパイク）**: Vercel のプロジェクト infra-supra（チーム faveo-systema）の Root Directory は `packages/web`（2026-11-09 に CLI で読み取って確認済み。Framework Preset は Vite・Node は 26.x）なので、`packages/web/vercel.ts` のままでよい。環境変数 `API_ORIGIN` に `https://<VPS のホスト名>` を（Preview だけに先に）入れ、プレビューをデプロイして `<プレビューの URL>/api/version` を開く。VPS の `{ commit, builtAt }` が返れば第一案で動いている。404 や画面の HTML が返れば、`vercel.ts` が環境変数を読めていないので予備案（転送の Function）を作る（Claude に頼む）。
6. **送信を立てる**: 動いたら `API_ORIGIN` を Production にも入れ、`VITE_STATS_ENABLED=true` を Production（と Preview）に入れて再デプロイする。1 回遊び切って、`select count(*), max(created_at) from results;` で 1 行増えたこと、プライバシーポリシーの「まだ何も送っていません」が消えたことを確かめる。
7. **版をそろえる**: 以後、画面とサーバーを同じコミットからデプロイし、`/api/version` の `commit` と Vercel のデプロイのコミットが同じかを見る。版がずれると正しいプレイも `mismatch`（422）になる（画面には出ない）。
