## 2. ゲームの状態

| 状態 | 内容 |
|---|---|
| 所持金 | 収益 − インフラの費用（見積エンジン）− 行動の費用 |
| 規模 | PV・MAU。成長率は満足度と出来事で変わる |
| **満足度**（G-01） | 要素ごとに「良い・普通・悪い」の段階で持ち、シナリオごとの重みで合計する。成長率（口コミ）と解約に効く |
| **開発の手間**（G-02） | 月ごとのポイント。改善・乗り換え・出来事への対応・自前運用の維持が取り合い、**余りが機能開発**（満足度と成長）に回る |
| ためていく量 | DB の容量・画像の保存量など。月ごとに増え、前提の境目に近づく |

満足度の要素:

| 要素 | 何で決まるか |
|---|---|
| 可用性 | 停止（前提に当たった）・偶発的な障害 |
| 速さ | 遅延の前提・SSR の重さ・画像の重さ |
| 画質 | 画像の圧縮の度合い |
| 鮮度 | ISR の再検証の間隔 |
| 機能（D-18 で追加） | 機能開発に回せた手間の累計（§9.4） |

- 性能の精密な推定（p50/p95）は待たない。段階への写し方はシナリオのデータ（ゲーム上の仮定）。
- 自前運用（VPS）の手間はお金（試作の $30/月）ではなく**ポイント**で表す。「安いが自分の時間が減る」がそのまま出る。

## 3. 出来事（G-03）

3 種類を混ぜる。

| 種類 | 起き方 | 例 |
|---|---|---|
| 状態で起きる | ためていく量や規模が境目を越える | DB が 8 GB を超えた・同時接続が増えた |
| 提案として来る | 受けるかどうかをプレイヤーが選ぶ。受けると満足度と成長が上がるが、新しい要件が乗る。断れば機会を逃す（機能追加の延期・企画書 §5.4） | チャット（WebSocket）を足すか・動画のアップロードを足すか |
| シナリオの台本 | 事業の出来事。時期はシードで幅を持たせる | 法人顧客が SLA を求める・料金改定・チームが増える |

**効き方は 3 段階**（ユーザーの補足: 乗り換えを迫るのはまれな大きなイベントにする）:

| 頻度 | 対応 | 例 |
|---|---|---|
| ふだん | プランの変更・設定 | 込み分に近づく・急増 |
| ときどき | 部品の追加・差し替え | 機能の提案を受けて要件が増える |
| **まれ（低確率）** | 乗り換えの検討 | SLA の要求・買い足せない上限（D1 の 10 GB）・大きな料金改定 |

- 乱数（シード付き）は偶発的な障害と、話題になる時期・まれな出来事の発生だけに使う。運で詰まない範囲に保つ（spike game 所見 6）。

完成品の構成を選ぶ代わりに、**役割ごとのスロット**に部品を選ぶ（グラフエディタ（Phase 5）の手前の形）。**Cloudflare を先に深く**し、Vercel と VPS は共通の役割だけ選べるようにする。

| 役割 | Cloudflare の選択肢 | 不適切な選択で当たる前提の例 |
|---|---|---|
| ISR のキャッシュ | KV / R2 / キャッシュしない（毎回 SSR） | キャッシュしない: Workers の CPU と D1 の読み取り（Cloudflare ではリクエスト数は変わらない）。KV の 1 秒 1 回は ISR では当たらない（§11.4） |
| 画像 | Images（リクエスト時）/ 事前に作ったサイズ違いを R2 / 最適化しない / D1 に置く（不適切） | 最適化しない: Cloudflare では速さだけ（R2 は転送量に課金しない）。Vercel では転送量と速さ。D1 に置く: 1 データベース 10 GB・1 行 2 MB |
| DB | D1 / KV を DB 代わりに（不適切）/ 外部の Postgres（Hyperdrive 経由で Supabase） | D1: 1 データベース 10 GB（引き上げ不可）。KV: 同じキーへの書き込みは 1 秒 1 回まで・他の拠点への反映は 60 秒以上かかることがある |
| リアルタイム | Durable Objects / なし | チャットの提案を受けたときに要る |

- 部品の組み合わせは、エンジンのノードとクラスごとの経路の違いとして表す（catalog の構成を部品から組み立てる）。
- **追加で集めるデータ**: Durable Objects・Hyperdrive・Queues の料金と制限、Workers のメモリ上限（いずれも未取得）。→ 2026-10-31 に取得（[調査メモ](./research/2026-10-31-gd4-data.md)。catalog には未収録）。GD-4 の詳細設計の案は §11。

## 5. 推移と見込み（G-05・F-1）

- 推移のグラフ（PV・費用・収益・所持金・満足度）を常に出す。
- 前提の使用率の推移を貯め、**直近 2〜3 か月の伸び率で外挿**した「このペースだと N か月後に超える」を出す。流量は倍率、ためていく量は月あたりの増分で外挿する。
  プレイヤーが見ている推移だけで計算し、ゲームの内部（成長率・台本）は覗かない。
- 残りの期間内に超える見込みのときだけ出す。出来事で外れたら、振り返りに「見込みが外れた理由」を出す。
- 「もう少し」（境目の半分・70% を超えた前提）の強調は続ける。
- **実装（GD-1・済）**: `packages/game/src/trends.ts`（`premiseTrends`・`selectTrends`）と、画面の「これまでの推移」（数値タイル 4 つ・収益と費用の折れ線・前提の使用率の小さな折れ線を上位 4 つ）。
  - 見込みの線は、境目を越える最初の月で止める（先まで伸ばすと縦軸が広がり、実際の推移が潰れるため）。
  - **話題になった月は見込みを出さない**: その月だけの伸びで外挿すると誤解を招く（10% → 2 か月後に超える、のようになった）。話題になったことはプレイヤーにも見えている出来事なので、ゲームの内部を覗くことにはならない。
  - 前の月の見込みより早く超えたら「見込みより早く超えた」の印を付ける。理由の詳しい振り返りは出来事（GD-3）と一緒に作る。
  - グラフは dataviz の指針に沿う（2 系列は検証スクリプトで全検査に通過・明るいテーマのみ。暗いテーマは画面全体の切り替えと一緒に検証する）。

## 6. 行動と代償

一度やれば終わりの改善にせず、代償を持たせて状況しだいで最適が変わるようにする。

| 行動 | 効果 | 代償 |
|---|---|---|
| 画像を圧縮する | 転送量が減る | 画質（満足度）。画像が売りのシナリオで重い |
| ISR の間隔を延ばす | 再生成が減る | 鮮度（満足度）。ニュース性の高いシナリオで重い |
| SSR を最適化する | CPU が減る | 開発の手間 |
| 部品を差し替える | 前提が変わる | 開発の手間（部品による） |
| プランを変える | 上限・込み分が変わる | ほぼ即時・手間なし（乗り換えと区別する。spike game 所見 5） |
| 乗り換える | 構成が変わる | 開発の手間（数か月）・移行の期間とリスク |

## 7. シナリオと評価（G-06・G-07）

- シナリオは**データで定義する**: テンプレート（Workload）・収益モデル・満足度の重み・開発の手間の量・出来事の台本・目標。
- まず**記事コミュニティ 1 本を深く**作り直して仕組みを固める。2 本目（画像投稿サービス。画像がたまり、画質の重みが大きい。企画書のシナリオ C）は、データの追加だけで足せるかの検証として後で入れる。
- **規模と成長の見直し（GD-3 で）**: 試作の記事コミュニティは月 40% の成長が 12 か月続き（約 53 倍・15 万 → 800 万 PV）、
  話題の月は 10 倍になる。インフルエンサー級の規模で、遊んだユーザーの感想も「非現実的な稼ぎ方」だった（2026-10-31・このままでよいと判断）。
  1 PV あたりの収益（$0.25/1,000 PV）は控えめで、稼ぎに見えるのは規模の急増による。構成の差が勝敗に効くのに規模が要った（spike game 所見 1）ため。
  成長を満足度で決める形（GD-2）とシナリオのデータ化（GD-3）のときに、サイトの性格に合った規模へ見直す。
- 評価:
  - **合否**: 所持金が目標以上、かつ満足度の平均が目標以上、かつ止まった月が上限以内（D-18 で停止の回数の上限を残すことにした。§9.6）。
  - **途中のゲームオーバー**（D-19）: 止まった月が上限を超えた時点・所持金が尽きた時点・規約違反の指摘を受けた翌月も違反したままのとき（アカウント停止）。12 か月目を待たない。
  - **軸ごとの成績**: 累積の利益・満足度・最終的な規模・機能開発に回せた手間を、1 つの点数にまとめずに並べる（唯一の正解を作らない。企画書 §11.3）。
  - **振り返り**: 当たった前提・近づいた前提と、そのときの選択を並べて締める。

### 9.1 満足度の段階の決め方

毎月、エンジンの結果（`estimate` の前提）と今の設定（`Mods`）だけから判定する。p50/p95 の推定は使わない（§2 の注記）。

| 要素 | 良い | 普通 | 悪い | 判定に使うもの |
|---|---|---|---|---|
| 可用性 | 下の 2 つに当たらない | 偶発的な障害（VPS）・乗り換えの切り替えの月 | 止まる前提に当たった（block・upgrade-required。規約違反 policy は止めずに指摘 → アカウント停止で扱う。D-19） | 試作の `index.ts:189-197` の `incident`・`blocking`、`pendingMigration`（実装では `switching`） |
| 速さ | 重さ 0 | 重さ 1〜2 | throttle の前提に当たった、または重さ 3 | 下の「重さ」 |
| 画質 | 圧縮なし（150 KB） | 中（100 KB） | 強（70 KB） | `Mods.imageKB` |
| 鮮度 | 再検証 5 分以下 | 1 時間以下 | 1 時間より長い | `Mods.revalidateSec` |

速さの「重さ」は次の数（各 1）:

| 重さ | 条件 | 根拠 |
|---|---|---|
| SSR が重い | `ssrCpuMs` ≥ 12 ms | テンプレートの既定 15 ms（`packages/catalog/src/templates/index.ts:12`）・Cloudflare Free の上限 10 ms（spike 所見 2） |
| 画像が重い | `imageKB` ≥ 120 KB、またはサイズ違い 1 種（大きい画像を全端末に配る） | `index.ts:43-68` の改善の値 |
| 前提に近い | throttle の前提の使用率 ≥ 70%（「もう少し」と同じ境目） | `index.ts:198`・`index.ts:240` |

- 試作の既定（SSR 15 ms・150 KB・3 種）は「重さ 2 → 普通」から始まる。最適化・圧縮で「良い」に上がるが、圧縮は画質を下げる（§6 の代償がそのまま出る）。
- GD-4 の部品（KV の反映遅延・画像の最適化なし）は、この表の判定の入力を足すだけで乗る。

### 9.2 段階の数値と合計

- 段階 → 数値: **良い 1・普通 0.5・悪い 0**。満足度 S = Σ 重み × 数値（0〜1）。毎月の S を記録し、推移のグラフ（§5）に出す。
- 重みはシナリオのデータ。§9.4 の機能開発を受ける 5 つ目の要素「機能」を足す案（→ §9.9 の T-1）。

| 要素 | 記事コミュニティ（案） | 画像投稿サービス（GD-5 の参考） |
|---|---|---|
| 可用性 | 0.40 | 0.35 |
| 速さ | 0.20 | 0.15 |
| 機能 | 0.20 | 0.15 |
| 鮮度 | 0.10 | 0.05 |
| 画質 | 0.10 | 0.30 |

記事コミュニティでの代表的な月の S（機能は「良い」とする）:

| 月の状態 | S | 試作で対応する扱い |
|---|---|---|
| 何もしない・問題なし（速さ 普通） | 0.90 | 成長 40% |
| throttle に当たった（速さ 悪い） | 0.80 | 成長 ×0.5（`index.ts:216-220`） |
| 偶発的な障害（可用性 普通） | 0.70 | 成長 ×0.7（`index.ts:210-215`） |
| 止まった（可用性 悪い） | 0.50 | 成長 −20%（`index.ts:204-209`） |

### 9.3 成長率・解約への写し方

月の純成長率 = **獲得 − 解約**。

| 項 | 式（案） | 意味 |
|---|---|---|
| 獲得（口コミ） | `0.5 × S`。**可用性が「悪い」月は 0** | 止まっている間は見られず、口コミが止まる |
| 解約 | `0.5 × (1 − S)` | 不満の分だけ離れる |

- 成長の式に入れる S は**評判** = (今月の S + 前月の S) / 2（1 か月目は今月の S。U-3）。1 回の停止の影響が 2 か月に分かれる。可用性が「悪い」月に獲得を 0 にするのはその月だけ。
- S = 0.9 で 0.45 − 0.05 = **40%**（今の `GAME.growth`・`index.ts:16` と一致させ、規模の見直しは GD-3 に残す）。
- 止まった月は 0 − 0.25 = **−25%**（今の −20%・`index.ts:26` の置き換え）。障害の月は +20%、throttle の月は +30%。
  `blockGrowth`・`throttleGrowthPenalty`・`incidentGrowthPenalty`（`index.ts:26-32`）は満足度に吸収して消す。
- **話題の月**（`index.ts:17-19`）: PV の 10 倍は台本として残し（GD-3 で出来事へ）、その後に残る倍率を満足度で変える。
  `残る倍率 = 1 + 0.8 × 評判（話題の月）/ 0.9`。既定の S で今の 1.8 と一致し、話題の月に止まると話題の多くを逃す。
- 収益の減り（`blockRevenueLoss` など・`index.ts:25-31`）は「止まっていた時間の損」としてお金の側に残す。満足度（先の成長）とは別の効き方として扱う（→ T-3）。
- 画面には獲得と解約を分けて出す（「満足度が下がると解約が増えた」が読めるように）。

### 9.4 開発の手間のポイント

**月 10 ポイント**（1 人が 1 か月に使える開発の時間を 10 とする）。毎月の配分は次の順で、余りが機能開発になる。繰り越しはしない。

| 順 | 使い道 | 消費（案） | 置き換える試作の値 |
|---|---|---|---|
| 1 | 自前運用の維持（VPS） | 3 / 月 | `selfHostedOpsUsdPerMonth` $30（`index.ts:29`）を消す |
| 2 | 割り込み（出来事への対応・GD-3） | 出来事のデータで決める | — |
| 3 | 進行中の乗り換え | 下の表 | `migrationCost` $40（`index.ts:23`）を消す |
| 4 | その月に選んだ行動 | 下の表 | `IMPROVEMENTS[].cost`（`index.ts:43-68`）のお金を消す |
| 5 | **機能開発（余り）** | 残り全部 | — |

| 行動 | 消費 | 期間 |
|---|---|---|
| プランの変更（Cloudflare Free ↔ Paid、Vercel Hobby ↔ Pro。`MVP_STACKS` の 0↔1・2↔3） | 0 | 翌月から（spike 所見 5） |
| 画像の圧縮の段階を変える | 1 | 翌月から |
| サイズ違いの数を変える | 1 | 翌月から |
| ISR の間隔を変える | 0 | 翌月から（代償は鮮度だけ） |
| SSR を最適化する（1 段あたり −5 ms・下限 5 ms） | 4 | 翌月から |
| 乗り換え（サーバーレス同士） | 6 / 月 × 2 か月 | 3 か月目に切り替え。期間中は新旧両方のインフラ費用を払う（U-5） |
| 乗り換え（VPS へ・VPS から） | 6 / 月 × 3 か月 | 4 か月目に切り替え。期間中は新旧両方のインフラ費用を払う（U-5） |

- **機能開発の効き方**: 累積の機能ポイント F を、シナリオの期待 E = 8 × 経過月数 と比べ、要素「機能」の段階にする（F/E ≥ 1 → 良い・≥ 0.6 → 普通・それ未満 → 悪い）。
  Cloudflare Paid で何もしなければ 10/月で「良い」、VPS は 7/月で「普通」。「安いが自分の時間が減る」（§2）が満足度を通じて成長に出る。
- **機能が増えると重くなる**: F が 10 増えるごとに SSR の CPU が +1 ms（上限はテンプレートの既定 + 5 ms）。最適化が一度きりにならない（§9.5）。
- **足りないとき**: 4（選んだ行動）は残りを超えるものを選べない（画面で無効にし、理由を出す）。
  1〜3 の必須分が 10 を超えたら、乗り換えの進捗が足りない分だけ延び、機能開発は 0。借り越し（翌月の前借り）はしない。

### 9.5 状況で最適が変わる行動

改善を「済み / 未」のフラグ（`GameState.improvements`・`index.ts:107`、重複の禁止 `index.ts:296`）から、**いつでも戻せる設定**に変える。

| 設定 | 選択肢 | 効果 | 代償 | 状況で変わる理由 |
|---|---|---|---|---|
| 画像の圧縮 | なし 150 KB / 中 100 KB / 強 70 KB | 転送量 ↓・速さ ↑ | 画質 ↓ | Vercel では転送量が大きく効く（spike 所見 4）が、他では画質を失うだけ。話題の月の前だけ強くする、などが選べる |
| サイズ違い | 3 / 2 / 1 種 | 画像変換の件数 ↓ | 1 種で速さ ↓（重さ +1） | 画像変換が課金される構成でだけ効く |

| プラン | 同じ事業者のプラン | 上限・込み分 ↑ | 固定費 ↑ | 規模が小さいうちは固定費が不利（spike 所見 7） |

### 10.4 ためていく量

今は `db.sizeGB` 0.3・`images.storedGB` 20・`images.distinct` 5,000 が固定（`templates/index.ts:59-67`）。ゲームの状態に**在庫**を持たせ、毎月の PV から増やす。

```ts
type Stock = { dbGB: number; imagesGB: number; images: number; articlePages: number };
type StockRule = {
  initial: Stock;                 // テンプレートの値から作る
  dbGBPerMillionPV: number;       // コメント・ログ（ゲーム上の仮定）
  gbPerImage: number;             // 原本 + サイズ違い。テンプレートの storedGB / distinct = 4 MB から導く
  // 画像の投稿数 = MAU × uploadsPerMau（テンプレートの値。MAU = 人の PV / 10）
};
```

| 項目 | 案 | 根拠 |
|---|---|---|
| 画像 | 毎月 `images += MAU × uploadsPerMau`・`imagesGB += 投稿数 × 0.004 × (imageKB / 150)`（圧縮で保存量も減る。ゲーム上の仮定） | 投稿数の式はテンプレート（`templates/index.ts:21-22`・`:65`）と同じ。1 枚 4 MB は 20 GB / 5,000 枚 |
| DB | 毎月 `dbGB += 0.05 × PV / 100 万`（ゲーム上の仮定） | 12 か月では D1 の 10 GB に届かない程度。届くのは P-4 を受けたときだけ（まれ） |
| 記事ページ | P-4 だけで増やす | ISR の再生成の量（spike concept 所見 17）が変わる |
| Workload への写し方 | `db.sizeGB = dbGB`・`images.storedGB = imagesGB`・`images.distinct = images`・`routes[article].pages = articlePages` | `simulate.ts:159-166`・`:233` がそのまま保存量と VPS のディスクにする |
| 推移と見込み | 制限 `storage-gb`・ホストのディスク・`gb-month` のプールは既に `accumulates: true`（`premises.ts:127`・`:186`・`:242`）。月ごとの増分で外挿する（`trends.ts:44-49`） | 新しい仕組みは要らない |

- 概算（今の catalog）: 100 万 PV で投稿は月 1,000 枚・4 GB。VPS のディスクは 30 GB から始まり、P-2 を受けない限り 12 か月で 100 GB に届かない。P-2 を受けると投稿が 3 倍になり、12 か月目の前後で届く（5 倍では大半のシードで 12 か月目までに止まった。§10.12）。圧縮とサイズ違いで 1 枚あたりの保存量が減る（下の表）ので、VPS では「画質と保存量」の判断になる。
- 画像の種類（`distinct`）が増えると、Cloudflare Images の一意な変換（種類 × サイズ違い）が増える。今も 1 か月目から込み分の 3 倍（15,000 / 5,000）で、Paid では費用だけ。

「運で詰まない」ための保証（テストで確かめる）:

1. 1〜2 か月目は台本・提案を出さない（状態の出来事だけ）。
2. まれな出来事は高々 1 回・予告あり。P-4 は提案なので断れる（断れば何も変わらない）。
3. 止まる効果を持つ要件（SC-5 の SLA など）は、予告の月から「乗り換えの手間（2〜3 か月）」より長い猶予を持つ。乗り換えを始めれば猶予を満たしたとみなす（D-19 の規約違反と同じ扱い）。

### 10.6 規模と成長の見直し

今は 15 万 PV から月 40% で 12 か月（53 倍・800 万 PV）、話題の月は 10 倍（§7）。spike game 所見 1 は「利幅を薄くし、規模を伸ばして、ようやく構成の差が効いた」。
規模を小さくすると、構成の差は**料金の絶対額では効きにくくなる**ので、効かせる場所を変える。

| 項目 | 今 | 案（ゲーム上の仮定） | 考え方 |
|---|---|---|---|
| スタートの PV | 15 万 | **30 万**（MAU 3 万） | 小さな技術記事のコミュニティ |
| 成長（S = 0.9） | 40% / 月 | **12% / 月**（獲得 0.15・解約 0.15） | 12 か月で約 3.5 倍・約 100 万 PV |
| 満足度 1 段の差（S 0.9 と 0.8） | 40% と 30%（12 か月で約 2 倍の差） | 12% と 9%（約 1.35 倍の差） | VPS の「機能 普通」が複利で開きすぎない |
| 話題の月 | × 10・残る倍率 1.8 | **× 3**・残る倍率 1.3（`buzz.extra` 0.3） | 前兆を出す（SC-1） |
| 収益の単価 | $0.25 / 1,000 PV | 据え置き | 利幅の薄さは残す（所見 1） |
| 12 か月の収益（概算） | — | 約 $2,200 | 延べ約 900 万 PV × $0.25 |

構成の差が効く場所（概算は今の catalog・`articleCommunity`）:

| 構成 | 30 万 PV | 140 万 PV | 450 万 PV（話題の月） | 12 か月の費用（概算） |
|---|---|---|---|---|
| Cloudflare Paid | $10.15 | $10.15 | $18.05 | 約 $130 |
| Vercel Pro + Supabase Pro | $45.00 | $45.00（CDN Requests 105%） | $341 | 約 $850 |
| さくらの VPS 2GB | $13.05 | $13.05 | $13.05 | 約 $160 + 手間 3 / 月 |

- 収益 $2,200 に対して Vercel Pro の費用は 4 割近くになり、所見 1 の「構成の差が勝敗に効く」は利幅の薄さで残る。話題の月の転送量（FDT）と Bot（SC-2・140 万 PV を × 2 にすると $45 → $159）が、Vercel の判断の時期になる。
- **VPS の勝ち筋**（今は届く戦略が無い。§9.7 の所見）:
  1. 成長の感度を下げる（上の表）。満足度の 1 段の差で規模が半分にならない。
  2. チームが増える（SC-3）と、維持の 3 ポイントの比率が 30% → 15% に下がる。席課金は Vercel にだけ乗る。
  3. 画像を多く載せる提案（P-2）は、Cloudflare（Images の変換）と Vercel（FDT・画像変換。140 万 PV で $45 → $100）で費用が増え、VPS は固定費のまま（概算は画像 10 枚 / ページ・種類 15,000）。代わりにディスク 100 GB と共有回線に近づく。
  4. 維持の手間 3 と機能の期待 8 / 月は変えない（変えると「安いが自分の時間が減る」が消える）。
- VPS の弱点も出来事で出す: SLA 非対応（SC-5・データ待ち）・ディスク 100 GB（S-3）・上位プランが未取得なのでプラン変更で逃げられない。
- 目標は「Cloudflare Paid・何もしない」が届き、「VPS で P-2 を受けて圧縮で回す」「Vercel で話題の前兆に圧縮」が工夫して届く間に置く（§10.8）。

### 10.7 見込みが外れた理由の振り返り

GD-1 の印 `earlierThanProjected`（`trends.ts:145-149`）は「前の月の見込みより早く超えた」だけを持つ。理由を、**その月の出来事を外して見積を引き直す**（反実仮想）ことで決める。

| 手順 | 内容 |
|---|---|
| 1 | 印が付いた前提 P と月 m について、m に効いていた出来事（予告・前兆は除く）を集める |
| 2 | 出来事ごとに、その効果を除いた Workload・構成で m の `estimate` を引き直し、P の使用率を求める（純粋関数・1 回の見積は軽い） |
| 3 | 除くと見込みの線（`projection`）以下に戻る出来事を理由にする。複数なら差の大きい順 |
| 4 | 出来事で説明できなければ、プレイヤーの行動（設定の変更・提案を受けた・乗り換え）で同じことをする。それでも無ければ「伸びが直近より速かった」 |

- 文の形: 「Bot のアクセス（PV × 2）で、Vercel Pro は CDN Requests 月 1,000 万まで込み（…）を、見込みより 2 か月早く超えた」。前提の文は catalog のもの（D-12）。
- 月の報告に `surprises: { premiseId; month; cause: { kind: 'event' | 'action' | 'growth'; id?: string; ratioWithout?: number } }[]` を足し、振り返りの ④（§9.6）に並べる。
- 見込みを出さない月（`skipProjection`・`trends.ts:96`）を、話題の月だけから「一時的な `traffic` の効果がある月」（SC-1・SC-2）に広げる。どちらもプレイヤーに見えている出来事なので、ゲームの内部を覗くことにはならない（§5）。
- 反実仮想は表示のためだけで、ゲームの状態に入れない（`trends.ts:3` と同じ扱い）。

### 11.2 構成の組み立て

今の完成品（`packages/catalog/src/stacks/index.ts:236-242` の 5 構成）を、**スロットの選択から組み立てる関数**に置き換え、完成品は「既定の選択」として残す。

```ts
// catalog（データ）。部品は「ノード + 経路の断片 + 課金先のメーター」を返す。振る舞いは estimator の ComponentKind のまま。
type SlotId = 'isrCache' | 'images' | 'db' | 'realtime';
type Choices = Partial<Record<SlotId, string>>;          // 例: { isrCache: 'kv', images: 'images', db: 'd1', realtime: 'none' }
type ComponentOption = {
  id: string; slot: SlotId; label: string;
  provider: string; accountId: string;                    // 部品が属する事業者（§11.6 のため。スタックの事業者に固定しない）
  inappropriate?: boolean;                                // 学びのための不適切な選択
  premiseRefs: string[];                                  // 当たりうる前提の id の前方一致（選ぶ前に出す）
  nodes: (plan: PlanTier) => ArchNodeInput[];
  routes: Partial<Record<RequestClass, string[]>>;        // スロットが受け持つクラスの経路の断片
  workload?: WorkloadPatch;                               // 「キャッシュしない」「事前に作ったサイズ違い」など、Workload の側を変える部品
};
function composeStack(platform: PlatformId, plan: PlanTier, choices: Choices): ArchitectureInput;
export const DEFAULT_CHOICES: Record<PlatformId, Required<Choices>>;
export const cloudflareVinext = (plan) => composeStack('cloudflare', plan, DEFAULT_CHOICES.cloudflare); // 今と同じ値を返す
```

- **完成品は既定の選択**: `composeStack(…, 既定)` が今の `cloudflareVinext`・`vercelSupabase`・`sakuraVps` と**深い比較で同じ** `ArchitectureInput` を返すことをテストで固定する（§11.7）。見積モードと `MVP_STACKS` の利用者はそのまま動く。
- 経路は「土台（静的アセット・Worker）+ スロットの断片」を順に重ねて作る。スロットが受け持つクラス（ISR のキャッシュ: `document-isr`・`isr-revalidate`、画像: `image-*`、DB: `document-ssr`・`api` の末尾、リアルタイム: `realtime-*`）は重ならないように決め、重なったら組み立てで落とす（estimator の構成の検証の純関数・prd/01 §4.2）。
- Workload を変える部品（キャッシュしない・事前に作ったサイズ違い）は、構成ではなく Workload の上書きとして返す。ゲーム側は `workloadFor` の後に当てる（`index.ts:371-403` の `mods` と同じ流れ）。
- **ゲームの状態**: `stackIndex`（`index.ts:243`）を `{ platform, plan, choices }` に分ける。今の `STACKS`（`index.ts:286-292`）の 5 つは「事業者 × プラン × 既定の選択」として残し、プラン変更（`isPlanChange`・`index.ts:451-454`）は事業者が同じかどうかで今のまま判定する。保存は選択の id だけを持つ。

**Vercel と VPS の共通の役割**（G-04: 共通の役割だけ）:

| 役割 | Vercel + Supabase | さくらの VPS |
|---|---|---|
| ISR のキャッシュ | ISR の永続ストレージ（既定）/ キャッシュしない | ディスク（既定。今はホストに含まれる）/ キャッシュしない |
| 画像 | 画像の最適化（既定）/ 最適化しない | ホストで変換（既定）/ 最適化しない |
| DB | Supabase（既定のみ） | MySQL の同居（既定のみ） |
| リアルタイム | **未取得**（メモ §8 R-8）。選べない（理由を出す） | **未取得**。選べない |

- 「キャッシュしない」「最適化しない」は 3 事業者で同じ意味を持つので、**事業者の違いがそのまま前提の違いとして出る**（Cloudflare は転送量 0 円で速さだけ・Vercel は Fast Data Transfer と関数の費用・VPS は CPU と共有回線）。D-12 の比べ方がいちばん素直に出る組み合わせ。
- DB の差し替えを Vercel・VPS で出さないのは、選択肢が別の事業者（Neon・RDS など）になり、§11.6 のプロバイダーをまたぐ構成そのものになるため。

### 11.4 不適切な選択の学び

前提の文は catalog に置き（D-12）、見積の「重要な前提」・出来事の通知・振り返りで同じ文を使う。下の「前提の文の案」は catalog に足す文（値はメモの出典つき）。

### 11.5 データ待ちだった出来事の解消

### 11.6 D-20 の将来の範囲（プロバイダーをまたぐ構成）との関係

- 今回は入れない。ただし**外部の Postgres（Hyperdrive 経由で Supabase）は、既に Cloudflare と Supabase をまたぐ構成**になる。§4 の表で Cloudflare の DB の選択肢として決まっているので、例外として「事業者の組を 1 つに固定（Cloudflare → Supabase）」で入れる案（→ X-6）。
- スロットの設計が将来を妨げないための決めごと:
  1. 部品は自分の `provider`・`accountId` を持つ（§11.2 の `ComponentOption`）。構成の事業者から導かない。複数のアカウント（無料枠の共有単位）は今の `accounts`（`schema.ts:97-105`）で表せる。
  2. スロットの名前と受け持つクラスは事業者に依存させない（`isrCache`・`images`・`db`・`realtime`）。「画像だけ Cloudflare」は、Vercel の土台に Cloudflare の `images` の部品を差すこととして表せる。
  3. 事業者間の転送量と往復の遅延は、prd/01 §4.2 の `ArchEdge.boundary`（`cross-provider`）で扱う設計がある。今の `ArchitectureSchema` は辺を持たず経路の列だけ（`schema.ts:1-2`・`:107-111`）なので、将来ここに境界を足す。今回の Hyperdrive では Supabase の egress（既存のメーター）だけを数え、遅延は「計算しない」と前提の文で明示する。
- ゲームの状態を `{ platform, plan, choices }` にしておけば（§11.2）、将来 `platform` を「土台の事業者」と読み替えて、別の事業者の部品を `choices` に入れられる。

| 4. ゲームの行動 | `component` の行動・DB の差し替えの進行・W-1・SC-5 を接続するコミットで golden を更新し、PR 本文に旧 → 新の表と差の理由を載せる |

足す性質のテスト（値に依存しない）:

| テスト | 内容 |
|---|---|
| 既定と同じ | 既定の選択の構成は今の完成品と同じ |
| 同じ部品への差し替え | 選べない（`actionEffort` が null。今の設定と同じ作法） |
| 不適切な部品 | 選ぶ前に `premiseRefs` の前提が出る。KV を DB 代わりにすると、鮮度が 1 段下がり、KV の書き込みの明細が増える |
| 画像を D1 に | 記事コミュニティの初期値で D1 の 10 GB に当たる |
| キャッシュしない | Cloudflare では Workers のリクエスト数が変わらず CPU が増える。Vercel では関数の実行が増える |
| 最適化しない | Cloudflare では費用が変わらない（R2 の転送量 0）。速さが下がる |
| 乗り換え | 乗り換え先は既定の部品で始まる |

基準プレイ（§10.8）: 今の 6 本は既定の選択のまま変えない（目標 $1,730 の根拠を動かさない）。**目盛りとして** 2 本を足す案: ⑦ CF Paid・KV を DB 代わり（届かない想定。不適切な選択の結果を軸ごとの成績に並べる）・⑧ CF Paid・チャットの提案を受ける（W-1）。SC-5 を入れると ③（VPS）の結果が変わりうるので、まれな出来事の重みを決めた後にシード 1〜50 で確かめ直す（「どのシードでも 1 本は合格」の性質を保つ）。
