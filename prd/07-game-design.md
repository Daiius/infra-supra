# 07. ゲームデザイン

> 状態: **設計は確定（2026-10-31・D-17）・実装は未着手**。試作（`packages/web` のゲームモード・`packages/game` の最初の形）は
> この設計より前のもので、§8 の順に置き換える。ゲームのバランスの値（ポイントの量・重み・確率）は**ゲーム上の仮定**で、
> シナリオのデータに置き、実在の値のように扱わない。

## 1. 出発点: 試作への指摘（2026-10-31）

| # | 指摘 | 原因の見立て |
|---|---|---|
| F-1 | 1 か月ずつの状況や判断が別々で、続いている感じがない。PV や無料枠の使用の推移を常に見たい。「もう少し」の強調は続けたい | 画面が毎月のスナップショットを出し直しているだけ。推移と見込みがない |
| F-2 | 決まった改善を全部やれば Cloudflare Paid のままでよかった。Cloudflare のどの部品を使うかも選べると、あえて不適切な選択をしたときの学びがありそう | 行動が一度きりで代償がない。構成が完成品からの選択で、部品の組み合わせを選べない |
| F-3 | 一般に「こっちに移行しないと」となるのはどんなときか | シナリオが流量（PV）の増加しか持たない。移行を迫る理由の多くは流量以外から来る |

## 2. ゲームの状態

| 状態 | 内容 |
|---|---|
| 所持金 | 収益 − インフラの費用（見積エンジン）− 行動の費用 |
| 規模 | PV・MAU。成長率は満足度と出来事で変わる |
| **満足度**（G-01） | 要素ごとに「良い・普通・悪い」の段階で持ち、シナリオごとの重みで合計する。成長率（口コミ）と解約に効く |
| **開発の手間**（G-02） | 月ごとのポイント。改善・乗り換え・出来事への対応・自前運用の維持が取り合い、**余りが機能開発**（満足度と成長）に回る |
| ためていく量 | DB の容量・画像の保存量など。月ごとに増え、前提の境目に近づく |

満足度の要素:

| 要素 | 何で決まるか |
|---|---|
| 可用性 | 停止（前提に当たった）・偶発的な障害 |
| 速さ | 遅延の前提・SSR の重さ・画像の重さ |
| 画質 | 画像の圧縮の度合い |
| 鮮度 | ISR の再検証の間隔 |

- 性能の精密な推定（p50/p95）は待たない。段階への写し方はシナリオのデータ（ゲーム上の仮定）。
- 自前運用（VPS）の手間はお金（試作の $30/月）ではなく**ポイント**で表す。「安いが自分の時間が減る」がそのまま出る。

## 3. 出来事（G-03）

3 種類を混ぜる。

| 種類 | 起き方 | 例 |
|---|---|---|
| 状態で起きる | ためていく量や規模が境目を越える | DB が 8 GB を超えた・同時接続が増えた |
| 提案として来る | 受けるかどうかをプレイヤーが選ぶ。受けると満足度と成長が上がるが、新しい要件が乗る。断れば機会を逃す（機能追加の延期・企画書 §5.4） | チャット（WebSocket）を足すか・動画のアップロードを足すか |
| シナリオの台本 | 事業の出来事。時期はシードで幅を持たせる | 法人顧客が SLA を求める・料金改定・チームが増える |

**効き方は 3 段階**（ユーザーの補足: 乗り換えを迫るのはまれな大きなイベントにする）:

| 頻度 | 対応 | 例 |
|---|---|---|
| ふだん | プランの変更・設定 | 込み分に近づく・急増 |
| ときどき | 部品の追加・差し替え | 機能の提案を受けて要件が増える |
| **まれ（低確率）** | 乗り換えの検討 | SLA の要求・買い足せない上限（D1 の 10 GB）・大きな料金改定 |

- 乱数（シード付き）は偶発的な障害と、話題になる時期・まれな出来事の発生だけに使う。運で詰まない範囲に保つ（spike game 所見 6）。

## 4. 部品を選べる構成（G-04）

完成品の構成を選ぶ代わりに、**役割ごとのスロット**に部品を選ぶ（グラフエディタ（Phase 5）の手前の形）。**Cloudflare を先に深く**し、Vercel と VPS は共通の役割だけ選べるようにする。

| 役割 | Cloudflare の選択肢 | 不適切な選択で当たる前提の例 |
|---|---|---|
| ISR のキャッシュ | KV / R2 / キャッシュしない（毎回 SSR） | KV: 同じキーへの書き込みは 1 秒 1 回まで・反映は最大 60 秒ほど遅れる |
| 画像 | Images（リクエスト時）/ 事前に作ったサイズ違いを R2 / 最適化しない | 最適化しない: 転送量と速さ |
| DB | D1 / KV を DB 代わりに（不適切）/ 外部の Postgres（Hyperdrive 経由） | D1: 1 データベース 10 GB（引き上げ不可）・1 行 2 MB。KV: 書き込みの頻度・整合性 |
| リアルタイム | Durable Objects / なし | チャットの提案を受けたときに要る |

- 部品の組み合わせは、エンジンのノードとクラスごとの経路の違いとして表す（catalog の構成を部品から組み立てる）。
- **追加で集めるデータ**: Durable Objects・Hyperdrive・Queues の料金と制限、Workers のメモリ上限（いずれも未取得）。

## 5. 推移と見込み（G-05・F-1）

- 推移のグラフ（PV・費用・収益・所持金・満足度）を常に出す。
- 前提の使用率の推移を貯め、**直近 2〜3 か月の伸び率で外挿**した「このペースだと N か月後に超える」を出す。流量は倍率、ためていく量は月あたりの増分で外挿する。
  プレイヤーが見ている推移だけで計算し、ゲームの内部（成長率・台本）は覗かない。
- 残りの期間内に超える見込みのときだけ出す。出来事で外れたら、振り返りに「見込みが外れた理由」を出す。
- 「もう少し」（境目の半分・70% を超えた前提）の強調は続ける。

## 6. 行動と代償

一度やれば終わりの改善にせず、代償を持たせて状況しだいで最適が変わるようにする。

| 行動 | 効果 | 代償 |
|---|---|---|
| 画像を圧縮する | 転送量が減る | 画質（満足度）。画像が売りのシナリオで重い |
| ISR の間隔を延ばす | 再生成が減る | 鮮度（満足度）。ニュース性の高いシナリオで重い |
| SSR を最適化する | CPU が減る | 開発の手間 |
| 部品を差し替える | 前提が変わる | 開発の手間（部品による） |
| プランを変える | 上限・込み分が変わる | ほぼ即時・手間なし（乗り換えと区別する。spike game 所見 5） |
| 乗り換える | 構成が変わる | 開発の手間（数か月）・移行の期間とリスク |

## 7. シナリオと評価（G-06・G-07）

- シナリオは**データで定義する**: テンプレート（Workload）・収益モデル・満足度の重み・開発の手間の量・出来事の台本・目標。
- まず**記事コミュニティ 1 本を深く**作り直して仕組みを固める。2 本目（画像投稿サービス。画像がたまり、画質の重みが大きい。企画書のシナリオ C）は、データの追加だけで足せるかの検証として後で入れる。
- 評価:
  - **合否**: 所持金が目標以上、かつ満足度の平均が目標以上。停止は満足度の可用性に吸収させ、別の条件にしない。
  - **軸ごとの成績**: 累積の利益・満足度・最終的な規模・機能開発に回せた手間を、1 つの点数にまとめずに並べる（唯一の正解を作らない。企画書 §11.3）。
  - **振り返り**: 当たった前提・近づいた前提と、そのときの選択を並べて締める。
