# 09. シナリオ: 受託先の業務アプリを運用する

> 状態: **確定（2026-11-01・D-33）・実装済み**。§6 の論点 C-01〜C-11 は、ユーザーがすべて推奨案のとおりに決めた（§8）。実装と確定した値は §9。
> ここに出てくる収益・規模・成長・手間・確率・倍率・満足度への効き方は、すべて**ゲーム上の仮定**で、実在の値でも相場でもない。
> 実在の料金・制限は catalog のデータ（Cloudflare・Vercel・Supabase・さくらの VPS）にあるものだけを使い、無いものは「未取得」と書く（AGENTS.md の 🔒）。
> 前提にしている設計は [07](./07-game-design.md)（§9 GD-2・§10 GD-3・§11 GD-4）と D-18〜D-30。07 は変えず、ここから参照する。

## 1. 目的と方針

### 1.1 出発点（ユーザーの要望・2026-11-01）

- 記事コミュニティは「コンテンツを作る会社」と「システムを開発する会社」が同じ形になっている。ユーザーの会社は Web アプリケーションの開発をしているので、**受託・準委任に近い雰囲気のシナリオ**もほしい。今のシナリオの感じは良いので、他のものもほしい。
- 1 版目の案は人件費・準委任の請求・複数案件を入れたが、ユーザーが方針を改めた:
  「インフラに主眼を置いた維持費の計算のつもりだった。開発費用を取り入れると話が複雑になりすぎる。**受託はシナリオのフレーバーとしてだけ扱い、運用費用に集中する。今の形をほぼ残す**」「人件費は入れない」。

### 1.2 方針

- **お金の流れは記事コミュニティと同じ形**: 収益 − インフラの費用（見積エンジン）− 一度きりの費用 = 所持金。手間ポイントは今のまま（余りは機能開発・満足度へ）。
- 違うのは **収益の中身**・**顧客のアプリのワークロード**・**出来事**だけ。受託らしさは、顧客から来る運用上の依頼（SLA・監査ログ・保管期間・繁忙期など）と、業務アプリの負荷の形で出す。
- **できるだけデータだけで足す**。prd/07 §8 の GD-5（2 本目のシナリオをデータの追加だけで足せるかの検証）を兼ねる（C-01）。

### 1.3 お金の流れ

> 記事コミュニティ: 読者 → PV → 広告の収益 → 所持金 ← インフラの費用。
> このシナリオ: 顧客（発注元の会社）→ **月額の運用・保守の費用（固定）+ 利用者数に応じた従量（小さな変動）** → 所持金 ← インフラの費用。
> 自社は顧客の業務アプリを作り終え、今は運用を受け持っている、という設定。インフラは自社のアカウントで持ち、費用は自社が払う（運用費に込み）。

| 項目 | 記事コミュニティ | このシナリオ |
|---|---|---|
| 収益の源 | PV × 広告の単価 | 固定の月額 + 利用者（MAU）× 従量の単価（どちらも仮定） |
| 規模の伸び | 満足度 → 口コミ → PV | 満足度 → 顧客の社内での利用の広がり（緩い）。出来事（他部署への展開）で段差 |
| 止まったとき | 広告の収益が減る（`loss.block`） | 同じ仕組みで「その月の運用費の減額」と読み替える（文面だけ） |
| 手間ポイント | 余りは機能開発 | 同じ（文面は「顧客への改善」） |
| 人件費 | 入れない（V-5） | 入れない（ユーザーの判断） |

### 1.4 入れないと決めたこと（1 版目からの撤回）

| 内容 | 入れない理由 |
|---|---|
| 人件費 | 維持費（インフラ）の計算が主眼。人件費を入れるとインフラの月額が誤差になる（1 版目の B-1・V-5 と同じ問題） |
| 準委任の請求（手間ポイント × 単価） | 開発費用の計算になり、主眼から外れる。手間ポイントはお金に換えない今の形を残す |
| 単価・精算幅 | 同上。出典のない相場を持ち込む必要もなくなる |
| 受託（一括）の検収・遅延 | 開発の工程の計算。運用の期間だけを扱う |
| 複数の案件・会社と案件の状態の分割 | エンジンの状態の形が変わる大きな拡張。1 顧客・1 構成で受託らしさは出せる |
| インフラの費用の負担の選択（実費精算・顧客名義） | お金の流れを変える。今回は「自社名義・運用費に込み」に固定する（C-04 で再確認） |
| 保守の終了・引き継ぎ | アカウントの移管の手順が未取得で、事業者の差を付けられない（データの欠けを罰にしない。D-24 X-5 と同じ考え方） |

## 2. ゲームの骨格の案

| 項目 | 案（推奨） | 備考 |
|---|---|---|
| 期間 | 12 か月 | 記事コミュニティと同じ |
| 顧客のアプリ | catalog の新しいテンプレート「業務の Web アプリ」（§4） | 見積モードとも共有する |
| 構成 | 今の 6 構成 + 部品（GD-4）をそのまま選ぶ | 構成の追加なし |
| 収益 | **固定の月額 F + 利用者 1 人あたり v**（どちらも仮定）。記事コミュニティの `adsUsdPer1000PV` と同じ位置 | 値は基準プレイで決める（§2.1） |
| 規模 | 利用者（MAU）は小さく始め、成長は緩い（例: 月 2〜4%・仮定）。他部署への展開の出来事で段差 | PV は小さく、1 人あたりの API・SSR が重い |
| 満足度 | 5 つの要素のまま。重みをデータで変える（可用性・速さを重く、画質・鮮度を小さく） | エンジンの変更なし（C-06） |
| 手間 | 月 10・VPS の維持 3（今のまま） | |
| 目標 | 所持金・満足度の平均・止まった月の 3 条件（今のまま。値は基準プレイで） | |
| 終わり方 | 今のまま（所持金が負・止まった月の上限・規約違反が 2 か月）。Vercel Hobby は「個人・非商用のみ」なので、顧客の業務アプリでは規約違反の流れ（D-19）に乗る | 今の仕組みで出る、受託らしい学び |

### 2.1 収益の桁（1 版目の B-1 の解消）

- 収益は「インフラの月額の差が合否に効く」桁に置く。目安は記事コミュニティと同じく、**12 か月の収益に対して、構成ごとの 12 か月のインフラ費の差が 1〜4 割**になる範囲（記事コミュニティは収益約 $2,200 に対して CF Paid 約 $130・Vercel Pro + Supabase Pro 約 $850・prd/07 §10.6 の概算）。
- 固定 F を大きくしすぎると構成の差が埋もれる。**固定を主にし、従量 v は小さく**して「利用が増えても収益はあまり増えないが、費用は増える」を出す（記事コミュニティとの違い。込み分を超えた従量課金がそのまま利幅を削る）。
- 値は業務アプリのテンプレートで構成ごとの月額を概算してから決める（記事コミュニティの GD-3 と同じ手順）。今は決めない（C-03）。
- 「運用費の相場」は書かない（出典なし）。画面にも「ゲーム上の仮定」と出す。

## 4. 顧客のアプリ（catalog のテンプレート）

catalog に `businessApp(monthlyPageViews)`（仮の名前）を足す。値はテンプレートの既定値（template-default・仮定）で、今の `WorkloadInput` の項目だけで書ける。

| 項目 | 記事コミュニティ | 業務の Web アプリ（案・仮定） | 当たりやすくなる前提 |
|---|---|---|---|
| ページの種類 | ISR 60%・SSR 40% | **ログインが要るので SSR が大半**（ISR はお知らせ程度か、なし） | Workers の CPU・Vercel の Active CPU・VPS の CPU |
| 1 人あたりの PV | 月 10 | 多い（毎日使う）。MAU は小さい | — |
| 平日と週末 | 1.3 | **大きい**（`weekdayToWeekend`） | ピークで決まる前提（接続・CPU・回線） |
| ピークの時間 | 2.5 | **大きい**（平日日中・始業直後。`peakHourFactor`） | 同上 |
| API | 1 / ページ・書き込み 0.1 | **多い**（一覧・検索・登録）・書き込みも多い | D1 の行の読み書き・Supabase の egress |
| 画像 | 5 枚 / ページ・150 KB | ほぼなし。代わりに**添付ファイル**を画像の在庫で表す（`images.storedGB`・`uploadsPerMau`） | R2・ディスクの保存量 |
| DB | 0.3 GB | 大きめに始まり、記録で増える | D1 5 GB / 10 GB・Supabase 8 GB |

- 見積対象を特定のスタックに寄せない（AGENTS.md・prd/06）: テンプレートはフレームワークを決めない。ゲームの構成は今の 3 事業者（Next.js 系・vinext）のままだが、文面で顧客のアプリの技術を決め打ちしない。
- 「添付ファイルを画像の在庫で表す」は、画像の変換（Images）が添付ファイルには効かないので、**変換の件数を 0 にする**（`perPage.images` を 0 にし、保存量だけ在庫で持つ）。表しきれなければ、ファイルの保存量の在庫を別に持つ拡張（§5 E-4）。

## 5. エンジンへの拡張（最小）と、データだけで済む部分

### 5.1 データだけで済む部分

- シナリオのデータ（`Scenario`）: 規模・成長・満足度の重み・目標・確率・時期・基準プレイ。
- 出来事: CS-1・CP-1（mods の項目があれば）・CP-2〜CP-5・CSC-2・CSC-3・CR-1・CR-2（`workload`・`stock`・`basePV`・`seats`・`interrupt`・`feature`・`contract`・`premise` の型で書ける）。
- catalog のテンプレート `businessApp`（Workload の仮定。料金ではない）。
- Vercel Hobby の規約違反・SLA の要件・席の料金は今の仕組みのまま。

### 5.2 エンジンへの拡張（最小）

| # | 拡張 | 中身 | 大きさ |
|---|---|---|---|
| E-1 | 収益の形 | `Scenario.revenue` に `fixedUsdPerMonth`（省略時 0）と、従量の単位（PV あたり / MAU あたり）を足す。止まった月などの減り（`loss`）は今の式を全体に掛ける | 小（記事コミュニティは省略時の値で golden 不変） |
| E-2 | 繁忙期の mods | `WorkloadMods` に `peakHourFactor`（と必要なら `weekdayToWeekend`）を足し、`traffic` の効果と同じく「その月だけ」効かせる | 小 |
| E-3 | 帳票の mods | `WorkloadMods` に API の CPU・応答の大きさを足す（今は `writesPerCall` だけ） | 小 |
| E-4 | 添付ファイルの在庫（必要なら） | `Stock` の画像を「ファイル」として使えない場合だけ、保存量の在庫を別に持つ | 小〜中（§4 の表し方で足りれば不要） |
| E-5 | シナリオの選択 | 画面が `ARTICLE_COMMUNITY` を固定で使っている（`packages/web/src/App.tsx:74`）。始める画面でシナリオを選び、文面（「広告の収益」→「運用費」など）をシナリオから読む | 中（web） |
| E-6 | シナリオで使わない設定の非表示 | 画像の圧縮・ISR の間隔は業務アプリでは効かない（ISR なし・画像なし）。シナリオのデータで行動を絞る | 小〜中（web と `checkAction`） |

- 各段で**記事コミュニティの golden（シード 42・3・31）が 1 セントも変わらない**ことを確かめる（prd/07 §10.8 の作法）。
- 「データだけで足せるか」の検証としての結果は、E-1〜E-3（型への小さな足し）と E-5・E-6（画面）が要る、という形で記録する。GD-5（画像投稿サービス）でも E-5 は同じく要る。

### 9.3 所見

- **B-1 は半分当たった**: 30 万〜100 万 PV の業務アプリは、有料プランではどの構成も込み分の内に収まる。繁忙期（ピーク × 2・利用 × 1.5）も有料プランの前提にはほとんど当たらない（VPS の CPU の使用率は数 %）。差を作っているのは流量でなく、**固定費**（Vercel Pro + Supabase Pro で月 $45。この規模では込み分の内）・**席**（担当者をメンバーに入れると Vercel Pro は $20 増える）・**D1 の 10 GB**（旧システムの記録の取り込みと監査ログを受けると近づく）・**VPS のディスクと維持の手間**・**SLA**（さくら 4GB だけ）だった。prd/07 §1 の F-3（移行を迫る理由は流量以外から来る）に沿う。繁忙期は Free の日次の上限の判断として残す。
- 依頼を全部受けると、D1 の 10 GB に近づいて乗り換えになり、半分以上のシードで届かない（D-64 の時点で 34 / 50）。「受託の依頼を受けるかどうかが、構成の上限の判断になる」を学びとして残す（値を寄せない）。
- VPS は何もしないと届かず、手入れ（最適化・ディスクの増設）で届く。記事コミュニティの VPS と同じ「安いが手間がかかる」が出た。
