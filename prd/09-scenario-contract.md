# 09. シナリオ: 受託・準委任の開発会社（設計の案）

> 状態: **案（2026-11-01）。ユーザーの判断はまだ経ていない。** §6 の論点 C-01〜を一問ずつ詰めてから、決定を `_grilling/decisions.md` に記録する（番号は後で振る）。
> ここに出てくる単価・人件費・保守料・手間・確率・倍率・満足度への効き方は、すべて**ゲーム上の仮定**で、実在の値でも相場でもない。
> 人件費・単価の相場には出典がないので、値は書かず記号（`p` など）か比で表す。
> 実在の料金・制限は catalog のデータ（Cloudflare・Vercel・Supabase・さくらの VPS）にあるものだけを使い、無いものは「未取得」と書く（AGENTS.md の 🔒）。
> 前提にしている設計は [07](./07-game-design.md)（§9 GD-2・§10 GD-3・§11 GD-4）と、D-18〜D-30。07 は変えず、ここから参照する。

## 1. 目的と、記事コミュニティとの違い

### 1.1 出発点（ユーザーの要望・2026-11-01）

- 記事コミュニティは「コンテンツを作る会社」と「システムを開発する会社」が同じ形になっている。ユーザーの会社は Web アプリケーションの開発をしているので、**準委任・受託に近い雰囲気のシナリオ**がほしい。
- 「チームで稼働するエンジニアの分だけ、作業の分だけ、ポイントだけでなく**収益も減らせるか**。両方減らすのは変ではないはず。少し難易度が上がるかもしれない」。
- 記事コミュニティでは人件費を所持金に入れていない（D-20 V-5）。広告の収益が月 $75〜$300 の規模で、人件費を入れると構成の差が誤差になるため。**人件費を扱うのは、収益が人の時間から来るこのシナリオが筋**になる。

### 1.2 お金の流れ

**記事コミュニティ（今）**:

> 読者 → PV → 広告の収益 → 所持金。所持金からインフラの費用（見積エンジン）と一度きりの費用（さくらのオプション）を払う。
> 開発の時間（手間ポイント）はお金に換えない。余りは機能開発になり、満足度 → PV の成長 → 広告の収益、と回り道で効く。

**受託・準委任の開発会社（案）**:

> 顧客 → 契約 → 請求 → 所持金。請求の中身は次の 3 種類（どれを主にするかは §2.3 と C-02）。
> - **準委任**: エンジニアが顧客の作業をした時間（手間ポイント）× 単価。**時間がそのままお金になる**。
> - **保守契約**: 顧客のサービスを運用・保守する月額の保守料。中の作業時間とは無関係に定額。
> - **受託（一括）**: 決まった機能を作り、納品・検収した月に一度に入る。
>
> 所持金からは **人件費**（人数 × 月額・仮定）と、**自社が払うインフラの費用**を払う。
> インフラの費用を誰が払うかは契約で変わる（§4.2）: 保守料に込み（自社の負担）/ 実費精算（顧客に付け替えて請求）/ 顧客名義のアカウント（自社の帳簿に乗らない）。
> 顧客のサービスの PV は自社の収益に**直接はならない**。PV はインフラの費用・前提（止まる・遅くなる）を通じて、顧客の満足 → 契約の更新・追加の案件に効く。

**違いの要点**:

| 項目 | 記事コミュニティ | 受託・準委任 |
|---|---|---|
| 収益の源 | PV（広告） | 人の時間（準委任）・定額（保守）・成果物（受託） |
| 手間ポイントの余り | 機能開発（満足度 → 成長 → 収益の回り道） | **請求できる時間**（準委任なら直接お金）。運用や障害の対応に取られると、ポイントと収益が両方減る |
| 人件費 | 入れない（V-5） | 入れる（固定費）。所持金が尽きるのが現実的な終わり方になる |
| インフラの費用 | 全部自社 | 契約しだい（込み / 実費精算 / 顧客名義）。**誰の帳簿に乗るか**が判断になる |
| 構成 | 自社のサービス 1 つ | 顧客（案件）ごと。環境を分けるか・同じアカウントに相乗りさせるか |
| 満足度 | 読者の満足 → PV の成長 | 顧客の満足 → 契約の更新・追加の案件（顧客のサービスの PV の成長にも効く） |
| D-12 の判断ポイント | 込み分・上限・自前運用の手間 | 上に加えて、アカウントの持ち主・請求の付け替え・無料枠の共有単位・SLA の裏付け・引き継ぎ・保守の終了 |

### 1.3 このシナリオで学べること（D-12 の軸）

実在の料金データ（catalog）の事実がそのまま判断の材料になるもの:

| 判断 | 効く事実（catalog にある） |
|---|---|
| Vercel Hobby で顧客の案件を動かしてよいか | 「Vercel Hobby は個人・非商用のみ」（`vercel.ts` の eligibility `non-commercial`）。受託の案件は商用なので、規約違反の流れ（D-19）に乗る |
| 顧客のアカウントにエンジニアを入れる費用 | 「Vercel Pro は基本料 $20 が席（メンバー）ごとにかかる」（`vercel.ts` の `members: per-seat`）。Supabase はメンバー無制限（`members: included`）。Cloudflare・さくらは**記載なし**（`not-stated`） |
| 複数の顧客を 1 つのアカウントに相乗りさせるか | 込み分と基本料は**アカウント × 事業者 × プラン**で 1 つ（estimator の `accountId\|provider\|planId` の単位。`packages/estimator/src/pricing/price.ts:132`）。Cloudflare Workers Paid の基本料・込み分は相乗りで共有できる。さくらの VPS は基本料が**ノード単位**（`scope: 'node'`）で、相乗りは 1 台に同居させることになる |
| 顧客に稼働率の SLA を約束できるか | セルフサービスのプランで SLA があるのは**さくらの VPS 4GB（99.95%）だけ**（`uptimeSla: offered`）。Cloudflare・Vercel は記載なし（Enterprise）、Supabase はなし（Enterprise 99.9%）（`uptimeSla`）。裏付けのない SLA を約束するかが判断になる |
| 自前運用の手間は誰の時間か | VPS の維持の手間（今は 3 / 月・仮定）は、保守料の中の作業なら**請求できない時間**になり、準委任に出せる時間を削る。月額の差（例: CF Paid $10.15 と VPS 2GB $13.05・prd/07 §10.6 の概算）より、失う請求の方が大きくなりうる |
| 検証環境を無料プランで持つか | Supabase Free は「1 週間使われないとプロジェクトが一時停止する」「有効な無料プロジェクトは 2 つまで」（`supabase.ts` の notes）。**notes は計算に使わない**（D-14）ので、使うなら構造化した事実に移す（§5・C-10） |
| 短い案件に VPS を使うか | さくらの VPS は「最低利用期間 3 か月」（`sakura-vps.ts` の notes。D-14 で計算に使わない） |
| 保守の終了・他社への引き継ぎ | アカウント・プロジェクトの移管の手順と制約は**未取得**（§7 B-3） |

## 2. ゲームの骨格の案

### 2.1 期間と規模

| 項目 | 案（推奨） | 考え方 |
|---|---|---|
| 期間 | **12 か月**（記事コミュニティと同じ） | 画面・推移・評価の作りをそのまま使う。保守契約の更新（§3）を 6 か月目と 12 か月目に置ける |
| 会社 | エンジニア **2 人**（手間 20 / 月）で始める | 1 人だと「保守に取られて準委任が 0」になりやすく、判断の幅が出ない（仮定） |
| 顧客 | 保守する顧客 **A**（自社が作った Web アプリ）と、準委任の顧客 **B** の 2 社 | A でインフラの判断、B で時間の売り先。2 社目の保守案件は出来事で来る（C-07） |
| 顧客 A のサービス | 新しいテンプレート「業務の Web アプリ」（§4.4・C-16）。規模は記事コミュニティより小さく、PV より API と DB が重い | 受託でよくある形に寄せ、ISR 中心の記事コミュニティと前提の当たり方を変える |

### 2.2 開始状態

| 項目 | 案 |
|---|---|
| 所持金 | 人件費の 2〜3 か月分（仮定）。人件費があるので、所持金が尽きるのが現実的な負け方になる |
| 顧客 A の構成 | 始めるときに選ぶ（今の 6 構成 + 部品）。あわせて**インフラの費用の負担**（込み / 実費精算 / 顧客名義）と**アカウントの持ち主**を選ぶ（§4.2） |
| 顧客 B の準委任 | 月の上限 `B_cap` ポイント（仮定）。単価 `p` / ポイント |
| 保守料 | 顧客 A から月 `m`（仮定）。込みを選ぶと `m` を高く、実費精算・顧客名義を選ぶと低くする（差は仮定。C-09） |

### 2.3 収益の形（どれを主にするか）

| 案 | 中身 | インフラの判断との関係 | エンジンの変更 |
|---|---|---|---|
| **A. 保守 + 準委任（推奨）** | 顧客 A の保守料（定額）+ 顧客 B の準委任（余りのポイント × 単価、上限つき） | A の構成の手間が B の請求を削る。A の込み分の超過は保守料の利幅を削る。**ユーザーの「ポイントと収益の両方が減る」がそのまま出る** | 中（人件費・請求できる余り・負担の 3 択） |
| B. 準委任だけ | 余りのポイント × 単価だけ | 自社が運用するものが無いと、インフラの判断が出てこない。自社のサービスを別に持つ形にすると記事コミュニティに戻る | 小 |
| C. 受託（一括）→ 保守 | 1〜4 か月目に A を作って納品（検収の月に一括の収益）、以降は保守 | 納品のときに構成とアカウントの持ち主が決まる。手戻り（仕様変更）で一括の利幅が減る。最も受託らしいが、作る期間はインフラの判断が少ない | 大（成果物の進捗・検収・遅延） |
| D. 全部 | A に加え、追加の案件を受託（一括）で受ける | 最も豊か | 大 |

- 推奨は **A を土台にし、受託（一括）は「追加の案件」の出来事として後から足す**（段 2。§5）。12 か月のうち多くを「作っている期間」にすると、D-12 の判断（運用・費用・前提）が出る月が減るため。

### 2.4 人件費

| 項目 | 案 |
|---|---|
| 形 | **1 人あたり月額 `w` の固定費**（仮定）。人数 × `w` を毎月所持金から引く |
| 値の決め方 | 相場は書かない（出典なし）。`w` は `p` との比で決める: 例として「1 人が稼働率 r（請求できたポイント / 10）で損益分岐」になるように `w = 10 × r × p`（r は仮定。C-04） |
| 人数の変化 | 出来事（採用・退職）で増減。手間の総量（10 / 人）と人件費が一緒に変わる。今の `effortPerMonth`・`seats` の効果を流用する |

### 2.5 手間ポイントと請求の関係（このシナリオの中心）

月のポイント（人数 × 10）の配分の順は今のまま（prd/07 §9.4）で、**余りの行き先**だけが変わる。

| 順 | 使い道 | 請求できるか（案） | 今の仕組み |
|---|---|---|---|
| 1 | 自前運用の維持（VPS の構成の案件ごと） | **できない**（保守料の中の作業） | `selfHostedUpkeep` |
| 2 | 割り込み（障害・顧客の依頼への対応） | 出来事で決める。障害の対応・保守の範囲の依頼は**できない**、追加の改修として見積もったものは**できる**（`billable` の印。§5） | `interrupt` |
| 3 | 進行中の乗り換え・DB の差し替え | **できない**（自社の判断の作業）。顧客の依頼による乗り換えなら別（C-05） | `migration`・`componentSwap` |
| 4 | その月に選んだ行動（最適化・部品の差し替え） | **できない** | `plannedEffort` |
| 5 | **余り → 顧客 B の準委任**（上限 `B_cap` まで） | **できる**: 請求 = 稼働 × `p` | 新しい（記事コミュニティでは機能開発） |
| 6 | 上限を超えた余り → 顧客 A のサービスの改善 | できない（保守料の中）。顧客 A の満足（機能）に効く | 今の機能開発と同じ |

- **ユーザーの問いへの答え**: 1〜4 にポイントを取られた月は、5 の請求が同じだけ減る。ポイントの減りと収益の減りが 1 本の式でつながる（`請求 = min(余り, B_cap) × p`）。両方減るのは変ではなく、受託で「運用に時間を取られて売上が立たない」のそのものになる。
- 難易度: 記事コミュニティでは VPS の維持 3 ポイントは「機能が普通に下がる」だけだった。ここでは**毎月 3p の請求を失う**。CF Paid と VPS 2GB の月額の差（約 $3）と比べると、p が $1 を超えれば手間の方が重い。VPS の勝ち筋は SLA（4GB）と固定費（流量が増えても費用が変わらない）に移る。
- 準委任の契約の上限・下限（精算幅）を入れるかは C-06。入れる場合は「下限を割ると控除」で、運用に取られたときの罰が強くなる。

### 2.6 目標（合否）と評価軸

| 項目 | 案（推奨） |
|---|---|
| 合否 | 12 か月後に **所持金 ≥ 目標**（人件費を引いた後）かつ **顧客 A の満足度の 12 か月平均 ≥ 目標** かつ **止まった月が上限以内**（記事コミュニティと同じ 3 条件。値は基準プレイで決める） |
| 途中の終わり（D-19 と同じ） | 所持金が負・止まった月が上限を超えた・規約違反が 2 か月続いた（Vercel Hobby で顧客の案件を動かすと最初の月に指摘が来る） |
| 加える終わり方（案） | 顧客 A に保守契約を更新されなかった（更新の月に満足度が境目未満）。終わりにするか、保守料が止まるだけにするか（C-17） |
| 軸ごとの成績 | 今の軸（累積の利益・満足度・最終の規模・機能開発）に **稼働率**（請求できたポイント / 総ポイント）と **保守契約の粗利**（保守料 + 実費精算の請求 − 自社が払ったインフラの費用 − 請求できなかった保守の手間 × p）を足す。1 つの点数にしない（企画書 §11.3） |
| 振り返り | 今の振り返り（当たった前提・手間の内訳）に「請求できなかった時間の内訳（維持・障害・乗り換え・行動）」と「インフラの費用を誰が払ったか」を足す |

| CR-3 | P | 顧客 A が内製化する・他社へ移る（保守の終了） | 引き継ぎの作業（手間）と、その後の保守料の停止。**アカウントの持ち主で手間が変わる**（顧客名義なら軽い、自社名義なら移管が要る） | 未 | 移管の手順と制約が未取得（§7 B-3）。取るまでは効き方を仮定にし、事業者の差を付けない |

- **入れない候補**: 顧客の倒産・未払い（D-12 の軸に関係しない。所持金の運だけになる）。準委任の偽装請負・指揮命令などの法的な扱い（ゲームの範囲外）。
- 序盤の保証（D-20 V-12）: 1〜2 か月目は台本・提案を出さない。
- 「まれ」の候補のうち CR-3 はデータ待ち。CR-1・CR-2・CR-4 は今の catalog で作れる。

## 4. 構成の選び方

### 4.1 案件ごとか、会社で 1 つか

| 案 | 中身 | 評価 |
|---|---|---|
| 会社で 1 つ（全顧客を 1 つの構成に） | マルチテナントの自社製品に近い | 受託らしくない。顧客ごとの判断（負担・持ち主・SLA）が出ない |
| **案件ごと（推奨）** | 顧客ごとに `{ platform, plan, choices }`（GD-4 の状態）を持つ | 受託の実態に合う。ただしゲームの状態の分割が要る（§5 の E-5・大） |
| 段 1 は 1 案件だけ | 顧客 A の構成だけを持ち、今のエンジンの「構成 1 つ」のまま | 小さく始められる。CP-4（2 社目）は段 2 |

推奨は「案件ごと」を目標にし、**段 1 は顧客 A の 1 案件だけ**（C-08・C-20）。

### 4.2 インフラの費用の負担とアカウントの持ち主

| 選択 | 自社の所持金への効き方 | 当たる事実（catalog） | 手間（仮定） |
|---|---|---|---|
| 自社名義・**保守料に込み** | インフラの費用を自社が払う。保守料は高め | 込み分の超過・料金改定が自社の利幅に直接効く | なし |
| 自社名義・**実費精算** | 費用を払い、同じ額を顧客に請求（手数料は仮定）。差し引きほぼ 0 | 費用の増加は顧客の満足に効く（請求額が増えた。仮定） | 毎月の付け替えの手間（小・仮定） |
| **顧客名義** | 帳簿に乗らない | 席の料金（Vercel Pro $20 / 席）は顧客に乗る。顧客の満足に効く（仮定） | 権限の調整の手間（一度）。引き継ぎは軽い |

- **相乗り**（顧客 A と C を同じ自社のアカウントに）: 込み分と基本料を共有できる（Cloudflare Workers Paid の $5 と込み分を 1 つで済ませる）。代わりに、ある顧客の流量が他の顧客の込み分を食う・引き継ぎで切り離せない（移管の手順は未取得）・SLA の要件が全体にかかる。estimator はアカウントの id で込み分を分けるので、**2 つの構成のノードを 1 つの `ArchitectureInput` に合わせ、同じ `accountId` を付ける**だけで表せる（§5 の E-6）。
- Vercel Hobby は「個人・非商用のみ」（eligibility）。顧客の案件で Hobby を選ぶと、名義によらず規約違反の流れ（D-19）に乗る。**今の仕組みのまま出せる**、受託らしい学び。
- 今の catalog（Cloudflare・Vercel + Supabase・さくらの VPS 2GB / 4GB）と部品（GD-4）で、構成そのものは追加なしで表せる。足りないのは「誰が払うか」「どのアカウントか」を状態に持つことだけ。

### 4.3 環境（本番・検証）

- 案件ごとに本番と検証の 2 環境を持つかは C-10。持つなら、検証環境の費用・無料枠の数（Supabase Free の「有効な無料プロジェクトは 2 つまで」・「1 週間使われないと一時停止」）が判断になる。ただし今は notes（D-14 で計算に使わない）なので、使うなら構造化した事実（`facts`）に移す（catalog の変更・出典は既存）。
- 推奨は**段 1 では本番だけ**。

### 4.4 顧客のアプリ（テンプレート）

- 今の catalog のテンプレートは `articleCommunity` だけ。受託の顧客 A に記事コミュニティを流用すると、ISR と画像が中心になり受託らしくない。
- 案: catalog に「業務の Web アプリ」（ログインが要る・SSR と API が中心・PV は小さく DB の書き込みが多い・画像は少ない）を足す。値は Workload の仮定（料金ではない）で、見積モードとも共有する（C-16）。
- 見積対象を特定のスタックに寄せない（AGENTS.md・prd/06）: ゲームの構成は今の MVP の 3 事業者（Next.js 系・vinext）のままだが、顧客のアプリのフレームワークを決め打ちする文面にしない。案件ごとにフレームワークを変える（Vite の SPA + API など）のは将来の範囲（prd/06 の DeployTarget が揃ってから）。
