# 05. テスト設計（料金計算を中心に）

> 状態: **設計中**。テストはすべて vitest（estimator・catalog・game は node 環境・DOM なし。web の画面の描画テストだけ jsdom。§7）。

## 1. 架空の料金データ（fictional）

- テストに使う料金は **`fictional-` で始まる provider** だけ。置き場は 2 つ（D-78。実装済み）。
  - `packages/catalog/src/fictional/`（`catalog/fictional` で読む。本体の index からは export せず、本番の `loadPriceBooks` に入らない）。
    料金計算の仕組みを一通り使う 3 つ: `fictional-edge`（USD・税抜。月・日・ノード単位の無料枠・1 回ごとと期間の切り上げ・tiered・料金未取得・席・all-usage のクレジット（bill））、
    `fictional-yen-host`（JPY・税込。使い切ると止まるクレジット（block）・定額で超えると adjust・ノード単位の基本料・一度だけの手数料）、
    `fictional-db`（USD。時間課金の月額上限・volume・丸めの記載なし）。出典は `example.invalid`（実在しない予約名）で、備考に「架空」と書く。
  - estimator の単体テストは依存の向き（[02](./02-architecture.md) §1。estimator は catalog を読まない）のため、
    `packages/estimator/src/pricing/fixtures.test-helpers.ts`（例の P-01〜P-14）と生成器 `random.test-helpers.ts`（§2b の性質）の架空データを使う。
  - golden は今はゲームの基準プレイの側（`packages/game` のテスト）にある（§5 は未着手）。
  数値は手計算しやすい**わざと丸い値**（単価 1・10・100、無料枠 1,000 など）にし、実在の料金と取り違えないようにする。
- 実在の PriceBook を使うテストは「スキーマを通る」「既知の構成で計算が完走する」までにとどめ、
  **金額をテストの期待値に書かない**（料金改定のたびにテストが壊れる・実在の値を二重管理することになるため）。

## 2. 料金計算の単体テスト（priceUsage）

| # | 観点 | ケース |
|---|---|---|
| P-01 | 定額単価 | 数量 × 単価 / per。per が 100 万単位のとき端数を比例で扱う |
| P-02 | 期間で切り上げ | 合計を単位で切り上げる（`scope: period`）。ちょうど境界・境界 + 1 |
| P-03 | 1 回ごとの切り上げ | 平均 2.3 ms × 1,000 件、単位 1 ms → 3 ms × 1,000（`scope: event`） |
| P-04 | 無料枠 | 使用量 < 枠・= 枠・> 枠。枠を超えた分だけ課金される |
| P-05 | 共有プール | 2 ノードが同じプールを使う。合算してから引く（ノードごとに引くより高くなる）。按分の表示が使用量に比例する |
| P-06 | 日次プール | 平日・休日で使用量が違う。月合計では枠内でも、平日 1 日が枠を超える → 平日の超過 × 平日数 |
| P-07 | tiered | 段をまたぐ数量。各段の単価で別々に計算される |
| P-08 | volume | 同じ数量で、到達した段の単価が全量にかかる。P-07 と金額が違うことを確かめる |
| P-09 | クレジット | クレジット < 対象の金額・= ・>。余りは繰り越さず、対象外のメーターには当たらない |
| P-10 | 固定費 | アカウント単位（ノードが 3 つでも 1 回）とノード単位（3 回）。席課金 |
| P-11 | 時間課金の上限 | 730 時間 × 時間単価 が月額上限を超えると上限で止まる |
| P-12 | 超過時の挙動 | `block` / `throttle` は金額 0 で `LimitBreach` を出す。`upgrade-required` は見積を不成立にする |
| P-13 | 通貨 | 原通貨が混在する Bill。明細は原通貨のまま、合計だけ換算される |
| P-14 | 明細の根拠 | すべての LineItem が priceRef と（usage なら）quantity・allowanceApplied を持ち、合計と一致する |

## 2b. 料金計算の性質（性質ベースのテスト）

`packages/estimator/src/pricing/properties.test.ts`。生成器 `random.test-helpers.ts` で架空の PriceBook（`fictional-gen`）と使用量を
決まったシード（1〜300）で作り、どの入力でも成り立つことを確かめる。失敗はシードの番号つきで出る。
**fast-check は入れていない**: 縮小（失敗した入力を小さくすること）は無いが、シードで再現でき、依存を増やさずに済む。縮小が要るほど複雑な性質が増えたら入れる。

| # | 性質 | 生成する範囲 |
|---|---|---|
| PP-01 | flat・tiered だけなら、使用量を増やしても合計は減らない | 月・日・ノードのプール、1 回ごと・期間の丸め、最小の課金量、block・throttle・adjust、bill・block のクレジット、基本料 |
| PP-02 | volume は単調でない例がある（PP-01 を flat・tiered に限る理由。§3） | 例 1 つ |
| PP-03 | 月のプールの内なら従量の金額・課金対象は 0 で、breach も無い | 丸め（期間）・段・volume を含む |
| PP-04 | 日のプール: 超えた量 × 平日・休日の日数だけ課金され、両方が枠内なら 0 | 平日・休日の 1 日の量 |
| PP-05 | プールをちょうど使い切る量を小数で分けても、足し算の誤差で超過・使い切りにしない | 0.1・0.2・1.1 などの和（D-78 で直した不具合）。逆に、大きな整数の枠（250 億）を 1 だけ超えたら 1 の超過として課金・breach する（許容誤差で消さない） |
| PP-06 | tiered は境目で連続（前後の差は δ × 最大単価 / per 以内）。段の量の和は使用量、段の金額の和は明細の金額 | 1〜4 段 |
| PP-07 | volume は境目で仕様どおり不連続（ちょうどはその段、超えると次の段の単価が全量） | 1〜4 段 |
| PP-08 | クレジットは従量を超えて引かない（従量 + クレジット ≥ 0、合計 ≥ 基本料） | 重なる複数のクレジット・bill と block |
| PP-09 | bill のクレジットは min(上限, 対象) だけ引き、使い切りの breach を出さない | |
| PP-10 | block のクレジットは従量を打ち消し、上限を超えたときだけ超えた額で `credit-exhausted` | |
| PP-11 | `ceilUnits` は値を覆う最小の単位の個数 | 単位 0.001〜1,000、単位の整数倍ちょうどを含む |
| PP-12 | 期間・1 回ごとの切り上げ: 課金対象（1 件あたり）は単位の整数倍で、切り上げ前から 1 単位未満だけ増える | |
| PP-13 | JPY ↔ USD: 換算は足し算と入れ替えられ、往復で戻り、為替を逆向きに書いても同じ。円建ての Bill の合計の換算 = 明細ごとの換算の和 | |
| PP-14 | 料金未取得の使用量を足しても合計は変わらず、`unpricedLines` が 1 増える | |
| PP-15 | アカウントは互いに独立（まとめて計算した合計 = 別々の合計の和） | |
| PP-16 | 最小の課金量（D-85）: 0 より多く最小以下なら最小の量と同じ請求・0 なら 0・最小を超えると最小の請求以上。ノードごとに当たる。PP-01 の単調性にも最小の課金量を含める | 最小 0.5〜10 万、プール・丸め・段・volume |

比較の許容誤差は相対 1e-9。大きな従量とクレジットが打ち消し合うと合計が小さくても誤差は明細の大きさに比例するので、明細の絶対値の和を尺度にする。

## 3. 資源シミュレーションのテスト（simulateResources）

- **保存則**: CDN の hits + misses = 入力（各クラス）。全 edge の転送量の合計 = 各ノードの送信量の合計。
- **二重計上なし**: 04 §4 の性質を、構成をランダムに組んで確かめる（fast-check）。
- **単調性**: 構成とプランを固定したまま MAU を増やすと、各 Usage は減らない。
  ⚠ **金額の単調性は性質にしない。** volume 料金では、段を上がると全量の単価が下がるため、
  使用量が増えて総額が下がることがありうる（例: 999 単位 × 1.0 = 999 に対し、1,000 単位 × 0.9 = 900）。
  金額で確かめるのは「tiered と flat だけの PriceBook なら単調」という限定した性質にする。
- **ゼロ**: MAU = 0 なら従量の Usage はすべて 0（固定費とストレージの初期容量だけが残る）。
- **線形性**: 時間分布を固定すれば、月間の件数系 Usage は MAU に比例する。

## 5b. フレームワーク

- 同じ Workload で、BuildOutput が静的だけのフレームワーク（架空）は、どの静的ホストでも関数の Usage が 0。
- ISR の再生成件数は PV を 10 倍にしても上限（期間 / 間隔）で頭打ちになる。
- ミドルウェアを `all` にすると、静的クラスの件数ぶん関数の実行が増える。
- `unsupported` の DeployTarget を含む構成は検証で弾かれる。

## 7. 画面の描画テスト（web・D-86）

画面を描いて操作し、**画面の壊れ**（例外・描けない・選択肢が出ない）を見つける。値（金額・満足度）は確かめない（game・estimator のテストが持つ）。
見た目（CSS・レイアウト・狭い幅）は見ない（jsdom はレイアウトを計算しない）。

- 道具: vitest + **jsdom** + `@testing-library/react`（と peer の `@testing-library/dom`）。依存を足した理由: 画面の確認が開発サーバーでの手作業だけで、
  描画の例外や選択肢の出し忘れを機械で拾えなかった。jsdom は happy-dom より標準に忠実で、Testing Library の標準の組み合わせ。
  `user-event`・`jest-dom` は入れない（`fireEvent` と素の `expect` で足りる）。
- 設定: テストのファイルの先頭の `// @vitest-environment jsdom` で、描画テストだけ jsdom にする（`model.test.ts` は node のまま。vitest の設定ファイルは足さない）。
  jsdom に無い API は [`smoke.test-helpers.tsx`](../packages/web/src/smoke.test-helpers.tsx) で最小限に補う:
  matchMedia（常に「動きを減らす」にして花火の canvas・数え上げを止める）・dialog の `showModal` と `<form method="dialog">` の送信・ResizeObserver と要素の大きさ（幅 640。グラフは幅 0 だと描かない）・scrollTo。
- 決定論: 乱数のシード 42・始めた日 2026-11-02 を画面の入力で与える（既定の「今日」に頼らない）。保存（localStorage）と URL はテストごとに消す。
- 失敗にするもの: 描画・操作の例外（`render`・`fireEvent` が投げる）、React の `console.error`（key の重複・描画の例外の報告）、期待した見出し・選択肢・表・グラフ（`role="img"`）が無いこと。
- 出来事のダイアログは自動で開いたら、中身が描けていることを見て「閉じて今月の行動へ」で閉じる（利用者と同じ操作）。
