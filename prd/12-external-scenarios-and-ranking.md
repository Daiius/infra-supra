## 0. ユーザーの問いへの答え（要約）

> 問い（2026-11-01）: 会社で扱われている事例を元にしたシナリオを作りたいが、public リポジトリには入れづらい。整理されたフォーマットでシナリオを定義して、外部から読み込ませる方法はないか。
> 将来ランキングを出すなら、クライアントで計算すると改竄が容易なので、選択肢をサーバーに送って結果を返す形にしたい気もする。
> そうすると、会社専用のサーバーにシナリオを置けば外部読み込みもやりやすい？ ポイントを外している気もする。

問いには、互いに独立した 2 つの問題が混ざっている。

1. **外部から読み込む = シナリオを「データ」にする問題。** 計算をどこでするかとは関係がなく、どちらの道でも先に要る。
   今の `Scenario` は関数を含む TypeScript のオブジェクトで（§1）、JSON にできない。宣言的な形（JSON + zod のスキーマ）にし、出来事の条件・効き方を決まった語彙だけで書けるようにする。
   今の 2 本（記事コミュニティ・受託）をその形で書き切れるかが試金石になる。
2. **置き場はサーバーが無くても選べる。** ブラウザでファイルを読み込めば、データは公開のリポジトリにもサーバーにも出ない（社内のドライブで配る）。
   社内向けのデプロイなら、環境変数でシナリオの URL を渡し、URL はアクセス制限の内側に置く。料金データは公開の情報なので共有のままで、会社に固有なのはシナリオの文面と数値だけ。
3. **ランキングの改竄対策 = 計算をどこで信用するか。** ゲームはシード付きの決定的な計算で、保存は行動の履歴（D-26）。
   「シード + 行動の列」を送り、サーバーが同じエンジン（純粋関数）で再生して点数を確かめれば、数値の改竄は通らない（**再生による検証**）。
   月ごとにサーバーと往復する形が要るのは「先の出来事を知られたくない（シードの先読み）」ときだけ。全員が同じシードで遊ぶ「今週のお題」なら、再生で足りる。往復は遅延・オフライン不可・サーバーの状態と費用が増える。
4. **おすすめの順**: シナリオのスキーマ化とファイルの読み込み → 再生による検証のランキング（シードはサーバーが発行）→ 必要なら月ごとの往復（§8）。

「会社専用のサーバーにシナリオを置く」は、ランキングを社内で持つときに自然に出てくる形（§6.5）。ただし外部読み込みのためにサーバーは要らない。

### 1.2 置き換えられないもの

「振る舞いはコード、具体値はデータ」（prd/README の設計の柱）をシナリオにも当てる。

| 対象 | 扱い |
|---|---|
| 効果の種類の**意味**（`traffic` が収益と容量にどう効くか・`imageRedesign` の手間の決め方・`contract` の要件の判定など） | エンジンのコードのまま。外部のシナリオは、そのエンジンの版が持つ語彙の中から選ぶだけ。新しい効き方が要るなら、エンジンに足して版を上げる（§2.6） |
| 要件（`Requirement`・`scenario.ts:122`）と前提（catalog の `premise`） | 事実の判定は catalog とエンジンのもの。シナリオは id で参照するだけで、新しい要件・前提の文を作れない（AGENTS.md の 🔒。事実のように見える文をシナリオが書けると、出典の無い事実が混ざる） |
| 料金・制限 | シナリオには入れない。catalog の構成・部品を参照するだけ（§2.3） |
| 自由な戦略（任意の条件で行動を返す関数） | 外部のシナリオでは書けない。§2.5 の語彙で書けない基準プレイは、組み込みのシナリオで TypeScript のまま持つか、作らない。基準プレイは目標の値の根拠と成績の目盛り（prd/07 §10.8）で、遊ぶのには要らない（ES-05） |

## 2. スキーマと JSON の形

### 2.1 方針

- 形は **zod のスキーマ**（`ScenarioFileSchema`）で決め、型はそこから導く（prd/02 §4 の「検証を 1 か所に」）。今の `Scenario` 型は、スキーマを通した後の形（読み込み済みの形）として残す。
- 組み込みの 2 本も同じ JSON で書き、**読み込みの経路を 1 本にする**（組み込みだけが TypeScript のままだと、外部のシナリオの経路が試されない）。
- スキーマの置き場は `packages/game`（`src/scenario-schema.ts`）。game は今 zod に直接依存していない（estimator 経由で入っている）ので、依存に足す（ES-14）。

### 2.3 catalog の参照

シナリオは料金・制限・前提の文を持たない。catalog のものを id で指すだけにする。

| 参照 | 中身 | 読み込みで確かめること |
|---|---|---|
| 構成 | `STACK_DEFS` の `id`（`catalog/src/stacks/index.ts:20-57`） | 存在する。添字に直す |
| 部品 | スロット（`SlotId`）と部品の `id`（効果 `component`・`hidden.slots`） | その組が catalog にある |
| 前提 | `when.premiseIds`・`premiseRefs`（前提の id の前方一致） | 前方一致で 1 件以上当たる（当たらない前方一致は書き間違いとみなしてエラー） |
| テンプレート | `workload.template.ref`・`frameworks.spa.shape.ref` | catalog にテンプレートの表（id → テンプレート・SPA の形・`pvPerMau`）を足す（今は関数の export だけ。ES-03） |
| フレームワーク | `frameworks.allowed`・`default`（`FrameworkId`） | catalog のプロファイルにある |
| 事業者 | `events[].platforms`（`Platform`） | catalog にある |
| 改定 | `revisions`（catalog の `scheduledChanges` の幅だけ） | — |

架空の料金が要る外部のシナリオは、シナリオの中に料金を書かず、`fictional-` の provider（prd/03 §10）を catalog に足す。
会社固有の料金（相対の割引など）は、この仕組みの範囲外にする（ES-12）。

### 2.4 テンプレート（Workload）を外から定義できる範囲

- 今のテンプレートは「PV を受けて `WorkloadInput` を返す関数」だが、PV が効くのは `mau` と `monthlyPageViewsOverride` だけ（C-1）。
  そこで **PV に依らない `WorkloadInput` + `pvPerMau`** を正の形にし、PV を入れる処理はエンジン（`workloadOf`）が持つ。
- 外から書ける範囲は、estimator の `WorkloadInputSchema`（`packages/estimator/src/workload/schema.ts:53`）が受け付けるもの全部（ルートの組・レンダリング方式・API の重さ・画像・DB・リアルタイム）。スキーマはそれを再利用する。
- 書き方は 2 つ: **catalog のテンプレートを参照して一部を上書き**（`ref` + `overrides`）と、**全部を書く**（`inline`）。見積モードと共有したいテンプレートは catalog に入れて `ref` で指す。会社固有のアプリの形は `inline` で書き、catalog に入れない。
- 書けないもの: フレームワークのプロファイルと載せ方（`catalog/src/frameworks/`）、部品のスロット、構成の組み立て。これらは「振る舞い」の側で、足すには catalog とエンジンの変更が要る。
- 上書きは浅い結合でなく**キーごとの深い結合**にする（`routes` のような配列は丸ごと置き換え）。結合の規則をスキーマの説明に書く。

### 2.5 基準プレイの行動の規則（`decide` の置き換え）

規則は上から順に評価し、条件をすべて満たした規則の行動をその順に並べる。**順番に意味がある**（今の `vps-sla` は「4GB へプラン変更」を「SLA の打診を受ける」より先に出す。受けるには要件を満たす構成が要るため。`article-community.ts:549-559`）。

| 条件 | 意味 | 今の使い方 |
|---|---|---|
| `{ "saw": "<出来事の id>", "phase"?: "notice" \| "occurred" \| "proposal" }` | 前の月の終わりに出ていた出来事（`sawEvent` と同じ） | `s-d1-limit`・`s-image-storage`・`p-sla`（予告）・`c-s-file-storage` |
| `{ "stack": "<構成の id>" }` | 今の構成 | `s.stackIndex === VPS` |
| `{ "setting": "<key>", "above" \| "below": n }` | 設定の値 | `s.settings.imageKB > 105` |
| `{ "stage": "<要素>", "not" \| "is": "good" \| "fair" \| "bad" }` | 前の月の満足度の段階 | `speed !== 'good'` |
| `{ "storageOption": boolean }` | ストレージ変更オプション | `!s.storageOption` |

| 行動 | 意味 |
|---|---|
| `{ "type": "respond", "accept": "all" \| "none" \| ["<id>", …] }` | 返事待ちの提案すべてに返事する（列に入っている id だけ受け、残りは断る） |
| 今の `Action` の各種 | 構成は添字でなく id で書く（`migrate`・`plan`） |

- 7 本の `decide` はこの語彙で書ける（§1.1 C-3）。書き換えで golden が 1 セントも変わらないことを、段 2（§8）の合格の条件にする。
- 規則を評価する関数（`policyActions(state, policy)`）は game の純粋関数。
- 語彙は**基準プレイのためだけ**に置き、プレイヤーの自動化（「話題が予告されたら〜」のような予約）には広げない（ES-06）。

### 2.6 版（schemaVersion）

- `schemaVersion` は整数。エンジンが読める版の範囲を持ち、古い版は移行関数（保存の `migrateAction`・`save.ts:62` と同じ作法）で今の形に直してから検証する。新しすぎる版は「このアプリの版では読めない」と出す。
- 版を上げるのは、語彙（効果・条件・規則）の追加と意味の変更のとき。値の追加で既定がある場合（省略可の項目）は上げない（prd/10 B-9 と同じ判断）。
- `revision` は作者のための番号で、同一性の判定には使わない（同一性は §3.1 のハッシュ）。

### 2.7 検証とエラーの見せ方

検証は 3 段にする。どれかで落ちたら**一部だけ読むことはしない**（遊べるのに数字がおかしい、をなくす）。

1. **形**（zod）: 型・必須・範囲（確率は 0〜1、`from ≤ to`、`months` の範囲、重みの合計が 1 など）。
2. **参照**: catalog の id（§2.3）、出来事の id の重複、規則の `saw` が実在の出来事か、`window` が `months` に収まるか、`premise` の出来事の前方一致が当たるか。
3. **試走**: シード 1 本で全月を回し、例外が出ないこと（基準プレイがあればその全部）。読み込みの時間に効くので、シードは 1 本だけにする。

エラーは「JSON の場所（`events[3].when.premiseIds[0]`）+ 何が悪いか + 直し方の例」の一覧で出す。zod の issue の `path` をそのまま場所に使う。
シナリオの作者向けには、同じ検証を CLI でも回せるようにする（`pnpm scenario:check <file>`。基準プレイをシード 1〜50 で回して目標の公平さ（prd/07 §10.8）も出す）。目標の値を決める作業は作者の手元でするので、これが要る。

## 3. 同一性とハッシュ

### 3.1 内容のハッシュ

- シナリオの同一性は **正規化した JSON の SHA-256**（キーを並べ替え・空白なし）で決める。`id` と `revision` は人のための名前で、同じ `id` でも中身が変われば別物として扱う。
- 正規化は game の純粋関数。ハッシュの計算は **web とサーバーの側**（Web Crypto の `crypto.subtle.digest`。ブラウザにも Workers などにもある）。game は `lib: esnext`・`types: []` で Web Crypto の型を持たない（prd/02 §2）ので、game に入れない。
- 台本の乱数は出来事の id とシードから引く（`random.ts:12`・`scenario.ts:327`）。**出来事の id や順番を変えると、同じシードでも出来事の時期が変わる**。中身が少しでも違えば同じ結果にならない前提で設計する。

### 3.2 結果を決めるもの

同じ結果を再現するには、次のすべてが同じである必要がある。保存とランキングはこれを記録する。

| 要素 | 今の扱い | 足すもの |
|---|---|---|
| シナリオ | `scenarioId`（組み込みだけ） | 内容のハッシュ・出所（§4.3） |
| 始めたときの選択 | 構成・フレームワーク・部品・再検証・シード・始めた日（`save.ts:17-38`） | — |
| 行動の列 | `turns` | — |
| エンジン（game・estimator のコード） | 記録なし | エンジンの版（ビルドに埋めた版の文字列）。ランキングだけで使う（§5.1） |
| 料金データ | 記録なし（PriceBook ごとに `version` はある・`estimator/src/pricing/schema.ts:265`） | ランキングでは使った PriceBook の版の組を記録する |

ローカルの保存（D-26）は、エンジンと料金データの版を今も記録していない（更新後の再生で結果が変わりうるのを受け入れている）。外部のシナリオでもこの扱いは変えない。

## 4. 読み込み方

### 4.1 3 つの出所

| 出所 | 方法 | データが出る範囲 | 向く場面 |
|---|---|---|---|
| **組み込み** | `packages/game/src/scenarios/*.json` をビルドに入れる | 公開（リポジトリと配信物） | 今の 2 本・公開してよいシナリオ |
| **ファイル** | 始める画面で「シナリオのファイルを開く」（`<input type="file">`・ドラッグ）。`FileReader` で読むだけで送らない | 開いた人のブラウザの中だけ | 社内のドライブで配る。サーバー不要 |
| **URL** | 環境変数（例: `VITE_SCENARIO_URLS`）に URL の一覧を入れてビルドし、起動時に `fetch` | URL の置き場のアクセス制限の内側 | 社内向けのデプロイ。全員が同じ版を使う |

- URL の出所の注意: Vite の環境変数は**ビルドした JS に文字列で埋まる**。URL そのものが漏れて困る場合は、社内向けのビルドを社内の制限の内側だけで配る（公開のデプロイに社内の URL を入れない）。シナリオの中身は環境変数に入れない。
- URL はアプリと**同じオリジン**（例: 同じホストの `/scenarios/*.json`）に置くのが単純。アクセス制限（Cloudflare Access・社内の IdP の前段のプロキシなど）の Cookie がそのまま効き、CORS の設定が要らない。別のオリジンに置くなら CORS と資格情報つきの `fetch` の設定が要る。
- どの出所でも、読んだ後は §2.7 の同じ検証を通す。

### 4.2 読み込みの層

- **I/O は web だけ**（prd/02 §2・§5）。game には「JSON の値を受けて、検証済みの `Scenario` か エラーの一覧を返す」純粋関数（`parseScenario(raw, catalog)`）だけを置く。
- web は「組み込み + 読み込んだもの」の表を持ち、始める画面のシナリオの選択に並べる（`scenario-briefing.tsx:17` の `SCENARIO_LIST`）。読み込んだシナリオには出所の印（「ファイル」「社内」）を付ける。
- 表示の文はシナリオのデータなので、HTML として描かず文字列として出す（React の既定の扱い）。外から来た文で画面を壊せないようにする。

### 4.3 保存（D-26）に残すもの

保存の版を 2 に上げ、シナリオの欄を次の形にする（版 1 は `{ source: 'builtin', id: scenarioId }` として読む移行を足す）。

```ts
scenario: {
  source: 'builtin' | 'file' | 'url';
  id: string;          // シナリオの id
  revision?: number;
  hash: string;        // 内容の SHA-256（§3.1）。組み込みも記録する
  url?: string;        // source: 'url' のとき
}
```

| 場面 | 扱い（案） |
|---|---|
| 組み込み・ハッシュが一致 | 今と同じく再生する |
| 組み込み・ハッシュが違う（アプリの更新でシナリオが変わった） | 今と同じく再生を試み、例外なら捨てる（今の D-26 の扱い。組み込みの値の調整で保存を捨てさせない） |
| ファイル | **中身は保存しない**（既定）。再開には同じファイルを開き直してもらう（「このゲームは『○○』のファイルで始めました。もう一度開いてください」）。開いたファイルのハッシュが違えば、再生せずに「中身が違う」と出す |
| URL | 起動時に取り直してハッシュを比べる。違えば再生せずに「シナリオが更新された」と出し、保存を消すか残すかを選ばせる |
| シナリオが見つからない（ファイルを開かない・URL に届かない） | 保存を**捨てない**で残す（D-26 の「黙って捨てる」は壊れた保存のための規則で、外部のシナリオが手元に無いのは壊れていない）。「最初から」で消せる |

ハッシュが違うのに再生を許す選択肢は置かない。出来事の時期まで変わりうる（§3.1）ので、続きとして意味がない。

### 4.4 機密の扱い

社内のシナリオで外に出したくないのは、**文面**（顧客や案件を思わせる言い方）と**数値**（規模・収益）。ブラウザに残る範囲を絞る。

| 場所 | 残るもの（案） |
|---|---|
| localStorage（`infra-supra:game-save`） | 出所・`id`・`revision`・ハッシュ・URL・行動の列。**文面と数値は残さない**。`id` に顧客名を入れないことをスキーマの説明と CLI の警告で促す |
| シナリオの中身 | 既定では残さない（タブを閉じれば消える）。「このブラウザに覚えておく」を選んだときだけ IndexedDB に置く（ES-09） |
| JSON の書き出し（prd/02 §5） | 保存と同じ（中身を含めない） |
| 外への送信 | ランキングを使わない限り、どこにも送らない。ランキングに送るのはハッシュと行動の列だけで、中身は送らない（§5.5） |
| 公開のリポジトリ | 外部のシナリオのファイルを置かない。誤ってコミットしないよう、置き場の名前（例: `*.scenario.local.json`・`scenarios.local/`）を `.gitignore` に入れる。Betterleaks の規則（`.betterleaks.toml`）にファイル名で止める規則を足すかは ES-10 |

社内のシナリオでも、**料金・制限・前提の文は公開の catalog のもの**で、シナリオに入らない（§2.3）。
社内のシナリオの値も「ゲーム上の仮定」で、実在の値ではない。実際の案件の数値をそのまま入れるかは作者の判断で、この仕組みは区別しない（画面には今と同じく「ゲーム上の仮定」と出す）。

## 5. ランキング

### 5.1 何を信用するか

- クライアントが送る点数は信用しない。送るのは **始めたときの選択 + 行動の列**（= 今の保存の中身）で、サーバーが同じエンジンで再生して点数を出す。
- 決定論の前提（prd/02 §3・`estimator/src/num/arith.ts:8`）: 結果に効く値は四則演算と `Math.sqrt`・丸め・最大最小だけで計算し、乱数は mulberry32 と FNV-1a（`random.ts`。整数とビット演算だけ）。これなら、ブラウザとサーバーの JS エンジンが違っても同じ入力で同じ結果になる。
  2026-11-01 に grep で確かめた範囲では、超越関数は `Math.pow`（`game/src/trends.ts:259,267`）だけで、使い道は所持金の見込み（`cashProjectionOf`・画面の表示だけ）。状態と点数には入っていない。これを CI のテストで守る（ES-15）。
- 再生は**同じエンジンと同じ料金データ**でなければ一致しない（§3.2）。サーバーはクライアントと同じビルドを持ち、ランキングは「エンジンの版 × 料金データの版 × シナリオのハッシュ」で分ける。アプリを更新したらランキングの区切り（シーズン）を変える（ES-08）。
- 改定の出来事（D-21）は始めた日で変わるので、始めた日もサーバーが決める。

### 5.2 流れ

```
クライアント                                   サーバー
  │ ① お題を取る（シナリオのハッシュ・エンジンの版）──▶│ お題を発行: {ticket, seed, startDate, scenarioHash, engine, expiresAt}
  │◀─────────────────────────────────────────────── │  （今週のお題は全員同じ seed。個別のお題は 1 回ごとに seed を作る）
  │ ② 手元で遊ぶ（今と同じ。オフライン可）            │
  │ ③ 提出: {ticket, stack, framework, components, revalidateSec, turns, 名前} ─▶│
  │                                                │ ④ 検証: ticket が有効・未使用 → newGame(seed, startDate…) から replaySave
  │                                                │    → ゲームが終わっている・月数が合う・点数を計算
  │◀────────────────── 順位・点数（サーバーが計算した値）│ ⑤ 保存: 点数・行動の列（再検証と表示のため）・ticket を使用済みに
```

- お題（ticket）はサーバーに行（id・seed・期限・使用済みか）を持つか、署名（HMAC）で状態を持たずに渡す。使用済みの記録は要るので、どちらにしても小さな DB は要る。
- 点数の定義は未決（ES-07）。案: 目標に届いたかを先に、次に最後の所持金、同点は満足度の平均。
- 提出の検証で例外が出た・ゲームが終わっていない・`turns` の長さが合わないものは受け付けない。

### 5.3 再生による検証で防げること・防げないこと

| 攻撃 | 再生で防げるか | 対策 |
|---|---|---|
| 点数・所持金の書き換え | 防げる（点数はサーバーが計算する） | — |
| 状態の書き換え（在庫・満足度・出来事を消す） | 防げる（状態は送らない。行動だけ） | — |
| 選べない行動を混ぜる | 防げる（`applyAction` は選べない行動で状態を変えない。再生の月数で食い違いを見つける・`save.ts:76-79`） | 不正な行動を含む提出は拒否にしてもよい（ES-07 と一緒に） |
| **先読み**（シードから先の出来事を手元で計算する） | 防げない。台本は `newGame` でシードから一度に作る（`scenario.ts:308`・prd/07 §10.5） | 全員同じシードのお題なら「詰将棋」として受け入れる（§5.4） |
| **やり直し**（手元で何度も遊び、いちばん良い列だけ出す） | 防げない | 同上。個別のお題では 1 人あたりのお題の数を絞る（本人の確認が要る） |
| 自動で最適な列を探す | 防げない | 受け入れる。上限は「同じシードで誰でも同じことができる」公平さで担保する |

### 5.4 先読みの扱い

| 形 | 先読み | 費用・制約 |
|---|---|---|
| **A. 今週のお題**（全員同じシード・期間つき） | 誰でもできる＝公平。詰将棋の形 | サーバーはお題の発行と提出の検証だけ。オフラインで遊べる |
| **B. 個別のお題**（1 回ごとに別のシード） | 手元のエンジンで先を計算できる。やり直しは、お題の数を絞れば制限できる | A と同じ + 本人の確認 |
| **C. 月ごとの往復**（サーバーがシードを持ち、月の行動を送って月の結果を受け取る） | できない（クライアントは次の月の出来事を知らない） | 月ごとの遅延・オフライン不可・サーバーに進行中のゲームの状態・1 ゲームあたり 12 回の再計算（状態を持たないなら毎回最初から再生）。予告（`notice`）と前兆はプレイヤーに見える出来事なので、往復でも出してよい |

推奨は **A から始める**（ES-04）。C は「先読みされると成り立たない遊び方」（例: 予告の無い出来事への備えを競う）を入れるときに足す。
C を入れても、エンジンは手元にもあるので、往復の応答を見ながら手元で先の分岐を試すこと（月の中での最適化）は防げない。防げるのは「まだ起きていない出来事を知ること」だけ。

### 5.5 外部のシナリオのランキング

- ランキングの鍵は **シナリオのハッシュ**（+ エンジンと料金データの版）。同じ `id` でも中身が違えば別の表になる。
- **検証するサーバーはシナリオの中身を持っている必要がある**。提出に中身を含めず、ハッシュで指す。サーバーは知らないハッシュの提出を拒む。
- **公開のサーバー**: 組み込みのシナリオのハッシュだけを受け付ける（許可リスト）。誰でも中身を登録できる形にすると、(a) 任意のシナリオで点数を作れる (b) 社内のシナリオを誤って公開のサーバーに送る事故が起きる。
- **社内のサーバー**: 同じサーバーのコードを社内向けに別にデプロイし、DB も別にする。シナリオは社内の URL（§4.1）から取るか、管理者が登録する。アクセス制限の内側に置き、本人の確認は前段の IdP に任せる（制限の製品が付けるヘッダーなど。事業者ごとに違うので、アダプターの層で吸収する）。
- 社内のサーバーは「外部読み込みのためのサーバー」ではなく、「社内のシナリオで社内のランキングを持つためのサーバー」。ランキングが要らなければ、§4.1 のファイルか URL で足りる。

### 5.6 サーバーの置き場の候補

要るのは、(1) game・estimator・catalog の TypeScript（純粋関数・環境非依存）が動く JS の実行環境、(2) お題・提出・点数の小さな表、(3) 1 回の検証で 12 か月の再生。
このリポジトリが比べている構成のどれにも載る。自分のサーバーの請求を自分の見積と突き合わせられる（prd/02 §6 と同じ考え）。

| 候補 | 実行 | 保存 | 気にすること |
|---|---|---|---|
| Cloudflare Workers + D1 | Workers | D1（SQLite） | **Workers Free は 1 リクエストあたり CPU 10 ms まで**（catalog の `limit:cloudflare:workers-free:cpu-ms-per-request`・出典つき）。12 か月の再生がこれに収まるかは**未計測**（段 0 で測る）。Paid の 1 リクエストあたりの上限は catalog に未取得 |
| Vercel Functions + Supabase（Postgres） | Node.js の関数 | Postgres | 関数の実行時間と課金の単位（catalog の Vercel のデータの範囲で比べる） |
| さくらの VPS + Node.js + SQLite / MySQL | 常駐のプロセス | ローカルの DB | 運用の手間（ゲームの自前運用と同じ話）。社内のサーバーなら既存の社内の基盤に載せる選択も同じ形 |

- サーバーのコードは新しいパッケージ（例: `packages/ranking`）に置き、HTTP と DB の層は事業者ごとのアダプターにする（中心は「提出 → 再生 → 点数」の純粋関数で、game に置ける）。依存の向きは `ranking → game → estimator ← catalog`（prd/02 §1 に 1 行足す）。
- バンドルの大きさ（catalog の料金データを丸ごと含む）と、1 回の再生の CPU 時間は段 0 で測ってから候補を絞る（ES-13）。

## 7. 危ない点

| # | 内容 | 影響 |
|---|---|---|
| R-1 | エンジンが既定値として記事コミュニティの値に落ちる経路（C-8） | 外部のシナリオで値が黙って記事コミュニティのものになる。段 1 で引数を必須にし、テスト「シナリオの値を全部変えると結果が変わる」を足す |
| R-2 | 語彙で書けない出来事の効き方が後から要る | 外部のシナリオの作者がエンジンの変更を待つことになる。語彙の追加は版を上げる（§2.6）。会社のシナリオの要望は、出典の要らないゲーム上の仮定の範囲なら公開のエンジンに足してよい |
| R-3 | ランキングの区切り（エンジン・料金データの版）が多すぎる | 料金データの小さな更新のたびにランキングが分かれる。シーズンの単位で版を固定し、その間はサーバーに旧版のビルドを残す（ES-08） |
| R-4 | 12 か月の再生の CPU 時間が未計測 | サーバーの置き場と費用が決まらない（§5.6） |
| R-5 | 外部のシナリオのファイルが公開のリポジトリに入る | §4.4 の `.gitignore`・ES-10 |
| R-6 | 組み込みを JSON にすると、TypeScript の型の補完が効かなくなる | JSON スキーマを zod から生成し、エディタの補完に使う（ES-11） |

## 8. 段階の計画

規模は 1 段 = 1 PR とした作業量の目安（見込みで、測った値ではない）。各段の終わりで golden（記事コミュニティ・受託）が変わらないことを合格の条件にする（段 5・6 は対象外）。

| 段 | 中身 | 規模 | 合格の条件 |
|---|---|---|---|
| 0 | 計測: 1 ゲーム（12 か月）の再生の CPU 時間とバンドルの大きさ（Node と Workers 相当の環境）。超越関数を使っていないことのテスト | 小 | 数値が §5.6 の判断に足りる |
| 1 | エンジンの内部のデータ化: C-1・C-2（`workloadOf`・`pvPerMau`）、C-4（構成の id）、C-5、C-7（`IMAGE_REDESIGN_ID` を外す）、C-8（既定値を外す） | 中 | golden が 1 セントも変わらない |
| 2 | 基準プレイの規則（§2.5）。7 本の `decide` を置き換える | 中 | golden が変わらない・基準プレイの表（prd/07 §10.8・prd/09 §9.2）が変わらない |
| 3 | スキーマ（zod）・`parseScenario`・3 段の検証・組み込みの 2 本を JSON に移す（試金石）・`pnpm scenario:check` | 中〜大 | 2 本が JSON で書け、読み込み後の結果が TypeScript 版と一致 |
| 4 | web の読み込み（ファイル・URL）・ハッシュ・保存の版 2・機密の扱い（§4.4）・エラーの一覧の画面 | 中 | 外部のファイルで最後まで遊べ、再読み込みで続きから（同じファイルを開き直す）再開できる |
| 5 | ランキング（今週のお題）: `ranking` パッケージ・お題の発行・提出・再生の検証・表示。公開のサーバーは組み込みのシナリオだけ | 大 | 改竄した点数・状態の提出が通らないテスト。同じ提出を 2 回検証して同じ点数 |
| 6 | （必要なら）個別のお題・本人の確認・社内のサーバーのデプロイの手順・月ごとの往復 | 大 | 先読みが要る遊び方を入れると決めたとき |

段 1〜3 は外部読み込みにもランキングにも要る共通の土台で、段 4 と段 5 は互いに独立している（どちらを先にしてもよい）。

## 9. 論点の一覧（未決・推奨案つき）

| # | 問い | 選択肢 | 推奨と理由 |
|---|---|---|---|
| ES-01 | 組み込みのシナリオも JSON に移すか | ① 移す（読み込みの経路を 1 本に）② TypeScript のまま・外部だけ JSON | **①**。② だと外部の経路が試されず、語彙の不足に気づけない。2 本が JSON で書けることが試金石（§0） |
| ES-02 | スキーマの形式 | ① zod（型を導く）② JSON Schema を正にして型を生成 ③ TypeScript の型だけ | **①**。prd/02 §4 の方針（zod で検証を 1 か所に）と同じ。エディタの補完用の JSON Schema は zod から生成する（ES-11） |
| ES-03 | テンプレートの書き方 | ① `ref`（catalog の表）+ 上書き と `inline` の両方 ② `inline` だけ ③ `ref` だけ | **①**。見積モードと共有するものは catalog に、会社固有のアプリは catalog に入れずに書ける |
| ES-04 | ランキングの最初の形 | ① 今週のお題（全員同じシード）② 個別のお題 ③ 月ごとの往復 | **①**。先読みとやり直しが公平になり、本人の確認も月ごとの往復も要らない。サーバーは発行と検証だけ |
| ES-05 | 外部のシナリオに基準プレイを必須にするか | ① 任意（あれば比較の表と目標の確認に使う）② 必須 ③ 持てない | **①**。遊ぶのに要らない。作者が目標を決めるときは CLI（§2.7）で回す |
| ES-06 | 行動の規則の語彙をどこまで広げるか | ① 今の 7 本が書ける最小 ② 一般の条件式（and / or / 比較）③ スクリプト（関数） | **①**。③ は外部のコードを動かすことになり、機密のシナリオを開くたびに任意のコードを実行する形になる。足りなくなったら条件を 1 つずつ足す |
| ES-07 | 点数の定義と、不正な行動を含む提出の扱い | ① 目標に届いたか → 所持金 → 満足度の平均。不正な行動を含めば拒否 ② 所持金だけ ③ シナリオごとに定義 | **①**。合否（prd/07 §7）を先にしないと、目標を外して所持金だけ大きい遊び方が上に来る |
| ES-08 | ランキングの区切り | ① シーズン（期間）ごとにエンジンと料金データの版を固定 ② 版が変わるたびに分ける ③ 分けない | **①**。③ は再生が一致しなくなる。② は表が細かく割れすぎる |
| ES-09 | 外部のシナリオの中身をブラウザに残すか | ① 既定は残さない・選べば IndexedDB ② 常に残す ③ 残せない | **①**。機密の既定を安全側に置き、毎回ファイルを開く手間は選択で省ける |
| ES-10 | 外部のシナリオのファイルをコミットから止めるか | ① 名前の規約 + `.gitignore` + Betterleaks のファイル名の規則 ② `.gitignore` だけ ③ 止めない | **①**。public リポジトリで `.env*` を止めているのと同じ作法（AGENTS.md の秘密の検査）。ただし規約の名前にしたファイルしか止まらない |
| ES-11 | エディタの補完 | ① zod から JSON Schema を生成して `$schema` で指す ② なし | **①**。外部の作者は TypeScript の型を使えない |
| ES-12 | 会社固有の料金（割引・契約の単価）を扱うか | ① 扱わない（公開の料金だけ）② シナリオに料金の上書きを持たせる | **①**。料金は catalog の実データだけ（AGENTS.md の 🔒）。要るなら別の論点として、見積モードの「契約の単価」の入力として設計する |
| ES-13 | ランキングのサーバーの置き場 | ① 段 0 の計測の後で §5.6 から選ぶ ② 今 Cloudflare Workers + D1 に決める | **①**。Workers Free の CPU 10 ms に収まるかが未計測で、決めると費用の見積がずれる |
| ES-14 | game が zod に直接依存するか | ① 直接の依存に足す（版は estimator と揃える）② estimator から再 export ③ スキーマを別のパッケージに | **①**。estimator の再 export は境界が曖昧になる。③ はパッケージが増えるだけ |
| ES-15 | 決定論をテストで守るか | ① 状態に効く計算のコード（画面の見込みの `trends.ts` を除く）に超越関数・`Date`・`Math.random` が無いことを lint か grep のテストで止める ② 守らない | **①**。ランキングは「ブラウザとサーバーで同じ結果」が前提になり、今は規約（prd/02 §3・AGENTS.md）だけで守っている |
| ES-16 | ランキングの名前の扱い（公開のサーバー） | ① 匿名の表示名だけ（本人の確認なし。今週のお題なら足りる）② ログイン ③ 外部の ID | **①**。ES-04 の ① では本人の確認が要らない。個別のお題（段 6）を入れるときに決め直す |
