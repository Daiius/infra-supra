## 決定

### D-01 フロントは Vite（Next.js は使わない）（暫定・2026-10-31）

- MVP は計算をブラウザで行い、保存もローカル。サーバーの処理がないので App Router の利点（SSR・サーバーの処理）を使わない。
- 静的配信だけで動くので、比較対象のどの構成にも載せられる（02 §6 の「自分自身で検証する」ができる）。
- seseraki と同じスタック（React 19 + Vite + TanStack Router + Tailwind v4 + daisyUI）にして、知見を流用する。
- 将来クラウド保存を足すときは API を別パッケージで立てる。

### D-02 パッケージは estimator / catalog / game / web に分ける（暫定・2026-10-31）

- 見積ツールを単独で切り出せるように、estimator と catalog は game を知らない（02 §1）。
- 企画書 §7.2 のモジュール（workload・infrastructure・resource-simulation・pricing・performance）は estimator の中のディレクトリにする。
  パッケージを細かく分けすぎると、型の行き来のたびに境界をまたぐことになるため。

### D-03 振る舞いはコード、具体値はデータ（暫定・2026-10-31）

- ComponentKind はコード、ServiceOffering と PriceBook はデータ（01 §4.1）。
- 「料金変更時にエンジンを変更しない」（企画書 §3.4）を満たしつつ、メーターの導出式を DSL にしない。

### D-04 Workload は正準な入力 + 導出値（暫定・2026-10-31）

- 企画書の入力項目のうち互いに導出できるもの（MAU・PV・平均 RPS・ピーク RPS など）を独立入力にしない（01 §3.1）。

- 静的出力は静的ホストの比較に帰着するが、Vercel などに載せたときの課金（ミドルウェア・画像最適化など）は別に扱う。

### D-16 金額・使用量は普通の number で計算する（確定・2026-10-31）

- ユーザーの確認: 10 進数ライブラリは要るか。→ 実測し、浮動小数点で困るのは小数の量を小数の単位で切り上げる境界だけと分かった
  （`0.1 × 3` を 0.1 単位で切り上げると 0.4。金額の誤差は相対 10⁻¹⁵ 程度で表示の桁に届かない）。number を推奨し、ユーザーが選んだ。
- 規律は 02 §3（`ceilUnits` に切り上げを閉じ込める・量は整数の単位・丸めは表示だけ）。
- 理由: 精度を決めるのは仮定のほうで、10 進数の代償（`a.times(b)` 形式の読みにくさ、ゲームや規模の掃引での数十〜百倍の遅さ）に見合わない。
- P1-2 は一度 big.js で実装したが、コミット前に number へ差し替えた。

### D-19 ゲームオーバーの条件（確定・2026-10-31）

- ユーザーの指摘（試作を触った感想）: 止まった月の上限を超えたら 12 か月目を待たずに終わる。規約違反は続けられないようにする。
- 止まった月が上限（2 回）を超えた月にゲームオーバー（理由と月を結果に出す）。所持金が尽きた月も同じ。
- 規約違反（利用資格の前提・`effect: 'policy'`。例: Vercel Hobby の商用利用）は、最初の月に運営元からの指摘（警告）を出し、**翌月も違反したままならアカウント停止でゲームオーバー**。
- 猶予は 1 か月。指摘の月にプラン変更すれば翌月は違反しない。乗り換え（2〜3 か月）は、**始めた時点で猶予を満たしたとみなし**、乗り換えの期間中は停止しない（ユーザー確認済み・2026-10-31）。
- 規約違反の月は「止まった月」に数えない（試作は止まる扱いだった）。数えると、乗り換えの猶予の間に停止の上限で必ず終わるため（ユーザー確認済み・2026-10-31）。
- 07 §7・§9.6。

### D-21 実際に予告されている改定の出来事（確定・2026-10-31）

- ユーザーの判断: 料金の部分はリアルにしている。現実に料金改定が事前に告知されていて、それまでの間であれば発生するイベントにする。

### D-43 SPA で OGP の前処理なしに話題を迎えたときのヒント（確定・2026-11-01）

- 背景: 記事コミュニティを SPA で何もしないと、VPS は 0/20 で達成しない（Next.js は 16/20）。落ちる理由は所持金だけで、どれも仮定 A-8（OGP の前処理なしでは話題の伸びが × 3 → × 2。prd/10 F-05）による。負荷・費用・満足度は Next.js と同じ。
- ユーザーの決定: `retryHintsOf` に、SPA で OGP の前処理（部品のスロット `ogp`）を付けずに話題の月を迎え、所持金の条件で落ちたときのヒントを足す。文面は「n か月目の話題で、記事ごとの SNS のカードが出ないため伸びが小さかった（前処理があれば、収益は約 +$X の見込み）」。方向は「SNS のカード（OGP）の前処理の部品を、話題の前に付ける」。部品名は出してよく、正解の構成名は出さない方針（D-40）は変えない。
- $X は A-8 の倍率から記録で見積もる。行動の列は状態に残らないので、プレイは引き直せない。話題の月の広告の収益は × f / × (1 + (f − 1) × c) 倍、以後の月は話題の後に残る伸び（`buzzLasting`。その月の評判で）の比の倍とする。成長率・費用・上限への当たり方の変化は入れない。
- 1 か月目の終わりに前処理を付けたプレイと比べると、VPS 2GB・4GB・Vercel Pro のシード 1〜3・42 で、収益の差と一致した（テストは VPS 2GB で $2 以内を確かめる）。
- 並びは影響額で比べる。足りない額に対する $X の割合を点にし、半分以上なら最上位にする。prd/07 §9.6。

### D-49 ISR の再検証にオンデマンドを足す（確定・2026-11-01）

- ユーザーの依頼: ISR の再検証の時間について、最初からオンデマンド ISR を選択肢として入れられないか。それまでは時間の間隔だけで、オンデマンドは即時反映の提案（p-ondemand・D-32）を受けたときの要件として入るだけだった。

### D-55 VPS の前段の CDN で HTML もキャッシュするときの再生成の数え方を直す（確定・2026-11-01）

- 既知の問題（PR #3 の本文）: 前段の CDN を「HTML もキャッシュ」（D-31）にしたとき、ISR の再生成の回数を閲覧の総数（CDN の手前）から数えるので、VPS の CPU を多めに見積もる。
- 調べた結果: 月の数は D-37 で CDN の miss と同じ式になっていて、CDN を miss して VPS に届いた閲覧と一致していた（CDN と ISR の期間が同じなので、届いた閲覧はそのつど再生成を起こす）。多めだったのはピークの時間帯だけで、閲覧はピークの miss で流すのに、再生成は月の数のまま流していた。
- 直した: estimator の simulate で、ISR のページを期間つきでキャッシュする CDN の後ろでは、再生成の流れを「CDN を miss して届いた閲覧」（月は miss・ピークはピークの miss）にした（prd/04 §2）。オンデマンド（D-49）はピークの miss の割合を月と同じとみなすので、変わらない。
- 影響（記事コミュニティ・何もしない・シード 1〜20・VPS 2GB / 4GB）: HTML もキャッシュ × 5 分でピークの CPU 使用率の最大が約 0.77 倍（2GB で 20.0% → 15.4%）。達成数・前段の CDN なし・静的と画像だけ・オンデマンドは変わらない。golden は変わらない（基準プレイに HTML もキャッシュは無い）。
- 残した点: CDN が無い構成でも、ピークの時間帯の再生成は月の数のまま流している（ピークは閲覧の密度が上がって ISR がよく当たるので、実際は少ない）。既定の構成の結果を変えないため、今回は直していない。

### D-56 オンデマンドの最大寿命（保険の時間の再検証）は選択肢にせず 1 日とみなす（確定・2026-11-01）

- ユーザーの決定: オンデマンド ISR の最大寿命（保険の時間の再検証）は選択肢にせず、説明だけにする。もっともらしい寿命を仮に入れておく。
- 実装: オンデマンド（`revalidateSec` 0）のときも最大寿命 1 日（86,400 秒・ゲーム上の仮定。よく使われる 1 時間〜1 日の長い側）の時間の再検証を併せて持つとみなす。再生成の回数に時間の式の分を足す（閲覧の回数を超えない。estimator の `onDemandMaxAgeSeconds`・prd/04 §2）。
- 説明: 設定の ⓘ に「実際には、再検証の呼び出しの取りこぼし（webhook の失敗・呼び忘れ・外部データの変化）に備えて、時間の再検証（最大寿命）を併せて設定することが多い（1 時間〜1 日など）。このゲームでは 1 日とみなす」と書いた。Next.js について書いたのは、公式の ISR のガイド（nextjs.org/docs/app/guides/incremental-static-regeneration・2026-10-15 更新・2026-11-01 取得）で確かめた範囲（タグで再検証するデータに revalidate: 3600 を併せて付けた例がある）だけ。文書は「1 秒より 1 時間のような長い間隔を勧め、精度が要るならオンデマンド」とも書くが、併用を勧める一文は無かったので、併用が多いという部分は一般の運用の説明として書いた。
- 見込みとの違い: 「閲覧の薄い記事ではほぼ 0」と見込んでいたが、時間の式では逆になる。閲覧の薄いページは読まれるたびに 1 日が過ぎていて作り直すので、最大寿命の分はほぼ閲覧の回数になる。頭打ちになるのは閲覧の濃いページ（ページ数 × 30 回 / 月）。記事コミュニティは 1 記事 1 日 3 回ほどの閲覧なので、最大寿命の分が効いた。
- 影響（何もしない・シード 1〜20・記事コミュニティ・オンデマンド）: 合否・満足度は変わらない。再生成（1 か月目）は約 1.4 万 → 5.9 万回、12 か月目は約 4.2〜5.6 万 → 9.7〜11.2 万回。5 分の約 18 万・56〜70 万回よりは少ない。12 か月の費用は Vercel Pro が $1,621 → $1,628 で、CF Paid（$178）と VPS 2GB（$157）は変わらない。golden は提案を全部受ける基準プレイ（cf-paid-accept）のシード 3（2197.87 → 2197.81）・31（650.55 → 643.29）だけが変わった。

- SPA の部品のスロット「API の置き場」（`api`）。既定は同じ事業者。許した組（公式で確かめた・2026-11-02）: Vercel・AWS（S3 + CloudFront）の静的 + **Cloudflare Workers + D1（binding）**、Cloudflare の静的 + **AWS API Gateway（HTTP API）+ Lambda + DynamoDB**。DB は API と同じ事業者に置く。遅延は計算しない（AX-13）。D1 の REST 直結は出さない（AX-10）。
- 課金: API Gateway の応答は東京 → インターネットの転送（HTTP API は「data transferred out」で課金・EC2 の料金）。Worker から外・S3 への受信は課金なし。Vercel の外部への rewrite は使わずサブドメイン + CORS（B-3 を避けた）。Workers のプランは Vercel Hobby なら Free・それ以外は Paid（仮定）。
- ゲーム: 移し替えは DB と同じデータの移行（6 × 1 か月・新旧両方の費用・仮定）+ アカウントの手間（D-52）。API を他の事業者に置くと構成の DB のスロットを出さず、API の応答のキャッシュ・D1 の画像とは同時に選べない（`componentConflict`）。
- 入れなかった: VPS（API）+ 静的は Cloudflare（自前運用の維持・障害を部品で効かせるルールが無い）、F-14（Next.js で API を別に置く）。
- 基準プレイ（何もしない・シード 1〜20）: **記事コミュニティの Vercel Pro + Workers + D1 は 0 / 20**（Supabase Pro は消えるが Vercel の席と HTML・JS の転送が残り、画像も R2 に出して所持金 $1,613。Hobby は静的だけでも非商用の規約で止まる）。**受託の Vercel Pro + Workers + D1 は 0 → 20 / 20**。Cloudflare の静的 + AWS の API は CF Free でも届く道筋になる（受託 20 / 20・記事は画像を縮めると 20 / 20）。CF Paid × 既定は不変（golden も不変）。prd/10 §9。
- 追記（レビュー OCL-5A7916E6・2026-11-02）: API を他の事業者へ移し替え終えたら構成の DB の選択を既定に戻し、API を他の事業者に置いている間は構成の DB の選択（KV を DB の代わりに）で鮮度を下げない。

### D-66 OpenNext の運用の費用（CloudFront の無効化・再検証の関数・S3 のキャッシュ）を数える（確定・2026-11-01）

- ユーザーの方針「より現実的な Web アプリケーション運用のコスト感」による。D-63 で数えていなかったものを公式で確かめて足した（推奨案で自律に決定）。prd/11 §13.1。
- CloudFront の無効化: オンデマンドの再検証 × ISR を CloudFront にキャッシュする形で、更新 × 2 ページ（記事と一覧。仮定 `ON_DEMAND_PAGES_PER_UPDATE`）× 2 パス（OpenNext の CloudFront の実装）。従量は月 1,000 パスまで無料・以降 $0.005。定額のプランは込みと読む（解釈。機能の表に全段で「Fast cache invalidations」）。
  エンジンに `invalidation-paths`（資源）・Workload の `onDemandPagesPerUpdate`・`cdn` の `invalidationPathsPerPage` を足した（prd/04 §2）。
- 再検証の関数（SQS → 再検証の関数 → サーバーの関数。待つ間も課金・1 GB は仮定）と S3 の ISR のキャッシュの保存量（ページ × 応答 × 2。倍率は仮定・`isrCacheSizeFactor`）を足した。ウォーマーは既定で無効なので 0。
- 結果: 記事コミュニティの OpenNext × オンデマンド × 従量は 19〜20/20 → **0/20**（1 か月目の無効化 $295 で所持金が尽きる）。定額 Pro・ISR をキャッシュしない部品・時間の再検証では起きない。5 分の再検証は数ドル増え、縮める・従量が 18 → 17/20（シード 5 が目標に $0.26 届かない）。受託は変わらない。
- golden: OpenNext・画像の最適化（時間の再検証）の所持金が $1.2〜1.6 減る（再検証の関数の GB 秒と保存量）。結果は変わらない。
- 追記（決定・supervisor）: 料金は曲げず、選ぶ前に分かるようにする。再検証の設定の「オンデマンド」（始める画面・ゲーム中）に、今月の規模での見込み「無効化 月約 N パス・約 $X（月 1,000 パスまで無料、以降 1 パス $0.005）」を出す（定額のプランは「込み。解釈」。`onDemandInvalidationEstimate`・`setupInvalidationEstimate`）。
  無効化の費用が最も大きくて負けたときは、次のプレイへのヒント（費用）が「定額のプラン・時間の再検証・ワイルドカードやタグでまとめる」の方向を出す。
- 未決: ワイルドカード・タグの無効化を部品にするか。

### D-67 API の置き場の段 3: Next.js の API を別の事業者に・Cloudflare の静的 + VPS の API（確定・2026-11-02）

- ユーザーの方針「より現実的なコスト感・費用を抑える複雑な構成も可能にしたい」。D-65 で入れなかった 2 つ（F-14・VPS の API）を推奨案で自律に入れた。prd/10 §9.5・§9.6。
- **Next.js（F-14）**: Vercel（Hobby・Pro）・Amplify・OpenNext の Next.js に「Cloudflare: Workers に API を置き、DB は D1（Next.js のサーバーから呼ぶ）」。SSR・ISR の作り直し・Route Handler の経路の DB を Worker → D1 に差し替え、ブラウザは今の事業者だけを呼ぶ（CORS なし）。
  サーバーから外への通信は OpenNext の Lambda だけ EC2 のデータ転送で数え（1 回 1 KB・仮定。エンジンに `cdn` の `egressKBPerRequest`）、Vercel・Amplify は料金の文書に項目が無いので数えない（前提の文）。SSR が API を待つことは前提の文（Next.js の文書の「will block the page from rendering」）で出し、遅延は計算しない（AX-13）。Worker の CPU は 1 回 5 ms（仮定）。
- **VPS の API**: Cloudflare（Free・Paid）の SPA に「さくらの VPS 2GB / 4GB に API と MySQL」。api のサブドメインは DNS だけのレコードで VPS に直接向ける。画像は R2 に置くので VPS のディスクに数えない（エンジンに `host` の `storesImages`）。
  **自前運用の維持（3 / 月）と偶発的な障害（月 8%）を部品にも効かせた**（構成のノードに VPS のホストがあれば。`selfHostedOf`）。障害は VPS が経路に載っている月だけ。
- 基準プレイ（何もしない・シード 1〜20）: **CF Paid × 既定は不変**（golden も不変）。受託の Vercel Pro の Next.js + Workers・D1 は 0 → 20 / 20（Supabase Pro の固定費が消える）、記事は 0 / 20 のまま。
  受託の Cloudflare + VPS 2GB の API は 17 / 20（VPS だけの構成は画像でディスクが埋まり 1 / 20）。記事は VPS の構成と同じく 0 / 20。DB が従量の AWS では Workers の基本料の分だけ高くなる。
- 見送った案: API の VPS の障害を「可用性は普通」として軽くする（§3.4）。売上の減り方は VPS の構成と同じにした（新しい係数の根拠が無い）。

### D-68 3 つ目のフレームワーク: Astro（確定・2026-11-02）

- ユーザーの方針「見積対象を作者のスタックに寄せない。Vite・Next.js・vinext、後で Astro」による。推奨案で自律に決定。仕様・出典・仮定・基準プレイは prd/06 §6。
- 形: 記事は静的にビルド（ISR の代わりにビルドし直し）・マイページはアダプターで SSR・JS はアイランドだけ。DeployTarget は Cloudflare（@astrojs/cloudflare・Workers）・Vercel（@astrojs/vercel）・VPS（@astrojs/node）が native、**AWS は unsupported**（公式のアダプターが無い。始める画面・乗り換えで選べない）。
- ビルドの課金を公式で確かめた範囲で数える: Workers Builds（Free 3,000 分・Paid 6,000 分 + $0.005 / 分。Free の超過は記載なしで「上位のプランが必須」と解釈）、Vercel Pro（CPU minute $0.0035・Elastic の最小 4 vCPU と解釈。Hobby は込み）。VPS は同じホストでビルドし数えない。エンジンに資源 `build-minutes`・単位 `minute`・Workload の `build`・ノード `ci-build` を足した（prd/04 §2）。
- 仮定: JS・CSS 0.3 倍、ビルドを起こす更新は内容の更新の 2%（30 万 PV で月 300 回）、1 回 1 分 + 1,000 ページあたり 0.5 分、初回表示で速さの重さを 1 つ減らす（記事コミュニティだけ）、オンデマンド = 更新のたびにビルドで即時反映の要件を満たす。設定「ビルドの間隔」は revalidateSec をこの意味で使う。
- 結果（何もしない・シード 1〜20）: 目標の根拠（CF Paid × Next.js）は変わらない。記事コミュニティの Astro は CF Paid 20 / 20・所持金 $2,601（Next.js $2,152）・VPS 2GB 17 / 20（Next.js 10 / 20）。差のほぼすべてが初回表示の仮定で、外すと Next.js とほぼ同じ。ビルドの費用は 30 万 PV では小さい（Vercel Pro で月 約 $8）。受託は Next.js と同じ値。
- 保存の形は変えない（framework の id に astro を足しただけ。古い保存は今のまま読める）。golden は変わらない。
- 残した点: Vercel の isr で記事を描く形、Server Islands、Astro × AWS、VPS のビルドの CPU、Hobby の 1 日 100 デプロイ、ビルドの遅れを鮮度に足すこと、初回表示の仮定の大きさの見直し。

### D-69 Astro の API の置き場（確定・2026-11-02）

- D-67 と D-68 が並行で入ったので、Astro では API の置き場を同じ事業者のみにしていた（自律の作業の推奨案）。公式で確かめて、現実にできる 2 つの組を推奨案で許した。prd/10 §9.7。
- **Vercel・VPS の Astro + Cloudflare Workers・D1**（`cf-workers-astro`）: Astro の SSR の fetch は実行時に走る（docs.astro.build の Data fetching）。D-67 の `cf-workers-server` と同じ形で、マイページ・API の経路の DB を Worker → D1 に差し替える。Vercel の関数から外への通信は数えない（D-67 と同じ）、VPS は転送量が無制限。
  VPS は MySQL を動かさない（常駐メモリ 0.75 GB・DB の CPU 0・ディスクに DB を置かない。エンジンに `host` の `storesDb`）。
- **Cloudflare の Astro + さくらの VPS の API**（SPA と同じ部品 `sakura-vps-2gb`・`4gb`）: ブラウザの API・投稿は D-67 と同じく VPS に直接。マイページを描く Worker が VPS の API を fetch で呼ぶ。Worker から外への fetch は課金されず転送の料金も無く、待つ時間は CPU 時間に数えない（Workers の料金・制限のページ）。
- 出さない組: Cloudflare の Astro + AWS の API（Worker の SSR が API Gateway を呼ぶ転送を確かめていない）・Astro × AWS（D-68）。
- 構成の名前は D-65 の実際の組の名前 +「（Astro）」。SSR が外の API を待つことは前提の文（`astro-server-fetch`）、遅延は計算しない（AX-13）。
- 基準プレイ（何もしない・シード 1〜20）: **CF Paid × Next.js（目標の根拠）と Astro の既定は不変**（golden も不変）。受託の Vercel Pro の Astro + Workers は 0 → 20 / 20（Supabase Pro の固定費が消える）。Cloudflare の Astro + VPS の API は記事 17 / 20・受託 12 / 20（Cloudflare の Astro だけより損）。VPS の Astro + Workers は Workers Paid の基本料の分だけ損。
- 文言: 「同じ事業者」の説明文（Cloudflare）を「シェルと同じ Worker」から「サイトと同じ Worker」に替えた（SPA と Astro で共有する）。
