## 決定

### D-01 フロントは Vite（Next.js は使わない）（暫定・2026-10-31）

- MVP は計算をブラウザで行い、保存もローカル。サーバーの処理がないので App Router の利点（SSR・サーバーの処理）を使わない。
- 静的配信だけで動くので、比較対象のどの構成にも載せられる（02 §6 の「自分自身で検証する」ができる）。
- seseraki と同じスタック（React 19 + Vite + TanStack Router + Tailwind v4 + daisyUI）にして、知見を流用する。
- 将来クラウド保存を足すときは API を別パッケージで立てる。

### D-02 パッケージは estimator / catalog / game / web に分ける（暫定・2026-10-31）

- 見積ツールを単独で切り出せるように、estimator と catalog は game を知らない（02 §1）。
- 企画書 §7.2 のモジュール（workload・infrastructure・resource-simulation・pricing・performance）は estimator の中のディレクトリにする。
  パッケージを細かく分けすぎると、型の行き来のたびに境界をまたぐことになるため。

### D-03 振る舞いはコード、具体値はデータ（暫定・2026-10-31）

- ComponentKind はコード、ServiceOffering と PriceBook はデータ（01 §4.1）。
- 「料金変更時にエンジンを変更しない」（企画書 §3.4）を満たしつつ、メーターの導出式を DSL にしない。

### D-04 Workload は正準な入力 + 導出値（暫定・2026-10-31）

- 企画書の入力項目のうち互いに導出できるもの（MAU・PV・平均 RPS・ピーク RPS など）を独立入力にしない（01 §3.1）。

- 02 §3。

### D-07 見積対象のフレームワークを入力の軸にし、特定のスタックに寄せない（確定・2026-10-31）

- ユーザーの指示: 作者の好みの構成に寄せない。Vite と Next.js・vinext を考慮し、Astro なども入れたい。
- フレームワーク → BuildOutput（中間表現）→ DeployTarget（ホスト × アダプター）で構成に写す（06）。
- MVP は Vite（SPA）・Next.js・vinext。Astro は MVP 直後に「データ追加だけで足せるか」の検証として入れる。
- 静的出力は静的ホストの比較に帰着するが、Vercel などに載せたときの課金（ミドルウェア・画像最適化など）は別に扱う。

- **料金データに「解釈」を持たせる**（所見 2）。公式の文書が食い違う箇所は、既定の解釈と別の解釈を並べ、見積は幅で出す（03 §10）。

### D-10 料金の解釈は最もらしい方に固定し、実請求で確かめる（確定・2026-10-31）

- Vercel Pro は「pricing ページの込み分 + $20 のクレジット」を採用（根拠はスパイクの README「Vercel Pro の解釈」）。
- 会社の Pro プランの使用量と請求で確かめる。手順は [`calibration-vercel-pro.md`](../../spikes/concept-2026-10-31/calibration-vercel-pro.md)。
  🔒 実数値は `.claude-personal/`（gitignore）に置き、リポジトリには結論だけを残す。
- 03 §9 の `interpretation`（採用した解釈 + 退けた解釈 + `verifiedAt`）。

### D-11 コストに効く仮定は、幅ではなく選択肢として扱う（確定・2026-10-31）

- ユーザーの方針: コストに効く仮定こそ、シナリオの選択肢・ユーザーの選択肢・見積の重要ポイントとして扱う。
- 01 §8「判断ポイント」。見積では、境目の値（反転点）を「重要な前提」として 1 文で添える。ゲームでは行動（画像圧縮・最適化など）になる。
- D-09 の「感度・閾値の表示を必須機能にする」は、この形に置き換える（幅・感度の帯は出さない）。

### D-12 プロダクトの軸は「プラットフォームの前提が生む重要なポイント」（確定・2026-10-31）

- ユーザーの言い換え: Web アプリケーションプラットフォームの前提で重要なポイントを扱える仕組み・ゲームにする。
- README「目的」の冒頭に置く。実装上は「プラットフォームの前提（データ）× アプリ側の判断（判断ポイント）」の交点として扱う（01 §8.1）。
- 見積の「重要な前提」とゲームのイベント・行動の説明は、前提に付けた同じ 1 文を使う。

### D-13 MVP の VPS はさくらの VPS 2GB（東京）の 1 プランに固定する（確定・2026-10-31）

- ユーザーの指示: さくらの VPS の 1 プランを選んで固定でよい。上限にかからなければ固定費くらいしかかからない想定。上位プランは後から入れる。
- 2GB（3 vCPU・SSD 100 GB・月 1,958 円 税込）を選んだ。Next.js・MySQL・nginx を同居させる最小の現実的な構成のため。
- Q-01 はこれで解消。海外（Hetzner）は調べたが MVP では使わない。
- スパイクの 2 回目で、1000 万 PV まで固定費のまま・効くのは共有回線（85%）と確認した（spikes の README）。

### D-16 金額・使用量は普通の number で計算する（確定・2026-10-31）

- ユーザーの確認: 10 進数ライブラリは要るか。→ 実測し、浮動小数点で困るのは小数の量を小数の単位で切り上げる境界だけと分かった
  （`0.1 × 3` を 0.1 単位で切り上げると 0.4。金額の誤差は相対 10⁻¹⁵ 程度で表示の桁に届かない）。number を推奨し、ユーザーが選んだ。
- 規律は 02 §3（`ceilUnits` に切り上げを閉じ込める・量は整数の単位・丸めは表示だけ）。
- 理由: 精度を決めるのは仮定のほうで、10 進数の代償（`a.times(b)` 形式の読みにくさ、ゲームや規模の掃引での数十〜百倍の遅さ）に見合わない。
- P1-2 は一度 big.js で実装したが、コミット前に number へ差し替えた。

### D-17 ゲームデザイン（確定・2026-10-31。grill で G-01〜G-07 を決めた）

> ⚠ **一部改定済み**（満足度の要素・停止の扱い）→「D-18」（2026-10-31）
> ⚠ **一部改定済み**（G-04 のプロバイダーをまたぐ構成を将来の範囲に）→「D-20」（2026-10-31）

- 出発点: 試作を触ったユーザーの指摘 F-1〜F-3（続いている感じがない・改善を全部やれば終わり・移行を迫る理由がない）。
- G-01 満足度: 要素（可用性・速さ・画質・鮮度）ごとの段階で持ち、シナリオの重みで合計。成長と解約に効く。
- G-02 開発の手間: 月ごとのポイント。改善・乗り換え・出来事・自前運用が取り合い、余りが機能開発へ。VPS の作業費はポイントに置き換える。
- G-03 出来事: 状態で起きる・提案として来る・台本の 3 種類。**乗り換えを迫るのはまれな大きなイベント（低確率）**（ユーザーの補足）。
- G-04 部品: Cloudflare を先に深く（ISR のキャッシュ・画像・DB・リアルタイム）。不適切な選択も選べる。
- G-05 見込み: 直近の伸び率で外挿。残り期間内に超えるものだけ出し、外れたら理由を振り返りに出す。
- G-06 シナリオ: 記事コミュニティ 1 本を深く、データで定義。2 本目はデータ追加だけで足せるかの検証。
- G-07 評価: 合否（所持金・満足度の平均）+ 軸ごとの成績（1 つの点数にしない）+ 振り返り。
- 詳細は 07。実装は 07 §8 の GD-1〜GD-5 の順。

### D-18 GD-2（満足度と開発の手間）の詳細（確定・2026-10-31）

- 07 §9 の案に、ユーザーが U-1〜U-8 を判断した。値（段階の境目・重み・ポイント・率）はゲーム上の仮定。
- U-1: 満足度に 5 つ目の要素「機能」を足す（機能開発に回せた手間の累計で段階を決める）。D-17 の G-01 の 4 要素を改定。
- U-2: **止まった月の上限（2 回以内）も合否に残す**。合格 = 所持金 ≥ 目標・満足度の 12 か月平均 ≥ 0.75・止まった月 ≤ 2。D-17 の「停止は可用性に吸収し、別の条件にしない」を改定。
- U-3: 成長は**前月と平均した評判**（(今月 + 前月) / 2。1 か月目は今月）で決める。
- U-4: 手間のポイントは繰り越さない。
- U-5: 乗り換えの期間中は**新旧両方の構成のインフラ費用を払う**。
- U-6: 機能開発が進むと SSR の CPU が重くなる（最適化を繰り返す理由にする）。
- U-7: 規模の見直しは GD-3 で行う（GD-2 は今の成長 40% に合わせる）。
- U-8: プラン変更と乗り換えの区別を GD-2 に前倒しする（07 §8 の表を直した）。

### D-19 ゲームオーバーの条件（確定・2026-10-31）

- ユーザーの指摘（試作を触った感想）: 止まった月の上限を超えたら 12 か月目を待たずに終わる。規約違反は続けられないようにする。
- 止まった月が上限（2 回）を超えた月にゲームオーバー（理由と月を結果に出す）。所持金が尽きた月も同じ。
- 規約違反（利用資格の前提・`effect: 'policy'`。例: Vercel Hobby の商用利用）は、最初の月に運営元からの指摘（警告）を出し、**翌月も違反したままならアカウント停止でゲームオーバー**。
- 猶予は 1 か月。指摘の月にプラン変更すれば翌月は違反しない。乗り換え（2〜3 か月）は、**始めた時点で猶予を満たしたとみなし**、乗り換えの期間中は停止しない（ユーザー確認済み・2026-10-31）。
- 規約違反の月は「止まった月」に数えない（試作は止まる扱いだった）。数えると、乗り換えの猶予の間に停止の上限で必ず終わるため（ユーザー確認済み・2026-10-31）。
- 07 §7・§9.6。

### D-20 GD-3（シナリオのデータ化と出来事）の詳細（確定・2026-10-31）

- 07 §10 の案に、ユーザーが V-1〜V-12 を判断した。値（確率・時期の幅・倍率・増分・手間・収益）はゲーム上の仮定。
- V-1〜V-3: まれな出来事は 1 ゲームに高々 1 回・発生 25%・予告 1 か月前。今のデータで作れる P-4 → S-5（記事の引き取り → D1 の 10 GB）だけにする。料金改定は `scheduledChanges` の予告の通知だけ。SLA は GD-4 でデータを取ってから。
- V-4: 規模は 30 万 PV スタート・月 12%・話題の月 × 3（自動プレイで確かめてから値を確定）。
- V-5: 人件費は所持金に入れない。V-6: **席・メンバーの料金も GD-3 で集める**（無いなら出典つきで記録、書かれていなければ「記載なし」）。
- V-7: 話題の前兆を出す。V-8: 所持金の目標は固定値で、シード 1〜50 で公平さを確かめる。V-9: Bot の遮断は手間だけの行動。
- V-10: 前提の文が無いプールに catalog で文を足す。V-11: 提案を断っても罰はない。V-12: 1〜2 か月目は台本・提案を出さない。
- **将来の範囲**（今は実装しない）: シナリオ・出来事の候補（画像配信が増える・Node.js の機能が要る機能追加・リアルタイムチャット・リアルタイム動画共有・RDB を前提にする複雑なデータ管理）と、**プロバイダーをまたぐ構成のパターン**（画像だけ Cloudflare・DB だけ AWS など）。D-17 の G-04 で範囲外としていた組み合わせを将来の範囲に改める。07 §10.11。
