## 決定

### D-01 フロントは Vite（Next.js は使わない）（暫定・2026-10-31）

- MVP は計算をブラウザで行い、保存もローカル。サーバーの処理がないので App Router の利点（SSR・サーバーの処理）を使わない。
- 静的配信だけで動くので、比較対象のどの構成にも載せられる（02 §6 の「自分自身で検証する」ができる）。
- seseraki と同じスタック（React 19 + Vite + TanStack Router + Tailwind v4 + daisyUI）にして、知見を流用する。
- 将来クラウド保存を足すときは API を別パッケージで立てる。

### D-02 パッケージは estimator / catalog / game / web に分ける（暫定・2026-10-31）

- 見積ツールを単独で切り出せるように、estimator と catalog は game を知らない（02 §1）。
- 企画書 §7.2 のモジュール（workload・infrastructure・resource-simulation・pricing・performance）は estimator の中のディレクトリにする。
  パッケージを細かく分けすぎると、型の行き来のたびに境界をまたぐことになるため。

### D-03 振る舞いはコード、具体値はデータ（暫定・2026-10-31）

- ComponentKind はコード、ServiceOffering と PriceBook はデータ（01 §4.1）。
- 「料金変更時にエンジンを変更しない」（企画書 §3.4）を満たしつつ、メーターの導出式を DSL にしない。

### D-04 Workload は正準な入力 + 導出値（暫定・2026-10-31）

- 企画書の入力項目のうち互いに導出できるもの（MAU・PV・平均 RPS・ピーク RPS など）を独立入力にしない（01 §3.1）。

### D-16 金額・使用量は普通の number で計算する（確定・2026-10-31）

- ユーザーの確認: 10 進数ライブラリは要るか。→ 実測し、浮動小数点で困るのは小数の量を小数の単位で切り上げる境界だけと分かった
  （`0.1 × 3` を 0.1 単位で切り上げると 0.4。金額の誤差は相対 10⁻¹⁵ 程度で表示の桁に届かない）。number を推奨し、ユーザーが選んだ。
- 規律は 02 §3（`ceilUnits` に切り上げを閉じ込める・量は整数の単位・丸めは表示だけ）。
- 理由: 精度を決めるのは仮定のほうで、10 進数の代償（`a.times(b)` 形式の読みにくさ、ゲームや規模の掃引での数十〜百倍の遅さ）に見合わない。
- P1-2 は一度 big.js で実装したが、コミット前に number へ差し替えた。

### D-19 ゲームオーバーの条件（確定・2026-10-31）

- ユーザーの指摘（試作を触った感想）: 止まった月の上限を超えたら 12 か月目を待たずに終わる。規約違反は続けられないようにする。
- 止まった月が上限（2 回）を超えた月にゲームオーバー（理由と月を結果に出す）。所持金が尽きた月も同じ。
- 規約違反（利用資格の前提・`effect: 'policy'`。例: Vercel Hobby の商用利用）は、最初の月に運営元からの指摘（警告）を出し、**翌月も違反したままならアカウント停止でゲームオーバー**。
- 猶予は 1 か月。指摘の月にプラン変更すれば翌月は違反しない。乗り換え（2〜3 か月）は、**始めた時点で猶予を満たしたとみなし**、乗り換えの期間中は停止しない（ユーザー確認済み・2026-10-31）。
- 規約違反の月は「止まった月」に数えない（試作は止まる扱いだった）。数えると、乗り換えの猶予の間に停止の上限で必ず終わるため（ユーザー確認済み・2026-10-31）。

### D-43 SPA で OGP の前処理なしに話題を迎えたときのヒント（確定・2026-11-01）

- 背景: 記事コミュニティを SPA で何もしないと、VPS は 0/20 で達成しない（Next.js は 16/20）。落ちる理由は所持金だけで、どれも仮定 A-8（OGP の前処理なしでは話題の伸びが × 3 → × 2。prd/10 F-05）による。負荷・費用・満足度は Next.js と同じ。
- ユーザーの決定: `retryHintsOf` に、SPA で OGP の前処理（部品のスロット `ogp`）を付けずに話題の月を迎え、所持金の条件で落ちたときのヒントを足す。文面は「n か月目の話題で、記事ごとの SNS のカードが出ないため伸びが小さかった（前処理があれば、収益は約 +$X の見込み）」。方向は「SNS のカード（OGP）の前処理の部品を、話題の前に付ける」。部品名は出してよく、正解の構成名は出さない方針（D-40）は変えない。

### D-55 VPS の前段の CDN で HTML もキャッシュするときの再生成の数え方を直す（確定・2026-11-01）

- 既知の問題（PR #3 の本文）: 前段の CDN を「HTML もキャッシュ」（D-31）にしたとき、ISR の再生成の回数を閲覧の総数（CDN の手前）から数えるので、VPS の CPU を多めに見積もる。
- 調べた結果: 月の数は D-37 で CDN の miss と同じ式になっていて、CDN を miss して VPS に届いた閲覧と一致していた（CDN と ISR の期間が同じなので、届いた閲覧はそのつど再生成を起こす）。多めだったのはピークの時間帯だけで、閲覧はピークの miss で流すのに、再生成は月の数のまま流していた。
- 直した: estimator の simulate で、ISR のページを期間つきでキャッシュする CDN の後ろでは、再生成の流れを「CDN を miss して届いた閲覧」（月は miss・ピークはピークの miss）にした（prd/04 §2）。オンデマンド（D-49）はピークの miss の割合を月と同じとみなすので、変わらない。
- 影響（記事コミュニティ・何もしない・シード 1〜20・VPS 2GB / 4GB）: HTML もキャッシュ × 5 分でピークの CPU 使用率の最大が約 0.77 倍（2GB で 20.0% → 15.4%）。達成数・前段の CDN なし・静的と画像だけ・オンデマンドは変わらない。golden は変わらない（基準プレイに HTML もキャッシュは無い）。
- 残した点: CDN が無い構成でも、ピークの時間帯の再生成は月の数のまま流している（ピークは閲覧の密度が上がって ISR がよく当たるので、実際は少ない）。既定の構成の結果を変えないため、今回は直していない。

- 見込みとの違い: 「閲覧の薄い記事ではほぼ 0」と見込んでいたが、時間の式では逆になる。閲覧の薄いページは読まれるたびに 1 日が過ぎていて作り直すので、最大寿命の分はほぼ閲覧の回数になる。頭打ちになるのは閲覧の濃いページ（ページ数 × 30 回 / 月）。記事コミュニティは 1 記事 1 日 3 回ほどの閲覧なので、最大寿命の分が効いた。

### D-79 OpenNext の CloudFront の無効化をワイルドカードでまとめる部品（確定・2026-11-02）

- D-66 の未決（ワイルドカード・タグの無効化を部品にするか）。ユーザーの方針「費用を抑えるより複雑な構成も可能にしたい」で、推奨案で自律に決定。prd/11 §13.1「無効化のまとめ方」。
- 確かめた事実（2026-11-02 取得）: ワイルドカードは 1 パス（`/*` も）・`*` はパスの最後だけで `/dir*` は自身と配下とクエリ文字列の違いを消す。CloudFront はタグの無効化に対応（`CacheTagConfig`・タグ 1 つ = 1 パス・同じ無料枠。定額のプランでは Pro 以上）。上限はパス・タグで毎秒 150、ワイルドカードは毎秒 1。
  OpenNext の自動の無効化に、まとめ方の設定は無い（CloudFront の実装はルートごとに `/<path>` と `/<path>?_rsc=*`）。caching の文書はワイルドカードの方が安いと書く。`invalidateTags`（PR #1308・2026-10-30）は handler の任意の口で、CloudFront の実装は対応していない。
- 決定:

### D-89 1 日の時間帯の形を入れ、Cloud Run の冷えた起動・アクティブな時間を時間帯で積む（確定・2026-11-02）

### D-90 止まる DB（Aurora の 0 ACU・Neon）を時間帯で数える（確定・2026-11-02）

- 背景: D-89 の残した点。止まる DB の動いている割合を月の平均の到着率で出していたので、夜間・休日に使われない受託の業務アプリでもほぼ止まらなかった（AX-12・prd/11 §15.3）。推奨案で自律に決定。prd/04 §3.5.1・prd/11 §11・§15.3。
- 決定:
  - 時間帯の形（`timeBuckets`）があれば、区間ごとに止まっている割合 = e^(−λ_b × W)（W = 止まるまでの待ち T + 1 件の処理の時間）。時刻 t に止まっている = 直前の W 秒に 1 件も届いていない、をポアソンで出したもので、コンテナの冷えた起動 e^(−λ × idleKeepSeconds)（D-88・D-89）と同じ形。
    区間の頭の W 秒は直前の時間帯（同じ日の種類の 1 時間前）の到着も窓に入るので閉じた形で積分する（`TimeBucket` に `slotHours`・`prev`）。W が 1 時間以上なら 2 つ以上前の時間帯までたどる（レビューの指摘 OCL-C6476435。最初は境目を見ずに止まる側へ過小に数えていた）。総当たり（1 秒ごとの数値積分）と一致することをテストで確かめた。
  - 形が無ければ D-51 の λT / (1 + λT) のまま（テストで一致を確かめた）。これは到着率の揺れを指数分布で混ぜた e^(−ΛT) の平均と同じ値で、揺れの形が分からないときの近似とみる。形があれば揺れは区間で表すので区間の中は e^(−λW)（揺れを二重に数えない）。そのため平らな形は形なしと一致しない（コンテナと違う点。形なしの方が止まる側に出る）。
  - 止まるまでの待ちは公式の既定のまま: Aurora 300 秒（最短で既定。auto-pause の文書を 2026-11-02 に再確認）・Neon 5 分（D-77 で取得済み）。
  - 再開を待つ件数の割合（`NodeUsage.resumeShare` = Σ share_b × 止まっている割合_b）を出すが、速さには入れない。基準プレイの規模（月 30 万 PV〜）では DB に届く件数の 0.01% 未満（夜に止まった DB を朝の 1 件目が起こすだけ）で、コンテナの 5% の閾値（`COLD_START`）に遠く届かない。Neon の再開は数百 ms。Aurora の約 15 秒は前提の文のまま。入れるときはコンテナの冷えた起動と max を取って重さを 1 つにする（二重に効かせない）。
  - 時間帯は課金（動いている時間）だけに使い、容量の判定は `peakHourFactor` のまま（D-89 と同じ）。
- 結果（基準プレイ・何もしない・シード 1〜20。達成数・12 か月の費用の平均 / 月）:
  - 受託 × Neon: Vercel Pro × Next.js 0/20・$41.8 → **6/20**・$36.2、SPA 7/20・$40.2 → **18/20**・$34.7、Netlify Pro × Next.js 0/20・$40.1 → **14/20**・$34.6、SPA 7/20・$40.0 → **18/20**・$34.5、Netlify Personal × Next.js 0/20・$37.3 → **19/20**・$31.8、SPA 20/20・$32.6 → $27.1。動いている割合は月 30 万 PV で 0.99 → 0.71。
  - 受託 × Aurora の 0 ACU: Amplify の SPA・Next.js $76.1・$87.0 → $55.3・$66.1、OpenNext × Next.js $73.7 → $52.9（すべて 0/20 のまま。0.5 ACU は不変）。
  - 記事: 止まらない側に寄る（0.986 → 1.000）。Neon で $0.1〜0.2 上がり（Netlify Pro × Next.js + `cf-resize` は 7/20・$52.3 → $52.4）、Aurora の 0 ACU は 0.5 ACU と同じ額（$0.6 上がる）。達成数は不変。
  - **CF Paid × Next.js（目標の根拠。記事 20/20・$15.2・受託 20/20・$5.7）・golden・網羅テストは不変**（止まる DB を持たない構成は変わらない）。
- 残した点: 受託で Neon が届きやすくなった分のシナリオの釣り合いの見直し（`baselines` に Neon が無い）・金曜 23 時 → 土曜 0 時の境目・メンテナンスで起こされる分（Aurora は起きた後 20 分止まらない）・接続を開いたままにする作り（Lambda の接続の使い回しで Aurora が止まらない）。
