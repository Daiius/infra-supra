## 1. 目的と方針

### 1.1 出発点（ユーザーの案・2026-11-22）

- 3 本目のシナリオとして「将棋の棋譜解析サービス」。利用者が棋譜を上げ、将棋エンジンで解析した結果（評価値の推移・悪手の指摘など）を見る Web サービス。
- 特徴: エンジンの解析は **CPU が重く、時間が長い**。**非同期のジョブ**になりうる。**同じ局面の結果は使い回せる**。棋譜と解析の結果を**保存する**。
- 作者が手元の実装で実際に悩んだ点（§2.3）を、**プレイヤーが選ぶ選択肢**にしたい（ユーザーの追加の要望）。

### 1.2 このシナリオで学ばせること（記事コミュニティ・受託との違い）

| 項目 | 記事コミュニティ | 受託（prd/09） | 棋譜解析（このシナリオ） |
|---|---|---|---|
| 費用を決める主な量 | 閲覧（PV）・画像・ISR の再生成 | 固定費・席・DB の 10 GB・SLA（流量は込み分の内。prd/09 §9.3） | **解析の CPU 時間**と、**解析の結果の保存量**（流量より計算と在庫） |
| 中心の判断 | ページの描き方・画像の部品 | 依頼を受けるか（上限の判断） | **重い計算をどこで動かすか**（サーバー・利用者の端末）・**どれだけ深く・何本残すか**・**結果を使い回すか** |
| 失敗の形 | 込み分を超える・CPU 10 ms に当たる | D1 の 10 GB・規約違反 | 1 回の解析が実行時間の上限に当たる・VPS の CPU が埋まる・解析の結果で DB が埋まる |

- 学びの核（案）: 「**重い処理は、置き場によって費用の形（従量か容量か）と上限が変わる。質（深さ・候補の数）を上げると、計算と保存の両方が増える。使い回すと減る**」。
- お金の流れは記事コミュニティ・受託と同じ形（収益 − インフラの費用 − 一度きりの費用 = 所持金。手間ポイントは今のまま）。違うのは収益の中身・ワークロード・出来事・選ぶ設定。

## 2. 題材の想定と負荷の形

### 2.1 サービスの形（題材の想定。抽象的に）

- 画面: 棋譜の一覧・棋譜のページ（評価値のグラフ・悪手の印・候補手と読み筋）・アップロード。ログインした利用者の個人のページが大半（受託の業務アプリに近い）。解析の結果を共有するページ（SNS のカード）は任意。
- 流れ: 棋譜を上げる（書き込み 1 回・小さい）→ 解析を依頼する → **解析が全局面（手数ぶん）を順に読む**（重い・長い）→ 結果を保存する → 利用者が開いて読む（読みは軽い）。
- 解析の結果: 局面ごとに **候補手を N 本**（MultiPV）。1 本は評価値・深さ・読み筋（手の列）。悪手の判定は候補の評価値の差から出す。
- 棋譜そのものは小さい（文字列）。保存量の大半は解析の結果【推測・題材の一般知識】。

### 2.2 負荷の形（記事コミュニティとの差）

| 量 | 記事コミュニティ | 棋譜解析（想定） |
|---|---|---|
| 1 PV あたりの CPU | SSR の数 ms〜十数 ms | 閲覧は軽い。**解析 1 回は桁違いに重い**（局面ごとの思考時間 × 手数） |
| 件数の比 | 閲覧 ≫ 書き込み | 閲覧 > 解析の依頼。ただし解析 1 回の CPU が閲覧の全部を上回りうる |
| 在庫 | 記事・画像 | 棋譜（小）・**解析の結果（手数 × MultiPV × 1 本の大きさ）** |
| 使い回し | CDN・ISR（同じページ） | **同じ局面**（序盤の定跡形は多くの棋譜で共通）・同じ棋譜の再閲覧 |
| ピーク | 話題の日 | 大きな対局の日・週末の対局の後【推測】 |

### 2.3 作者が手元の実装で悩んだ点（題材の想定。固有の値は写さない）

参考にした手元の実装の形を抽象化したもの。値・名前・設定は書かない。

- **解析の置き場**: 常駐のホストの worker がジョブを取りに行って解析する形と、**軽い評価関数で利用者のブラウザ（WASM）で解析する形**を併せ持つ。ブラウザ側は候補を 1 本に絞り、サーバー側は複数本を残す。サーバー側は CPU とメモリの使用がそのまま費用になる。
- **2 段の解析**: まず短い思考時間でざっと全局面を読み（すぐ結果を見せる）、後から長い思考時間で読み直す。
- **MultiPV の本数**: 悪手の判定と検討の再利用のために複数本を残すと、保存量が本数に比例して増える。
- **保存の形**: 局面ごと・候補ごとに行を分けると行の数と索引で大きくなり、1 棋譜 1 行に詰めると桁で小さくなった（何も捨てずに、形だけで）。検索に使う値だけ列に出す。
- **深さと時間**: 深さの指定は所要時間が読めないので、時間（局面ごとの思考時間）で区切る方を選んだ。深くすると 1 局面が分単位になりうる。
- **同じ局面の索引**: 局面のハッシュで棋譜をまたいで局面を引く（同じ局面の使い回し・検索の土台）。

## 3. 今のモデルで表せること・表せないこと

### 3.1 表せること（【事実】）

- **重い処理を 1 リクエストの重さで表す**: `processing.cpuMs`・`ioWaitMs`（壁時計時間 = cpuMs + ioWaitMs。`packages/estimator/src/workload/schema.ts:14-22`）。API の 1 回の重さは `api.cpuMs` で、出来事で `WorkloadMods.apiCpuMs` に差し替えられる（`packages/game/src/scenario.ts:72-74`・`packages/game/src/workload.ts:209-210`）。受託の帳票の出力（`c-p-report`・`scenarios/contract-operations.ts:191`）と同じ型。

- **ファイルの保存**: 受託の添付ファイルと同じく画像の在庫で表せる（`perPage.images: 0`・`transformAt: 'none'`・`storedGB`・`uploadsPerMau`。`catalog/src/templates/business-app.ts:77`・`:89-96`）。棋譜は小さいので DB に入れる方が自然【推測】。
- **使い回し**: SPA の API の応答のキャッシュ（`cacheSeconds`。`workload/schema.ts:75`）・ISR・人気の偏り `zipfExponent`（`workload/schema.ts:42`）。

- **通知のメール**: `email.perMau / perWrite`（`workload/schema.ts:212`・`business-app.ts:101`）。

## 5. 作者の悩みを選択肢にする（置き場・MultiPV・深さ・使い回し・保存の形）

### 5.2 MultiPV の本数（1 局面で何本の候補を残すか。→ KF-08）

形: 解析の結果の大きさ ≒ **手数 × MultiPV × 1 本の大きさ**（1 本 = 評価値・深さ・読み筋）。

今のモデルの語彙で表せるか（【事実】と【推測】）:

| 量 | 今の語彙 | 表せるか |
|---|---|---|
| 在庫（DB の大きさ） | `dbGBPerMillionPV × 人の PV × dbRateFactor`（`month/transitions.ts:225`） | **畳めば表せる**: 1 棋譜の結果の大きさ × 100 万 PV あたりの解析の数を `dbGBPerMillionPV` に入れる。本数の違いは `dbRateFactor` の倍率（`scenario.ts:69`）で表せる【推測】。ただし `dbRateFactor` は今は出来事の提案の効果（`WorkloadMods`）で、プレイヤーが選ぶ設定ではない【事実】 |
| 書き込み（行の数） | `writesPerCall × rowsWrittenPerWrite`（`resolve.ts:651`・`workload/schema.ts:147-148`） | **表せる**: 局面・候補ごとに行を分けると `rowsWrittenPerWrite` ≒ 手数 × MultiPV、1 棋譜 1 行に詰めると ≒ 1。D1 は行の書き込みで課金する（`cloudflare.ts:528`・`:640`）ので差が出る【推測】 |
| DB の上限 | `storage-gb`（`cloudflare.ts:917` など） | 表せる（受託の D1 の 10 GB と同じ形） |
| CPU | MultiPV を増やすと探索が少し重くなる【推測・一般知識】 | `api.cpuMs` に倍率を掛ける仮定で近似 |
| 選ばせる口 | 設定は 4 つで固定（`settings.ts:13-22`） | **拡張が要る**: 設定「候補手の本数」（1・3 など。値は仮定）を足し、在庫の倍率と書き込みの行数に写す |
