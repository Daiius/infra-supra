## 1. 目的と方針

### 1.1 出発点（ユーザーの案・2026-11-22）

- 3 本目のシナリオとして「将棋の棋譜解析サービス」を作る。利用者が棋譜を上げ、将棋エンジンで解析した結果（評価値の推移・悪手の指摘など）を見る Web サービス。
- 特徴: エンジンの解析は **CPU が重く、時間が長い**。**非同期のジョブ**になる。棋譜と解析の結果を**保存する**。
- 作者が手元の実装で実際に悩んだ点（§2.3）を、**プレイヤーが選ぶ選択肢**にする（ユーザーの要望）。

### 1.2 このシナリオで学ばせること（記事コミュニティ・受託との違い）

| 項目 | 記事コミュニティ | 受託（prd/09） | 棋譜解析（このシナリオ） |
|---|---|---|---|
| 費用を決める主な量 | 閲覧（PV）・画像・ISR の再生成 | 固定費・席・DB の 10 GB・SLA（流量は込み分の内。prd/09 §9.3） | **解析の CPU 時間**と、**解析の結果の保存量・書き込みの回数** |
| 中心の判断 | ページの描き方・画像の部品 | 依頼を受けるか（上限の判断） | **重い計算をどこで動かすか**・**どう区切って投げるか**・**候補をいくつ残し、どんな形で保存するか** |
| 失敗の形 | 込み分を超える・CPU 10 ms に当たる | D1 の 10 GB・規約違反 | 1 件の解析が実行時間の上限に当たって止まる・ピークで解析が滞る・解析の結果で DB が埋まる |

- 学びの核（KF-02 で決定）: 「**重い処理は、置き場によって費用の形（従量か容量か）と上限が変わる。質（候補の数）を上げると保存が増える。区切り方と保存の形で、上限と課金の回数が変わる**」。キューの設計は扱わない（§1.3）。
- お金の流れは記事コミュニティ・受託と同じ形（収益 − インフラの費用 − 一度きりの費用 = 所持金。手間ポイントは今のまま）。違うのは収益の中身・ワークロード・出来事・選ぶ部品と設定。

### 1.3 途中で決まった前提（D-231）

grill の途中で決まり、複数の論点の前提になったもの。

| # | 前提 | 効くところ |
|---|---|---|
| P-1 | **将棋に固有の選択は絞り、インフラに効くものに集中する**。将棋の知識を増やすと問題の理解が大変になる（ユーザー）。選ばせるのは、実行時間の上限に効く「解析の区切り方」と、保存量に効く「候補の数」だけ。画面の言い方も一般的にする（MultiPV ではなく「1 局面に残す候補の数」など） | KF-05・KF-08・KF-09・KF-11 |

| P-5 | **利用者の端末の解析は、アプリを使っている間だけ動き、バッテリーを使う**。長時間の処理には向かない | 置き場の「利用者の端末」・出来事 7（裏の長い処理はサーバーで） |

## 2. 題材の想定と負荷の形

### 2.1 サービスの形（題材の想定。抽象的に）

- 画面: 棋譜の一覧・棋譜のページ（評価値のグラフ・悪手の印・候補手と読み筋）・アップロード。ログインした利用者の個人のページが大半（受託の業務アプリに近い）。解析の結果を共有するページ（SNS のカード）もある（出来事 5）。
- 流れ: 棋譜を上げる（書き込み 1 回・小さい）→ 解析を積む → **全局面（手数ぶん）を順に読む**（重い・長い）→ 結果を保存する → 利用者が開いて読む（読みは軽い）。
- 解析の結果: 局面ごとに**候補を N 個**残す。1 個は評価値・深さ・読み筋（手の列）。悪手の判定は候補の評価値の差から出す。
- 棋譜そのものは小さい（文字列）。保存量の大半は解析の結果【推測・題材の一般知識】。

### 2.2 負荷の形（記事コミュニティとの差）

| 量 | 記事コミュニティ | 棋譜解析（想定） |
|---|---|---|
| 1 PV あたりの CPU | SSR の数 ms〜十数 ms | 閲覧は軽い。**解析 1 回は桁違いに重い**（局面ごとの思考時間 × 手数） |
| 件数の比 | 閲覧 ≫ 書き込み | 閲覧 > 解析。ただし解析 1 回の CPU が閲覧の全部を上回りうる |
| 在庫 | 記事・画像 | 棋譜（小）・**解析の結果（手数 × 候補の数 × 1 個の大きさ）** |
| ピーク | 話題の日 | 大きな対局イベントの時期（出来事 1）【推測】 |

### 2.3 作者が手元の実装で悩んだ点（参考にした手元の実装。固有の値は写さない）

- **解析の置き場**: 常駐のホストの worker がジョブを取りに行って解析する形と、**軽い評価関数で利用者のブラウザ（WASM）で解析する形**を併せ持つ。ブラウザ側は候補を 1 つに絞り、サーバー側は複数を残す。サーバー側は CPU とメモリの使用がそのまま費用になる。
- **2 段の解析**: まず短い思考時間で全局面をざっと読み、すぐ結果を見せる。後から長い思考時間で読み直す。
- **候補の数**: 悪手の判定と検討の再利用のために複数を残すと、保存量が数に比例して増える。
- **保存の形**: 局面ごと・候補ごとに行を分けると、行の数と索引で大きくなった。1 棋譜 1 行に詰めると、何も捨てずに形だけで桁が小さくなった。検索に使う値だけ列に出す。
- **区切り方**: 1 局を受け取り、結果を小分けに保存しながら進め、途中で切れても続きから再開できる形にした。
- **使い回し**: 全局面の解析は棋譜ごとに読み直す。使い回しは、検討の盤の 1 局面の評価で、同じ棋譜の中が主（KF-11 で入れないと決めた根拠）。

## 3. 今のモデルで表せること・表せないこと

### 3.1 表せること（【事実】）

  - D1 は行の書き込みで課金し（`cloudflare.ts:528`・`:640`）、大きさの上限は `storage-gb`（`cloudflare.ts:917`）。
- **利用者の端末に配る重いファイル**: JS・CSS の 1 ファイルの大きさと、ブラウザのキャッシュから出す割合（`assets: { sizeKB, browserReuse }`。`workload/schema.ts:150-151`）。WASM のエンジンと評価関数の配布はこれで近似できる【推測】。
- **リアルタイム**: `realtime`（Workload）と Durable Objects 型の部品（[07](./07-game-design.md) §11）。出来事 6 の土台。

## 5. プレイヤーが選ぶもの（作者の悩みを選択肢にする）

ゲームでの位置づけの語彙:

- **部品**: スロットと選択肢。構成のカードで選ぶ（[07](./07-game-design.md) §11・`stacks/index.ts:69`）。
- **設定**: アプリ全体の値。画像の形式・サイズ違い・再検証の間隔と同じ並び（`settings.ts:13`）。
- **描き方の設定**: ページの行で選ぶ再検証の間隔など（[13](./13-route-strategies.md)・`web/src/route-plan-field.tsx:78`）。

このシナリオで新しく選ばせるのは次の 4 つ。どれもページごとの値ではないので、描き方の設定には当たらない。

| 選ぶもの | 位置づけ | 効くインフラの量 | 論点 |
|---|---|---|---|
| 解析の置き場（4 つ） | 部品（新しいスロット） | 費用の形・上限・滞留 | KF-07 |
| 解析の区切り方（3 つ） | 設定 | 実行時間の上限・書き込みの回数 | KF-05 |
| 1 局面に残す候補の数 | 設定 | 保存量（行の大きさ）・書き込み | KF-08 |
| 保存の形（一手を 1 行 / 1 局を 1 行） | 部品（DB の使い方） | 書き込み・読みの回数の課金・在庫 | KF-12 |

**選ばせないもの**: 解析の深さ（固定。KF-09）・棋譜をまたぐ結果の使い回し（入れない。KF-11）・GPU とメモリ（構成の既定。KF-13）。P-1 のとおり、将棋に固有でインフラへの効きが弱いもの、または題材として不自然なものを外した。

### 5.1 解析の置き場（KF-07。最初の版から 4 つとも。**実装済み（PR-5・`kifu/04-analysis-placement`・D-235）**）

| 選択肢（部品の id） | 費用の形 | 当たる上限・前提 | 満足度への効き方（仮定。PR-8 で実装・§5.5） | 表し方（実装） |
|---|---|---|---|---|
| ① アプリと同じ実行環境（`same`。既定） | 従量: 解析の CPU・壁時計時間・メモリ × 件数（VPS の構成は月額の中で、VPS の使用率に入る） | 1 件の CPU・実行時間の上限（§9.2）。区切り方で当たり方が変わる | 増えれば並べて動くので滞りにくい。費用はそのまま増える | 非同期の API（estimator の `api-async` のクラス）を API と同じ経路に流す |
| ② 常駐の worker（`worker-vps-2gb`・`worker-vps-4gb`。さくらの VPS をアプリとは別に 1 台） | 容量: VPS の月額（PV によらず定額）。CPU の使用率が埋まると滞る | worker の VPS の CPU・メモリの使用率（[04](./04-resource-simulation.md) §3.7。前提 `host:cpu:analysis-worker`）。1 件の時間の上限は無い | ピークで滞ると速さ −（§5.5）。維持の手間 +（自前運用。game の `selfHostedOf` が worker の VPS も数える） | 非同期の API の経路を `[analysis-worker, …アプリの API の経路]` にする。worker は結果をアプリの API（HTTPS）に送り、アプリの処理（関数・コンテナ・ホスト）はその 1 件を受けて書くだけの CPU（`classCpuMs`・`ANALYSIS_RESULT_CPU_MS` 5 ms・仮定）。DB の書き込みはそのまま |

### 5.4 保存の形（KF-12。部品。**実装済み（PR-7・`kifu/06-storage-shape`・D-237）**）

選択肢の言い方は「**一手を 1 行**」と「**1 局を 1 行**」（ユーザー）。

試算の要点（仮定の規模で、catalog の課金の単位を当てた。値は規模の仮定しだいなので、比べ方だけを写す）:

- **回数で課金する DB では大きく効く**。
  - Firestore（文書の数で課金）: 一手を 1 行は、1 局を 1 行の数十倍になった。
  - DynamoDB: 1 KB に満たない小さな行でも書き込みを 1 単位ずつ払うので、一手を 1 行は約 10 倍になった。1 局を 1 行に詰めると、書き込みは中身の大きさそのものまで下がる。それ以上は減らない。
- **D1 は、10 GB の上限に当たる時期が動く**。行の読み書きは込み分の内に収まり、効くのは容量だけ。一手を 1 行は、行ごとのオーバーヘッドの分だけ大きくなる。上限に当たる量が約 1.5 倍動く。
- **容量・固定費で課金する DB（Supabase・RDS・Aurora・Cloud SQL・Neon）では、ほぼ効かない**。差は行のオーバーヘッドの分の容量だけ。
- 1 局を 1 行の代わりに、棋譜をまたぐ検索はしにくくなる（機能の仮定で釣り合わせる案）。1 局の更新は 1 項目全体の書き直しになる【推測】。

R-2 の確認（2026-11-23 に公式の原文で取り直した。出典は catalog の各事業者の facts）:

- DynamoDB: 書き込みは項目ごとに 1 KB へ切り上げる（BatchWriteItem も項目ごと。上書きの UpdateItem は前後の大きいほうの項目全体）。読み取りは Query なら返した項目の合計を 4 KB へ切り上げ、GetItem・BatchGetItem は項目ごと、Scan は評価した項目で数える。項目の大きさは属性名も含み、400 KB まで。項目ごとの 100 B は**保存の課金のためだけ**（読み書きの単位には入らない）。
- Firestore: 読み取りは返した文書の数（0 件でも 1 回）。索引のエントリは 1,000 件ごとに 1 回だが、範囲の条件が 1 つまでの問い合わせは数えない。offset で飛ばした文書も数える。書き込みは set・update の 1 回が 1 回で、大きさによらない。1 文書は 1 MiB まで。
- D1: rows read は走査した行（行の大きさによらない。索引が当たらないと全表を走査した分）。rows written は書いた行で、索引の列を含む書き込みは索引の分も 1 行足す。

実装（D-237）:

| 量 | 一手を 1 行 | 1 局を 1 行 |

| 1 件の書き込みの行 | ① 1 行・② 手数ぶん・③ 塊の手数 + 続きの位置の 1 行（それぞれ + 棋譜の行を件数に均した分） | どの区切り方も 1 件に 1 局の行を 1 行（① ③ はその行を上書きする。③ の続きの位置は 1 局の行の中に持つ） |

- **試算どおり**: Firestore は読みの文書の数（棋譜を開くたびに 101 → 2）で効く。② なら書き込みも 1 局 2 回になり、約 15〜30 倍の差。DynamoDB は ② で 1 行 1 KB 未満の切り上げの無駄が消えて下がる（中身の大きさまで）。D1 は行の読み書きが込み分の内で、効くのは保存の超過分（候補 3 で 6.85 GB / 5.66 GB。10 GB の上限には 30 万 PV では当たらない）。容量・固定費の DB（Supabase・RDS・Aurora・Cloud SQL・Neon）はほぼ効かない。
- **試算と違う点**: ① で 1 局を 1 行にすると、DynamoDB は上書きのたびに行全体の大きさで数えるので **約 7〜19 倍に増える**（試算は 1 局を 1 回で書く前提だった）。保存の形は区切り方と組み合わせて選ぶものになる（1 局を 1 行は ② で効く・① では Firestore の読みだけ下がる）。DynamoDB の ② の差（約 5 倍 / 2 倍）が試算（約 10 倍 / 6 倍）より小さいのは、一手を 1 行の 1 行に候補の数ぶんを入れた（試算は 1 候補 1 行）ため。
- DynamoDB の読みは今も DB の応答の大きさ（`db.responseKBPerQuery`。全体で 1 つ）を 4 KB へ切り上げて数えるので、保存の形で替わらない（実際も Query の合計と GetItem の 1 項目でほぼ同じ）。

### 5.5 満足度（KF-10。**実装済み（PR-8・`kifu/07-analysis-satisfaction`・D-238）**）

| 要素 | 効き方（仮定） | 感度 |
|---|---|---|
| ピークの滞留 | 置き場の容量（worker の CPU）がピークの到着に追いつかないと −。併用・サーバーレスの利点が出る | — |
| 解析の速さ | 速いほど +。基準は「ページを開いている間に終わる」（P-4） | **高** |
| 解析の正確さ | 正確なほど +（端末の軽い評価関数は −、候補の数が多いと +） | 速さより**低** |

- 速さの判定（`rules.ts:163-168`）は SSR の CPU だけを見るので、滞留・速さ・正確さの判定を足す（PR-8）。記事・受託の golden を変えないよう、このシナリオだけで効く形にする。

実装（D-238）:

- 満足度の要素を 2 つ足した: **解析の速さ**（`analysisSpeed`）・**解析の正確さ**（`analysisAccuracy`）。ピークの滞留は別の要素にせず、解析の速さの待ちとして効かせる。`SatisfactionRules.analysis` を持つシナリオだけで判定し、ほかのシナリオでは段階を持たない（`Stages` に無い。満足度の点・画面・集計は今までのまま）。判定は game の `analysis-satisfaction.ts`（`judgeAnalysis`）。
- 重み（`KIFU_SATISFACTION_WEIGHTS`。仮定・合計 1）: 可用性 0.35・速さ 0.15・機能 0.15・**解析の速さ 0.25**・**解析の正確さ 0.1**（反映スピード・画質 0）。満足度 → 評判 → 成長（KF-03 の間接の効き方）は今までの作法のまま。
- **解析の速さ** = 1 局の解析が見えるまでの時間。5 分以内が良い（ページを開いている間。P-4）、15 分以内が普通（少し離れて戻れば見える）、それより長いと悪い（`KIFU_ANALYSIS_SATISFACTION`。仮定）。
  - サーバー: 1 件の時間（起動の CPU + 局面の数 × 1 局面 + 評価関数を読む待ち + DB の待ち）× 順に解く回数。① 局面ごとは 1 局の件数を並べて動かす（サーバーレスは全部・VPS は vCPU の数まで）。② 1 局まとめては 1 件、③ 小分けは塊を続きから順に解く。
  - **ピークの滞留（B-5）**: 解析する VPS（worker の VPS、または VPS の構成の同じ実行環境・併用の本解析）のピークの時間帯の CPU の比（前提 `host:cpu:` の比 = 需要 ÷ vCPU × 使用率の上限 0.7）が 1 を超えたら、**(比 − 1) × 30 分**を待ちに足す（ピークの 1 時間のうちに積み上がった分を、届いた解析が平均して待つとみた仮定）。月の平均の比（比 ÷ ピークの係数）も 1 以上なら、1 日を通して追いつかないので「悪い」。キューの長さ・待ちの時間を正確に出すとは言わない。
  - サーバーレス（関数・コンテナ）は滞留しない。1 件の上限に当たって止まるのは、今までどおり可用性の判定（解析の速さは時間から出す）。
  - **worker の VPS だけの遅くなる前提（CPU・回線）は、ページの速さと収益の減り（遅い月）に数えない**（worker が混んでもページは遅くならない。`analysisOnlyThrottle`）。PR-5 の時点では worker の CPU に当たるとページの速さが「悪い」になっていた。VPS の構成の同じ実行環境はアプリの VPS が混むので、ページの速さも解析の速さも下がる（今までどおり）。止まる前提（worker のメモリ・ディスク）は可用性のまま。
  - 利用者の端末: 局面の数 × 1 局面 × 0.5（軽い評価関数で 1 局面は軽いが、端末はサーバーより遅いのを畳んだ値）。1 件ごとの起動はページを開いたときの 1 回なので数えない。区切り方によらない。遅い端末（その 3 倍）で段階が下がるなら、ふつうの端末の段階から 1 段下げる（端末の差）。1 局 100 手で約 3 分（遅い端末は約 10 分）なので「普通」。
  - **併用**: 端末の速報とサーバーの本解析の早いほう。VPS が滞っても速報で速さを保つ。
- **解析の正確さ** = 候補の数（3 つ以上で良い・1 つは普通）。端末は候補が 1 つに固定なので「普通」（D-244 で、軽い評価関数で 1 段下げるのをやめた。D-238 の時点は「悪い」）。併用は本解析で戻るが、**本解析の速さが「悪い」（利用者がページを離れた後に届く）なら 1 段下げる**（滞留は正確さが見えるまでの遅れとして効く）。
- **候補の数は正確さにだけ効かせる（B-7）**。機能（開発の累計）には足さない。候補の数は解析の件数と CPU も替えない（D-236）ので、速さにも効かない。
- 画面: 月の報告の満足度の札に「解析の速さ」「解析の正確さ」を足し（判定したシナリオだけ）、「良い」でない月は理由（見えるまでの時間・滞留の待ち・ピークの比・端末の時間）を「改善できる項目について」の ⓘ に出す。結果の画面の要素の平均の表も、判定した要素の列だけ出す。ヒント（⑤ 満足度の要素）にも次の一手の文を足した。

| # | 問い | 推奨案 | 決定 | 理由・補足 |
|---|---|---|---|---|
| KF-01 | 設定（フレーバー） | 自社の一般向けの Web サービス | **推奨どおり** | 記事コミュニティと同じ「自社の収益」の形で、成長と話題が効く |

### 9.2 1 件の上限（PR-3・PR-4。D-234）

測りと判定（`packages/estimator`）:

- 測り `wall-ms-per-request`（1 回の実行の壁時計の時間 = CPU + I/O の待ち）を `cpu-ms-per-request` の隣に足した。CPU と壁時計は別の上限で、両方を見る。判定するのは関数とコンテナのノード（CPU は今までどおり関数だけ）。
- 受け方（`invocation: 'http' | 'async'`）: Workload の `api.invocation`（省略は http）と、上限の `invocation`（省略は両方）。B-6 のとおり、非同期の解析は**受けて処理する側**（キューの受け手・Cron・バックグラウンド関数）の上限で判定する。キューの費用は数えない（P-2）。その受け方の流れが届かないノードでは、受け方を持つ上限の前提を出さない（記事・受託に「キューの受け手 15 分」を出さない）。
- 資源シミュレーションは、ノードごとに受け方ごとの 1 回の実行の CPU・壁時計の最大（`NodeUsage.maxBy`）と、壁時計の最大（`maxWallMsPerRequest`）を持つ。ISR の再生成は CPU と同じ数え方で、起こした閲覧の http の実行に足す。
- 設定で上げられる上限は**最大で判定**し、既定を `defaultValue` に持つ。使う量が既定を超えて最大以下なら、前提の内訳に「既定の … を超えるので、設定で … まで上げる前提です」と出す（止めない）。
- game の止まる判定は前提の `hit` と `effect`（block）を見る今の仕組みのまま（`month/outcome.ts` の `stopsSite`）。新しい上限はどれも `onExceed: 'block'` なので、当たればその月は止まる。

調査メモ（要約経由）との照合: 数値はどれも原文と一致した（Lambda の最大 1,800 秒、Workers の Cron の CPU が間隔 1 時間以上なら 15 分まで、など）。メモに無く原文で足したもの: Lambda の既定 3 秒（configuration-timeout）、Cloud Run を Cloud Tasks・Pub/Sub から呼ぶときはその側の期限が効くこと、Firebase Hosting から Cloud Run へのリクエストの 60 秒（下の「数えないもの」）。

確認できず・数えないもの:

- **Netlify Functions の 1 回の実行の CPU の上限**: 文書に無い（メモリ 1 GB とそれに比例した計算量だけ）。入れない。
- **Amplify Hosting の SSR の 1 件の CPU の上限・1 件の実行の上限**: 文書に無い（上の 15 分は実行インスタンスの寿命）。
- **Firebase（Cloud Functions for Firebase）の既定の timeout**: 置き場の候補の構成に無い（Firebase Hosting は CDN としてだけ使う）ので取得もしない。
- 同期の HTTP の前段の上限（CloudFront のオリジンの応答 30 秒（既定）・API Gateway の HTTP API 30 秒・Firebase Hosting から Cloud Run への 60 秒）: 関数・コンテナのノードでなく前段のノードの上限で、解析は非同期（P-2）なので今は数えない。同期で受ける重い処理を足すときに見直す。
- Lambda Managed Instances の 90 分・Vercel の 1,800 秒（Beta）・Workers の Cron の 15 分の CPU: 別の実行の形・Beta なので採らない。

棋譜解析のテンプレートでの当たり方（`packages/catalog/src/templates/kifu-analysis.test.ts`）:

- 局面ごと（既定・PR-3 の時点は 1 件 = CPU 500 ms + 待ち 20 ms。PR-6 からは CPU 5 秒 + 待ち 1.02 秒）では、当たるのは Workers Free の CPU 10 ms だけ。
- PR-3 の時点では 1 局まとめての目安（CPU 50 秒）でも壁時計の上限には当たらなかった。PR-6 で 1 局面の重さと固定の重さを置き直し、区切り方ごとに止まる構成を §5.2 の表にした（D-236）。
- 1 件 20 分の架空の重さなら、15 分の上限（Workers の受け手・Netlify のバックグラウンド関数・Amplify）と Vercel の関数（300・800 秒）に当たり、Lambda（30 分）と Cloud Run の非同期（30 分）には当たらない。

記事・受託への影響: 基準プレイの golden（`game.test.ts`・`contract.test.ts`）と組み合わせの総当たり（`pnpm test:sweep`）は変わらない。SSR・API は数十 ms なので、増えた前提はどれも当たらない（使用率 0% 前後）。費用と前提のハッシュ（`route-strategies-equivalence.test.ts` の 2 つ目の記録）は前提の数が増えた分だけ変わるので取り直した。増えた前提を除いたハッシュが前の記録と一致する（費用・使用量・今までの前提の当たりと使用率は 1 つも変わらない）ことを確かめてから取り直した。
