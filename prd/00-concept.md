# Web Infrastructure Simulator — 企画・開発仕様書

## 1. プロジェクト概要

### コンセプト

実在するクラウドサービスやホスティングサービスを組み合わせてWebアプリケーションのインフラを設計し、実際の料金体系に基づくコスト見積もりと、サービス運営のシミュレーションを行うWebアプリケーションを開発する。

本アプリケーションには、共通のシミュレーションエンジンを利用する2つのモードを設ける。

**① Infrastructure Estimator（見積モード）**

開発予定のWebアプリケーションについて、必要な機能、アクセス規模、データ量、通信量などを入力し、インフラ構成ごとの月額費用や性能上の制約を比較する。

**② Infrastructure Tycoon（ゲームモード）**

与えられたWebサービスの要件に対してインフラを設計し、サービスを運営するシミュレーションゲーム。

時間経過に伴うユーザー増加、アクセス急増、機能追加、障害などに対応しながら、収益性、可用性、性能、運用負荷を最適化する。

### 目指す体験

- 実際のクラウド料金を用いてインフラ構成を比較できる
- Webサービスの性質によって最適なインフラが変わることを体験できる
- 無料枠、従量課金、固定費の違いを理解できる
- トラフィック増加によるボトルネックやコスト増加を予測できる
- 初期費用だけでなく、運用・移行・保守のコストも考慮できる
- インフラ設計のトレードオフをゲームとして楽しめる
- ゲームで得た知識を実際のWebアプリ開発に活用できる

### 基本方針

**料金は可能な限り実在する価格データに基づき、性能は明示された仮定に基づいてシミュレーションする。**

ゲームとしての面白さのために架空の料金を設定することは原則避ける。

ただし、実際には測定できない性能や障害確率などについては、シミュレーション上の仮定として扱う。

実測値、公開仕様、推定値、ゲーム上の仮定を区別できる設計とする。

## 3. 共通の設計モデル

両モードは同じデータモデルと計算エンジンを使用する。

### 3.1 Workload Model

Webアプリケーションの利用状況と処理内容を定義する。

主な入力項目：

**トラフィック**
- MAU / DAU
- 月間PV
- 1ユーザーあたりのページ閲覧数
- 1ページあたりのAPI呼び出し回数
- 平均RPS・ピークRPS
- 時間帯別のアクセス分布
- 一時的なアクセススパイク倍率

**静的コンテンツ**
- HTML / JavaScript / CSSの平均転送量
- 画像の枚数と平均サイズ
- 動画の平均サイズ・再生時間・ビットレート
- CDNキャッシュヒット率
- ブラウザキャッシュによる再取得率

**アプリケーション処理**
- 静的配信 / SSR / APIの割合
- APIリクエストあたりのCPU処理量
- リクエストあたりのメモリ使用量
- バックグラウンドジョブ数
- バッチ処理の実行頻度

**データベース**
- 読み取り・書き込み頻度
- 1クエリあたりの読み取り行数
- 1クエリあたりの書き込み行数
- データベース容量
- データ増加速度
- クエリの複雑性
- 必要な同時接続数

**リアルタイム通信**
- WebSocketの同時接続数
- メッセージ送受信頻度
- WebRTCの同時セッション数
- 1セッションあたりの参加人数
- 音声・映像ビットレート
- TURNリレー利用率
- SFU経由の配信量

これらはすべて必須入力にはしない。

「簡易設定」と「詳細設定」を用意し、簡易設定では一般的な値を仮定する。

### 3.2 Infrastructure Model

インフラ構成をサービスの役割ごとに表現する。

主なコンポーネント：

- DNS
- CDN
- Static Hosting
- Serverless Functions
- Application Server
- Load Balancer
- Relational Database
- Key-Value Store
- Object Storage
- Cache
- Queue
- Background Worker
- WebSocket Server
- WebRTC SFU / TURN Server
- Monitoring / Logging

各コンポーネントに実在するサービスを割り当てる。

例：

| 役割 | サービス |
|---|---|
| Static Hosting | Cloudflare Pages、Vercel、S3 |
| Compute | Workers、Lambda、VPS |
| Database | D1、Supabase、RDS、MySQL |
| Object Storage | R2、S3、B2 |
| CDN | Cloudflare、CloudFront |
| Realtime | Durable Objects、セルフホストWebSocket |

ノード同士を接続するグラフ構造として保持する。

各接続には通信方向、通信量、レイテンシ、ネットワーク境界などの情報を持たせる。

### 3.3 Resource Simulation Engine

Workload ModelとInfrastructure Modelから、実際のリソース消費量を計算する。

出力例：

- 月間リクエスト数
- CPU実行時間
- メモリ使用量
- ストレージ使用量
- ストレージ操作数
- DB読み取り・書き込み行数
- ネットワーク転送量
- CDNとオリジン間の転送量
- WebSocket接続時間
- WebRTC転送量
- 最大同時実行数

月間合計だけでなく、時間帯別の負荷を評価できる構造とする。

### 3.4 Pricing Engine

各プロバイダーの料金体系を独立したデータとして定義する。

考慮する項目：

- 固定月額料金
- 無料枠
- リクエスト課金
- CPU時間課金
- メモリ使用量課金
- ストレージ容量課金
- ストレージ操作課金
- データ転送課金
- リージョン差
- プランごとの上限
- 超過料金
- プラン間での無料枠共有
- 最低課金単位

料金データには以下のメタデータを持たせる。

- プロバイダー
- サービス名
- プラン
- リージョン
- 通貨
- 適用開始日
- 取得日
- 出典URL
- 料金データのバージョン

料金表はアプリケーションコードから分離する。

料金変更時にエンジンを変更することなく、データ更新のみで対応できるようにする。

無料枠については、サービス単位ではなくアカウント・プロジェクト・プラン単位で共有される場合も表現できるようにする。

実際の請求額は税金、為替、割引、契約条件によって異なるため、概算であることを明示する。

### 3.5 Performance Engine

性能・可用性に関する推定を行う。

主な評価項目：

- 最大処理能力
- CPU・メモリ使用率
- DB負荷
- キュー滞留
- p50 / p95 / p99レイテンシ
- エラー率
- 可用性
- ボトルネック

公開されているサービス制限は実際の仕様に基づく。

アプリケーション固有の性能は、仮定された処理コストやベンチマークプロファイルから推定する。

単に月間リクエスト数が上限未満という理由で、高い可用性や性能を保証しない。

### 3.6 Business Simulation Engine

ゲームモードで使用する経営シミュレーションエンジン。

主な変数：

- 売上
- インフラ費用
- 運用費用
- 移行費用
- 月次利益
- 累積キャッシュ
- ユーザー満足度
- ユーザー数
- 解約率
- サービス稼働率

売上モデルには以下を想定する。

- 月額サブスクリプション
- 広告収入
- 従量課金
- 法人契約
- 固定月額の受託運用費

売上モデルもシナリオ定義から差し替え可能にする。

## 4. 見積モード

### 4.1 基本フロー

1. Webアプリケーションの種類を選択
2. 必要な機能を指定
3. 想定ユーザー数・アクセス量を入力
4. インフラ構成を選択
5. 月額コストと性能を推定
6. 別構成と比較
7. 結果を保存・共有

### 4.2 アプリケーションテンプレート

初期テンプレート：

- 静的Webサイト
- SSRを含むWebサイト
- ToDoアプリ
- 画像投稿サービス
- 動画配信サービス
- 検索機能を持つデータベースアプリ
- WebSocketチャット
- WebRTCビデオ会議
- SaaS型業務アプリ

テンプレートには初期Workload Modelを設定する。

### 4.3 見積結果

以下を表示する。

**費用**
- 月額合計
- コンポーネント別費用
- 固定費・従量課金の内訳
- 無料枠の消費状況
- 月額・年間費用
- 予測値の不確実性

**性能**
- 想定負荷に対する余裕
- ボトルネック
- サービス制限への接近度
- 推定レイテンシ

**比較**
- 複数構成の料金比較
- アクセス増加時の費用曲線
- 構成ごとのメリット・デメリット
- 料金以外の制約

見積結果には、使用した料金データのバージョンと仮定条件を保存する。

### 4.4 シナリオ比較

例えば月間PVを次のように変化させて比較できる。

- 1万PV
- 10万PV
- 100万PV
- 1000万PV

PVだけでなく、画像転送量やDB書き込み頻度も変化させられるようにする。

単一の最安構成を提示するだけでなく、負荷規模ごとに有利な構成が変わる様子を可視化する。

## 5. ゲームモード

### 5.1 基本ループ

1. シナリオを選択
2. 初期要件・予算・収益モデルを確認
3. インフラ構成を設計
4. 運用を開始
5. 時間を進める
6. アクセス・売上・費用・性能を計算
7. イベントが発生
8. 必要に応じてインフラを変更
9. 目標達成またはゲームオーバーを判定

### 5.2 時間モデル

基本単位は1か月。

ただし、負荷計算では時間単位またはより細かい粒度のアクセス分布を使用できるようにする。

時間経過はプレイヤーの操作で進めるターン制を基本とする。

リアルタイム進行はMVPでは不要。

### 5.3 イベント

想定イベント：

**アクセス関連**
- SNSで話題になる
- インフルエンサーに紹介される
- 検索エンジンからの流入増加
- Botによる大量アクセス
- DDoS

**サービス関連**
- 画像投稿機能の追加
- 動画アップロード機能の追加
- 全文検索の追加
- リアルタイム通知の追加
- WebSocketチャットの追加
- WebRTC通信の追加

**インフラ関連**
- 無料枠の超過
- クラウドサービスの料金改定
- リージョン障害
- DBの容量不足
- CPU・メモリ不足
- 接続数上限への到達
- キャッシュ設定ミス

**ビジネス関連**
- 法人顧客の獲得
- SLA要件の追加
- 予算削減
- 収益モデル変更
- 顧客離脱

イベントは、発生条件、確率、効果、継続期間をデータとして定義する。

### 5.4 プレイヤーが取れる行動

- インスタンスサイズ変更
- プラン変更
- プロバイダー変更
- CDN追加
- キャッシュ設定変更
- DB変更
- ストレージ変更
- サーバー台数増減
- ロードバランサー追加
- アプリケーション最適化
- 画像圧縮
- 動画品質変更
- 機能追加の延期
- 新機能への投資

行動には必要に応じて費用、作業時間、移行リスクを設定する。

### 5.5 ゲーム評価

単純なコスト最小化だけでは評価しない。

評価軸：

- 累積利益
- キャッシュ残高
- 可用性
- レイテンシ
- ユーザー満足度
- 顧客維持率
- 運用工数
- システムの拡張性

例えば、最安の単一VPS構成が短期的には有利でも、障害リスクや運用工数によって長期的には不利になる場合がある。

一方で、小規模サービスに過剰な冗長化を導入しても評価は下がる。

### 5.6 初期シナリオ

**シナリオA：個人開発ToDoアプリ**

低トラフィック、DB永続化、少額のサブスクリプション収益。

目的：無料枠や低価格プランを活用して黒字運営する。

**シナリオB：人気投票サイト**

普段は低トラフィックだが、SNSで拡散するとアクセスが急増する。

目的：低い固定費を維持しながらスパイクに対応する。

**シナリオC：画像投稿サービス**

ユーザー数と画像保存量が継続的に増加する。

目的：ストレージ費用と転送費用を最適化する。

**シナリオD：動画共有サービス**

大きな転送量とストレージ消費が発生する。

目的：画質、費用、収益性のバランスを取る。

**シナリオE：リアルタイムコミュニケーション**

WebSocketやWebRTCを使用する。

目的：接続数、帯域、遅延、運用コストを最適化する。

## 7. 技術設計方針

### 7.1 基本構成

TypeScriptを中心に実装する。

フロントエンドにはReactを使用する。

フレームワークとしてNext.js App RouterまたはViteを検討する。

アーキテクチャエディタにはReact Flow系のライブラリを検討する。

グラフ表示にはRechartsなどを利用する。

### 7.2 シミュレーションエンジン

シミュレーションの計算部分は、UIやサーバー実装から独立したTypeScriptモジュールとする。

例：

- `workload`
- `infrastructure`
- `resource-simulation`
- `pricing`
- `performance`
- `business-simulation`
- `scenario`

純粋関数を中心に設計する。

入力条件と料金データが同一なら、同一の計算結果が得られること。

ゲームのランダムイベントにはシード値付き乱数を使用する。

### 7.3 データ永続化

MVPではローカル保存を優先する。

見積条件、アーキテクチャ構成、ゲーム進行状況をJSON形式で保存・読み込みできるようにする。

将来的にユーザー認証やクラウド保存を追加できる構造にする。

### 7.4 料金データ

料金データはJSONなどの構造化形式で管理する。

実在サービスの料金を収集する際は、公式料金表を一次情報とする。

料金更新を容易にするため、プロバイダー別の定義ファイルを用意する。

将来的な料金データの自動取得も考慮するが、MVPでは手動更新でよい。

## 10. 品質要件

### 計算の正確性

- 料金計算は決定論的であること
- 無料枠を正しく処理すること
- 課金単位の丸めを正しく扱うこと
- 同一リソースの二重計上を避けること
- 料金表のバージョンを保存すること
- 計算根拠を追跡できること

### ゲームの再現性

- 同じシナリオ、同じシード、同じ行動なら同じ結果になること
- 保存データから同じ状態を復元できること
- ゲームバランス調整と料金計算を分離すること

### UX

- 初心者でも簡単な構成から始められること
- 詳細な設定は必要に応じて展開できること

## 11. 重要な設計原則

### 11.1 見積エンジンとゲームエンジンを分離する

見積モードは、ゲームのための架空の計算を使用しない。

ゲームモードは、見積エンジンが算出した費用を利用する。

### 11.2 実際の料金と仮定を区別する

料金、性能、障害率、ユーザー行動の各データには出典または仮定を明示する。

### 11.3 インフラの選択に唯一の正解を作らない

最適な構成はワークロード、予算、性能要件、運用能力によって変化する。

### 11.4 過度な精密化を避ける

初期段階では正確な物理シミュレーションよりも、合理的な見積もりとトレードオフの再現を優先する。

### 11.5 計算過程を説明可能にする

ユーザーが「なぜこの料金になったか」「なぜ性能が不足したか」を理解できること。

## 12. Coding Agentへの実装指示

まず既存のリポジトリ構成を確認すること。新規プロジェクトの場合は、シンプルなTypeScriptベースの構成を提案すること。

いきなり全機能を実装せず、Phase 1から段階的に進めること。

最初に以下を実施する。

1. ドメインモデルの設計
2. モジュール間の依存関係の整理
3. 料金データスキーマの設計
4. Workloadからリソース消費量への変換仕様
5. 料金計算のテストケース設計
6. MVPの実装タスク分解

実装に際しては、計算ロジックとUIを明確に分離すること。

外部料金データが未確認の場合、実際の料金であるかのような数値をハードコードしないこと。テスト用の架空料金は明確に識別すること。

計算エンジンは将来的にNode.js、ブラウザ、Web Workerなど異なる環境で実行できるようにすること。

まずPhase 1の詳細設計と実装計画を提示し、その後に実装を開始すること。
